# 02. 面试速查

## 一、架构与设计决策（6 题）

---

**Q1：为什么选择 DeepAgents 而不是原生 LangChain Agent 或纯 LangGraph？**

→ 思路：从项目需求出发，对比三种方案的匹配度

→ 回答：
> 原生 LangChain Agent 是单 Agent，没有多智能体调度能力；LangGraph 能编排流程，但子代理调度、上下文隔离、文件系统管理都需要手动实现。DeepAgents 建立在 LangGraph 之上，内置了 task 工具做子代理调度、上下文自动隔离、文件系统工具，开箱即用。对于我们这种「1 主 + N 专」的层级模式，DeepAgents 最匹配。

---

**Q2：为什么选择层级模式而不是协作模式？**

→ 思路：理解两种多智能体架构的适用场景

→ 回答：
> 层级模式是主 Agent 统一调度，子 Agent 各司其职；协作模式是去中心化，Agent 之间自由通信。我们的场景是信息获取（搜索/数据库/知识库）→ 汇总 → 生成报告，任务边界清晰，需要统一调度，层级模式更可控。协作模式适合需要多方向探索的开放性问题，但容易失控。

---

**Q3：主 Agent 的 system_prompt 里最重要的规则是什么？**

→ 思路：理解 Prompt 设计中的核心约束

→ 回答：
> 最重要的是**两阶段执行顺序**：必须先调用子 Agent 获取完整信息，确认拿到全部信息文本后，再调用文件生成工具。这条规则防止 Agent 在信息不全时就生成文档（用占位符或编造内容）。另外还有工作目录强制要求——所有文件操作必须在指定目录下，防止文件乱放。

---

**Q4：子 Agent 的 description 应该怎么写？写得不好会怎样？**

→ 思路：description 是主 Agent 调度的唯一依据

→ 回答：
> description 必须具体、动作导向，说明这个子 Agent 能做什么、什么时候该用它。比如网络搜索助手的 description 写了「在需要进行非内部信息的公开信息查询时务必使用此助手」。写得不好会导致主 Agent 调度错误——该用数据库的去用了搜索，该用搜索的去查了数据库。

---

**Q5：为什么要强制"信息获取和文档生成分离"？**

→ 思路：防止 LLM 的常见问题

→ 回答：
> LLM 有一个常见问题：在信息不全时会编造内容填充文档。强制两阶段分离后，主 Agent 必须先拿到所有子 Agent 的返回结果，确认信息完整，再调用 generate_markdown。Prompt 中明确写了「绝不允许在获取信息之前调用文件生成工具」，这是硬约束。

---

**Q6：项目中哪些地方用了单例模式？为什么？**

→ 思路：识别代码中的单例应用

→ 回答：
> ToolMonitor 用了单例模式。原因：它需要在所有工具中全局可用，且共享同一个 WebSocket 连接管理器。如果每个工具都创建自己的 monitor 实例，就无法统一收集状态和推送消息。单例保证全局唯一，所有工具调用 monitor.report_xxx() 时都指向同一个实例。

---

## 二、ContextVars 与并发（3 题）

---

**Q7：为什么用 ContextVars 而不是全局变量？出了什么问题才发现的？**

→ 思路：从实际问题出发解释技术选型

→ 回答：
> FastAPI 是异步框架，多个用户请求在同一个线程中并发执行。如果用全局变量存 thread_id 和 session_dir，User A 的请求会覆盖 User B 的值，导致文件存到别人的目录、WebSocket 消息发错人。这就是所谓的「串台」问题。ContextVars 是 Python 3.7+ 专为 asyncio 设计的协程级局部变量，每个 Task（用户请求）有独立的值，互不干扰。

---

**Q8：ContextVars 和 threading.local 有什么区别？为什么 threading.local 不行？**

→ 思路：理解隔离粒度

→ 回答：
> `threading.local` 是线程级隔离，`ContextVars` 是协程级隔离。asyncio 的所有协程运行在同一个线程中，所以 threading.local 无法区分不同用户的请求——它们都在同一个线程里，共享同一个 local 对象。ContextVars 是 asyncio 原生支持的，每个 Task 有独立的上下文副本。

---

**Q9：如果不 reset ContextVars 会怎样？**

→ 思路：理解资源管理和潜在风险

→ 回答：
> 两个问题：一是内存泄漏，Token 对象持有对旧值的引用，长期运行会累积；二是上下文污染，如果线程池复用线程，残留的 ContextVar 值可能被下一个请求读到，导致数据串线。所以在 finally 块中必须调用 `reset_session_context()` 清理。

## 三、子 Agent 与工具（4 题）

---

**Q10：数据库查询助手为什么要"三步走"？直接让 LLM 写 SQL 不行吗？**

→ 思路：理解 Text-to-SQL 的幻觉问题

→ 回答：
> LLM 直接写 SQL 会臆造不存在的表名或字段名（幻觉）。三步走是：① `list_sql_tables` 看到真实表名；② `get_table_data` 预览数据样本，理解字段格式（比如日期是 '2026-01' 还是 '2026/01'）；③ 基于真实信息再用 `execute_sql_query` 执行。这比直接写 SQL 的准确率高很多。

---

**Q11：网络搜索助手为什么要限制"最多 5 次、至少 3 角度"？**

→ 思路：在深度和效率之间取得平衡

→ 回答：
> 「至少 3 角度」强制多维搜索，防止单次搜索就结束（广度不够）。「最多 5 次」防止 LLM 在找不到答案时无限重试，消耗大量 Token 和时间（深度有上限）。这两个约束在搜索质量和执行效率之间取得平衡。没有次数限制，一个复杂查询可能搜几十次，Token 成本爆炸。

---

**Q12：Tavily 搜索和 Google 搜索有什么区别？为什么选 Tavily？**

→ 思路：理解 Tavily 的 AI-native 设计

→ 回答：
> Google 返回的是链接+摘要，Agent 还需要进一步爬取网页才能获取内容。Tavily 是专为 AI 设计的搜索引擎，返回的是清洗后的结构化内容（网页正文），直接就能给 LLM 使用，省去了爬取和清洗的步骤，大幅减少 Token 消耗。免费版每月 1000 次请求，够开发和学习用。

---

**Q13：子 Agent 的 tools 为什么默认继承主 Agent 的工具？这有什么风险？**

→ 思路：理解 DeepAgents 的继承机制

→ 回答：
> DeepAgents 的设计是子 Agent 默认继承主 Agent 的 tools，除非显式指定。好处是子 Agent 可以使用通用工具（如文件读写）。风险是子 Agent 可能误用主 Agent 的工具（比如子 Agent 去生成了文件，这应该是主 Agent 的职责）。所以在子 Agent 配置中显式指定 tools 列表，覆盖继承，确保各司其职。

## 四、WebSocket 与实时反馈（2 题）

---

**Q14：WebSocket 连接断开后怎么处理？**

→ 思路：理解连接生命周期管理

→ 回答：
> `websocket_endpoint` 中用 `try/except WebSocketDisconnect` 捕获断开事件，调用 `manager.disconnect()` 清理连接字典。ToolMonitor 的 `_emit()` 方法在 WebSocket 发送失败时有 try-except 兜底，不会因为连接断开导致 Agent 执行中断。Agent 的核心逻辑和 WebSocket 推送是解耦的。

---

**Q15：WebSocket 和 SSE 有什么区别？这个项目为什么选 WebSocket？**

→ 思路：理解两种实时通信技术

→ 回答：
> SSE 是单向的（服务端→客户端），WebSocket 是全双工的（双向通信）。本项目选 WebSocket 是因为：① 需要维持长连接接收前端心跳（ping/pong），保持连接活跃；② 后续可能需要双向交互（如用户中断任务、发送追加指令）；③ 前端需要发送文件上传等请求，WebSocket 可以复用同一个连接。

---

## 五、Prompt 工程（2 题）

---

**Q16：Prompt 外置到 YAML 文件有什么好处？**

→ 思路：从工程管理角度思考

→ 回答：
> 三个好处：① **解耦**——修改 Prompt 不需要改代码，降低了耦合度；② **版本管理**——YAML 文件可以独立 git 追踪，方便回滚和对比变更；③ **协作**——非技术人员（如产品经理）也可以直接编辑 YAML 优化 Prompt，不需要懂 Python。用 `yaml.safe_load()` 加载而不是 `yaml.load()`，防止 YAML 中的恶意代码执行。

---

**Q17：Prompt 中的"防死循环"机制是怎么设计的？**

→ 思路：理解 LLM 自主循环的风险控制

→ 回答：
> 两层防护：① **硬性次数约束**——网络搜索最多 5 次，到了就强制停止；② **多角度要求**——至少 3 个角度搜索，确保广度。对于数据库查询助手，三步走（list→preview→SQL）本身就是一种流程约束，限制了 LLM 的自由度。这些约束本质上是用 Prompt engineering 控制 LLM 的行为边界。

## 六、异常处理与鲁棒性（2 题）

---

**Q18：如果某个子 Agent 执行失败了怎么办？**

→ 思路：理解多智能体系统的容错设计

→ 回答：
> 两层容错：① **工具层**——每个工具内部有 try-except，返回错误信息而不是崩溃，LLM 可以根据错误信息调整策略；② **Agent 层**——主 Agent 的 `astream()` 外层有 try-except 兜底，异常时通过 monitor 推送错误到前端。子 Agent 失败不会导致整个系统崩溃，主 Agent 可以尝试其他子 Agent 或降级处理。

---

**Q19：_prepare_session_environment 做了哪些防护？**

→ 思路：理解文件路径处理的安全性

→ 回答：
> 四个防护：① **目录隔离**——每个 thread_id 创建独立的 `output/session_{thread_id}` 目录；② **路径清洗**——去掉 LLM 生成的虚拟路径前缀（/workspace, /mnt/data 等），防止路径混乱；③ **上传文件迁移**——将 `updated/` 中的文件复制到工作目录，保持原始上传区干净；④ **POSIX 格式**——路径统一用 `/` 分隔符，防止 Windows 反斜杠导致 LLM 幻觉。

## 七、性能与扩展（2 题）

---

**Q20：这个系统支持多少并发用户？瓶颈在哪里？**

→ 思路：理解异步架构的能力边界

→ 回答：
> 并发能力取决于 LLM API 的并发限制（qwen-max 的 RPM/RPD）和 Tavily API 的配额（免费版 1000 次/月）。应用层本身是全异步的（FastAPI + asyncio），ContextVars 做了隔离，理论上可以支持几十到上百并发。真正的瓶颈在外部 API 调用——每次子 Agent 调用都会消耗 LLM Token 和外部 API 配额。

---

**Q21：如果要支持更多数据源（比如新的 API、新的知识库），怎么扩展？**

→ 思路：理解系统的可扩展性

→ 回答：
> 只需要三步：① 写一个新的工具文件（`tools/new_tools.py`）；② 写一个新的子 Agent 定义（`agent/sub_agents/new_agent.py`），配置 name、description、system_prompt、tools；③ 在 `main_agent.py` 的 `subagents_list` 中注册。不需要改主 Agent 的逻辑——DeepAgents 的 task 工具会自动根据 description 路由到新的子 Agent。

---

## 八、基础概念延伸（2 题）

---

**Q22：DeepAgents 和 LangChain/LangGraph 三者是什么关系？**

→ 思路：理解框架生态的层次

→ 回答：
> 层层递进：LangChain 做"动作"（LLM + 工具交互，单 Agent）；LangGraph 管"流程"（图结构，支持循环/并行/持久化）；DeepAgents 负责"组织"（内置规划器、子代理、文件系统、记忆）。DeepAgents 建立在 LangChain 和 LangGraph 之上，使用 LangGraph 作为运行时。三者不是互斥的，是层层封装。

---

**Q23：这个项目的 Text-to-SQL 和传统 RAG 有什么区别？**

→ 思路：理解两种信息获取方式的本质差异

→ 回答：
> RAG 是检索非结构化文档（PDF、Markdown），核心是向量相似度匹配；Text-to-SQL 是查询结构化数据（MySQL 表），核心是 LLM 理解表结构后生成 SQL。RAG 需要切分、向量化、检索；Text-to-SQL 需要表结构理解、SQL 生成、执行。两者互补——RAG 处理"知识"，SQL 处理"数据"。
