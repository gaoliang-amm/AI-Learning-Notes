# 01. 核心模块设计

## 模块总览

| # | 模块 | 一句话 | 解决什么问题 |
|---|------|--------|-------------|
| 1 | 多智能体调度 | 主 Agent 通过 task 工具分发任务给子 Agent | 单 Agent 注意力被多领域任务稀释 |
| 2 | 子 Agent 专业化 | 三个子 Agent 各有独立 Prompt、工具、执行逻辑 | 不同数据源需要不同处理策略 |
| 3 | 会话隔离 | ContextVars 实现协程级变量隔离 | asyncio 并发下全局变量串线 |
| 4 | 实时监控 | ToolMonitor 单例 + WebSocket 推送 | 用户看不到 Agent 在想什么 |
| 5 | 提示词管理 | YAML 外置 + Python 加载 | Prompt 硬编码在代码里，迭代困难 |

## 1. 多智能体调度

### 1.1 作用

主 Agent 不直接执行搜索或查询，而是通过 DeepAgents 的 `task` 工具将任务分发给专业子 Agent。这是整个系统的「调度中枢」。

### 1.2 为什么这么设计

主 Agent 的核心职责是**理解意图 → 拆解任务 → 调度资源 → 汇总结果**。如果主 Agent 自己也去搜索、查数据库，会面临：
- 上下文窗口被中间结果占满，丢失全局视野
- 不同数据源需要不同工具和策略，一个 Agent 无法兼顾
- 错误处理和重试逻辑耦合在一起，难以维护

### 1.3 替代方案对比

| 方案 | 优点 | 缺点 | 为什么选/不选 |
|------|------|------|--------------|
| 单 Agent 全包 | 简单、无需调度 | 上下文爆炸、专业化不足 | ❌ 不选，复杂任务会失败 |
| LangGraph subgraph | 精细控制 | 手动编排边、上下文需手动管理 | ❌ 不选，开发成本高 |
| DeepAgents task 工具 | 自动调度、上下文隔离 | 依赖 description 质量 | ✅ 选，开箱即用，快速搭建 |
| 原生 Agent 自主决策 | 灵活 | 不可预测、不可审计 | ❌ 不选，企业场景需可控 |

### 1.4 核心代码

```python
# agent/main_agent.py
subagents_list = [
    knowledge_base_agent,    # RAGFlow 知识库
    database_query_agent,    # MySQL 数据库
    network_search_agent     # Tavily 网络搜索
]

main_agent = create_deep_agent(
    model=model,
    subagents=subagents_list,              # 注册子代理
    tools=[generate_markdown, convert_md_to_pdf, read_file_content],  # 主 Agent 工具
    system_prompt=main_agent_config["system_prompt"]  # 从 YAML 加载
)
```

### 1.5 面试追问

**Q：主 Agent 怎么决定调用哪个子 Agent？**
> 通过子 Agent 的 `description` 字段。主 Agent 看到 description 后判断当前任务是否匹配，匹配则通过 task 工具分发。description 越具体，调度越准。

**Q：子 Agent 返回结果后主 Agent 怎么处理？**
> 子 Agent 的返回结果会注入到主 Agent 的 messages 中，主 Agent 根据结果决定是否需要继续调用其他子 Agent（多轮迭代），或者信息充足后开始生成文档。

## 2. 子 Agent 专业化

### 2.1 作用

三个子 Agent 各自专注一个数据源，拥有独立的 system_prompt、独立的工具、独立的执行逻辑，实现「专业的人干专业的事」。

### 2.2 为什么这么设计

不同数据源的访问方式完全不同：
- 网络搜索：多轮多角度检索，需要防死循环
- 数据库：需要先了解表结构再写 SQL，防幻觉
- 知识库：需要先获取助手列表再分层提问

如果用一个 Agent 处理所有数据源，Prompt 会变得极其复杂，且容易混淆不同数据源的边界。

### 2.3 三个子 Agent 对比

| 子 Agent | 工具 | Prompt 关键约束 | 执行策略 |
|----------|------|----------------|---------|
| 网络搜索 | internet_search（Tavily） | 至少 3 角度，最多 5 次检索 | 多轮迭代：搜索→观察→决定是否继续 |
| 数据库查询 | list_sql_tables, get_table_data, execute_sql_query | 先 list→再 preview→最后 SQL | 三步走，防幻觉 |
| RAGFlow | get_assistant_list, create_ask_delete | 先获取助手列表→再分层提问 | 两步走，分层检索 |

### 2.4 核心代码

```python
# 网络搜索子 Agent
network_search_agent = {
    "name": sub_agents_config["tavily"]["name"],         # 从 YAML 加载
    "description": sub_agents_config["tavily"]["description"],
    "system_prompt": sub_agents_config["tavily"]["system_prompt"],
    "tools": [internet_search]                           # 独立工具集
}

# 数据库查询子 Agent
database_query_agent = {
    "name": sub_agents_config["db"]["name"],
    "description": sub_agents_config["db"]["description"],
    "system_prompt": sub_agents_config["db"]["system_prompt"],
    "tools": [list_sql_tables, get_table_data, execute_sql_query]
}
```

### 2.5 面试追问

**Q：子 Agent 的 description 和 system_prompt 有什么区别？**
> `description` 是给主 Agent 看的——主 Agent 根据它决定是否调度这个子 Agent。`system_prompt` 是给子 Agent 自己看的——子 Agent 根据它决定如何执行任务。两者缺一不可。

**Q：网络搜索为什么要限制"最多 5 次"？**
> 防止 LLM 在找不到答案时无限重试，消耗大量 Token 和时间。硬性约束 + 多角度要求，在深度和效率之间取得平衡。

**Q：数据库查询为什么不能直接让 LLM 写 SQL？**
> LLM 可能臆造不存在的表名或字段名（幻觉）。三步走（list→preview→SQL）让 LLM 先看到真实的表结构和数据样本，再生成 SQL，大幅降低幻觉率。

## 3. 会话隔离（ContextVars）

### 3.1 作用

使用 Python `ContextVars` 确保不同用户的请求（协程）在服务器内部完全隔离，不会混淆文件路径、thread_id 等会话数据。

### 3.2 为什么这么设计

**问题**：FastAPI 是异步框架，多个用户请求在同一个线程中并发执行（asyncio 协程）。如果使用全局变量，User A 的数据会被 User B 覆盖。

**三种方案对比**：

| 方案 | 隔离粒度 | 适用场景 | 为什么选/不选 |
|------|---------|---------|--------------|
| 全局变量 | 无隔离 | 单用户 | ❌ 并发串线 |
| threading.local | 线程级 | 多线程 | ❌ asyncio 所有协程在同一线程，失效 |
| ContextVars | 协程级 | asyncio 并发 | ✅ 专为异步设计，每个 Task 独立 |

### 3.3 核心代码

```python
# api/context.py
from contextvars import ContextVar

_session_dir_ctx: ContextVar[Optional[str]] = ContextVar("session_dir", default=None)
_thread_id_ctx: ContextVar[Optional[str]] = ContextVar("thread_id", default=None)

def set_session_context(path: str):
    """设置当前请求的会话目录，返回 Token 用于后续重置"""
    return _session_dir_ctx.set(path)

def get_session_context() -> Optional[str]:
    """获取当前请求的会话目录，任何深层调用均可直接使用"""
    return _session_dir_ctx.get()

def reset_session_context(session_token, thread_token=None):
    """请求结束时重置，防止内存泄漏或污染后续请求"""
    _session_dir_ctx.reset(session_token)
    if thread_token:
        _thread_id_ctx.reset(thread_token)
```

**使用方式**：
```python
# main_agent.py - 请求开始时绑定
thread_token = set_thread_context(thread_id)
session_token = set_session_context(session_dir_str)

try:
    # Agent 执行...
    async for chunk in main_agent.astream(...):
        _process_stream_chunk(chunk)
finally:
    # 请求结束时清理
    reset_session_context(session_token, thread_token)
```

### 3.4 面试追问

**Q：ContextVars 和 threading.local 有什么区别？**
> `threading.local` 是线程级隔离，`ContextVars` 是协程级隔离。asyncio 中所有协程运行在同一个线程，所以 threading.local 无法区分不同请求。ContextVars 专门为 asyncio 设计，每个 Task（即每个用户请求）有独立的上下文。

**Q：为什么要 reset？不 reset 会怎样？**
> Python 的 ContextVar 在 Task 结束后不会自动清理。如果不 reset，Token 对象会持有对旧值的引用，导致内存泄漏。更严重的是，如果线程池复用线程，残留的 ContextVar 值可能污染下一个请求。

## 4. 实时监控（ToolMonitor + WebSocket）

### 4.1 作用

将 Agent 的内部思考过程（工具调用、子 Agent 调度、最终回复）实时推送到前端，让用户看到"AI 在想什么"。

### 4.2 为什么这么设计

用户提交任务后，如果只能看到最终结果，等待体验很差。实时推送思考过程可以：
- 让用户知道系统正在工作（防焦虑）
- 方便调试和定位问题
- 提升产品体验

### 4.3 架构设计

```
ToolMonitor（单例）──收集事件──→ ConnectionManager（WebSocket管理器）
     │                                    │
     ├── report_tool()                    ├── connect(thread_id)
     ├── report_assistant()               ├── send_to_thread(msg, thread_id)
     ├── report_task_result()             └── disconnect(thread_id)
     └── report_session_dir()
```

**三层输出降级**：
1. **WebSocket 定向推送**（优先）：通过 thread_id 精准推送给对应用户
2. **全局 runtime 输出**（降级）：DeepAgents 脚本模式下的 stream_writer
3. **控制台打印**（保底）：方便调试

### 4.4 核心代码

```python
# api/monitor.py
class ToolMonitor:
    _instance = None  # 单例

    def __new__(cls):
        if cls._instance is None:
            cls._instance = super().__new__(cls)
            cls._instance.websocket_manager = None
        return cls._instance

    def _emit(self, event_type: str, message: str, data=None):
        payload = {"type": "monitor_event", "event": event_type, "message": message, "data": data or {}}
        # 1. WebSocket 定向推送
        if self.websocket_manager:
            thread_id = get_thread_context()  # 从 ContextVars 获取
            asyncio.create_task(self.websocket_manager.send_to_thread(payload, thread_id))
        # 3. 控制台保底
        print(f"\n[Monitor:{event_type}] {message}")
```

### 4.5 面试追问

**Q：为什么用单例模式？**
> ToolMonitor 需要在所有工具中全局可用，且共享同一个 WebSocket 连接管理器。单例保证全局唯一实例，避免重复创建连接。

**Q：WebSocket 和 SSE 有什么区别？选哪个？**
> WebSocket 是全双工（双向通信），SSE 是单向（服务端→客户端）。本项目选 WebSocket 是因为需要维持长连接、接收前端心跳（ping/pong），以及后续可能的双向交互（如用户中断任务）。

## 5. 提示词管理（YAML 外置）

### 5.1 作用

所有 Prompt（主 Agent + 3 个子 Agent）外置到 YAML 文件，与代码解耦，便于迭代优化。

### 5.2 为什么这么设计

Prompt 是 Agent 效果的核心因素，需要频繁迭代。如果硬编码在 Python 代码里：
- 每次修改 Prompt 需要改代码、重新部署
- 版本管理混乱（代码和 Prompt 混在一起）
- 非技术人员（如产品经理）无法参与 Prompt 优化

### 5.3 替代方案对比

| 方案 | 优点 | 缺点 | 为什么选/不选 |
|------|------|------|--------------|
| 硬编码在代码里 | 简单 | 迭代困难、无法版本管理 | ❌ 不选 |
| 数据库存储 | 可在线修改 | 需要管理后台、过度设计 | ❌ 不选，项目规模不需要 |
| YAML 文件 | 解耦、可版本控制、可读性好 | 需要加载逻辑 | ✅ 选，适合项目规模 |
| JSON 文件 | 机器可读 | 不支持注释、可读性差 | ❌ 不选 |

### 5.4 核心代码

```yaml
# prompt/prompts.yaml
main_agent:
  system_prompt: |
    你是一个沃华医药公司的智能团队负责人，负责协调三个专家助手完成复杂任务
    你的团队成员如下：
    1. 网络搜索助手  2. 数据库查询助手  3. RAGFlow助手
    ...

sub_agents:
  tavily:
    name: "网络搜索助手"
    description: 负责进行网络知识搜索的智能体助手...
    system_prompt: |
      你是一个专业的网络信息查询助手...
      在检索网络知识的时候，至少检索3个角度，一共最多进行5次检索
  db:
    name: "数据库查询助手"
    description: 负责进行数据库查询的智能体助手...
    system_prompt: |
      你是一个专业的数据库查询助手...
      通常的工作流程是：先列出可用表，确认表名；如果需要，预览表数据；最后编写并执行SQL查询
```

```python
# agent/prompts.py
import yaml
from pathlib import Path

def load_prompt(file_path):
    with open(file_path, 'r', encoding="utf-8") as f:
        return yaml.safe_load(f)  # 安全加载，防止代码注入

root_path = Path(__file__).parents[1]
prompt_config = load_prompt(root_path / "prompt" / "prompts.yaml")
main_agent_config = prompt_config["main_agent"]
sub_agents_config = prompt_config["sub_agents"]
```

### 5.5 面试追问

**Q：为什么用 YAML 不用 JSON？**
> YAML 支持注释（`#`）和多行文本（`|` 块折叠标量），对 Prompt 这种长文本非常友好。JSON 不支持注释，多行文本需要转义，可读性差。

**Q：为什么用 yaml.safe_load 不用 yaml.load？**
> `yaml.load()` 可以执行 YAML 中的自定义对象和代码，存在安全风险（如果 YAML 被恶意篡改，可能执行系统命令）。`yaml.safe_load()` 只解析标准数据类型（字符串、数字、字典、列表），完全禁止代码执行。
