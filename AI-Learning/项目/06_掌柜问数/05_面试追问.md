# 掌柜问数 — 面试追问

> [!abstract] 15 个高频追问 + 标准答案，覆盖设计决策、方案对比、调试能力、异常处理、量化指标。

---

## 设计决策类

### Q1：为什么选择 DB RAG 而不是直接微调 LLM 写 SQL？

→ **思路**：从成本、效果、可维护性三个角度对比。

→ **回答**：微调 LLM 需要大量标注的 SQL 数据，成本高且数据库结构变更后需要重新训练。DB RAG 方案把元数据作为上下文喂给 LLM，不需要训练，数据库结构变了只需要更新元数据配置。对于企业内部的特定数据库，DB RAG 的效果更好、维护成本更低。

---

### Q2：为什么用三层存储（MySQL + Qdrant + ES）而不是只用一个？

→ **思路**：分析每层存储解决的具体问题。

→ **回答**：MySQL 负责结构化存储所有元数据，支持精确查询；Qdrant 负责语义匹配，用向量相似度找到"销售额"对应"order_amount"；ES 负责字段值的模糊匹配，用倒排索引找到"华北"对应数据库里的值。三者互补，单一存储无法同时满足这三种检索需求。

---

### Q3：为什么用 LangGraph 而不是 LangChain？

→ **思路**：从流程特点出发分析。

→ **回答**：LangGraph 支持图结构编排，可以定义并行节点（三路召回同时执行）和条件分支（SQL 校验通过/失败走不同路径）。LangChain 的 Chain 是线性结构，无法实现并行召回。而且 LangGraph 的 State 自动在节点间传递，代码更清晰。

---

### Q4：为什么用 jieba 分词 + LLM 扩展，而不是直接用 LLM 提取关键词？

→ **思路**：从速度和效果两个角度分析。

→ **回答**：jieba 分词速度很快（毫秒级），作为第一轮快速提取。但 jieba 是字面分词，不理解语义，所以用 LLM 做第二轮语义扩展。如果直接用 LLM 提取关键词，虽然效果好但延迟高。两者结合是速度和效果的折中。

---

### Q5：元数据配置文件由谁维护？怎么保证元数据的准确性？

→ **思路**：从工程实践角度回答。

→ **回答**：配置文件由数据分析师或数据工程师维护。我们在配置中要求填写每个字段的 description 和 alias，这些信息帮助 LLM 理解字段含义。元数据准确性通过两个机制保障：一是字段值示例（examples）从数据库实际采样，二是定期和数据库 schema 做比对，发现遗漏及时补充。

---

## 方案对比类

### Q6：向量召回的 score_threshold 设为 0.6，这个值怎么确定的？

→ **思路**：从实验调优角度回答。

→ **回答**：通过测试集调优确定的。我们用 50 个测试问题，分别测试 0.4/0.5/0.6/0.7/0.8 五个阈值，观察召回率和精确率。0.6 时召回率 85%、精确率 80%，是最佳平衡点。太低会引入噪音，太高会漏掉相关字段。

---

### Q7：为什么不直接用 RRF 融合三路召回结果？

→ **思路**：从数据规模和复杂度角度分析。

→ **回答**：当前系统是企业内部数据仓库，表和字段数量有限（约 5 张表、20+ 字段）。三路召回的结果直接去重合并即可，不需要复杂的排序融合。如果数据规模更大（比如几百张表），可以考虑用 RRF 融合排序。

---

### Q8：为什么用 EXPLAIN 校验而不是直接执行 SQL？

→ **思路**：从安全性和性能角度分析。

→ **回答**：直接执行有风险：一是可能执行 DELETE/DROP 等危险操作，二是执行错误的 SELECT 也可能消耗大量资源。EXPLAIN 是 MySQL 的语法检查命令，不执行查询只检查语法，能发现表不存在、字段名错误、JOIN 语法错误等问题，既安全又快速。

---

## 调试能力类

### Q9：如果 SQL 生成质量差，你怎么排查？

→ **思路**：从数据链路逐层排查。

→ **回答**：我会分层排查：
1. **召回层**：检查召回的表和字段是否包含正确答案需要的信息。如果漏了关键字段，说明召回策略有问题
2. **过滤层**：检查 LLM 过滤是否误删了正确信息。对比过滤前后的 table_infos
3. **生成层**：检查 prompt 中的上下文是否完整。可能是 YAML 格式化有问题，或者缺少了关键的 examples
4. **模型层**：temperature 设为 0 保证稳定性，如果结果不稳定可能是模型问题

---

### Q10：怎么测试整个系统的端到端效果？

→ **思路**：从测试方法和指标角度回答。

→ **回答**：准备 50 个测试问题，每个问题标注期望的 SQL 和结果。端到端测试：输入问题 → 系统生成 SQL → 执行 SQL → 对比结果。评估指标包括：SQL 生成准确率（语法正确+逻辑正确）、最终结果准确率、平均响应时间。目前 SQL 首次通过率 85%，加校正后 95%。

---

## 异常处理类

### Q11：如果召回结果为空怎么办？

→ **思路**：从降级策略角度回答。

→ **回答**：当前实现中，如果三路召回都为空，合并后 table_infos 和 metric_infos 为空列表，LLM 会基于空上下文生成 SQL，大概率会生成错误 SQL，然后被 EXPLAIN 校验拦截。更好的做法是：召回为空时直接返回"未找到相关数据"的提示，而不是继续生成 SQL。

---

### Q12：如果 EXPLAIN 校正后仍然失败怎么办？

→ **思路**：从错误传播角度回答。

→ **回答**：当前设计最多校正一次。如果第二次 EXPLAIN 仍然失败，错误会传播到 execute_sql 节点，抛出异常，API 层捕获后返回错误信息给前端。生产环境中可以增加最大重试次数（如 3 次），或者在多次失败后降级返回"无法生成正确 SQL"的提示。

---

### Q13：如果 LLM 调用超时怎么办？

→ **思路**：从用户体验和系统稳定性角度回答。

→ **回答**：设置合理的超时时间（如 30 秒）。超时后通过 SSE 推送错误信息给前端，提示用户稍后重试。可以在 QueryService 层加 try-except，超时异常时 yield 错误事件。生产环境中可以加请求队列和限流，防止高并发打垮 LLM 服务。

## 量化指标类

### Q14：系统的数据规模是多少？响应时间多少？

→ **思路**：给出具体数字。

→ **回答**：数据仓库有 5 张表（1 事实表 + 4 维度表），约 20+ 字段，2 个指标（GMV、AOV）。元数据库有 table_info、column_info、metric_info、column_metric 四张表。Qdrant 向量库中字段信息约 100+ 条向量，指标信息约 10+ 条。ES 全文索引约 500+ 条字段值记录。单次查询端到端响应时间约 3-5 秒（含 LLM 调用）。

---

### Q15：和掌柜智库（doc RAG）有什么区别？

→ **思路**：从检索目标和生成目标两个维度对比。

→ **回答**：掌柜智库是 doc RAG，检索的是文档内容，生成的是文本回答。掌柜问数是 db RAG，检索的是数据库元数据，生成的是 SQL 语句。核心技术差异：doc RAG 需要文档切分和 embedding，db RAG 需要元数据索引和 SQL 校验。两者都用了 LangGraph 工作流和 Qdrant 向量库，但召回策略和生成策略完全不同。
