> [!abstract] 本文档拆解系统的关键模块，每个模块包含：作用、设计决策、替代方案对比、核心代码。

## 1. 元数据知识库构建

### 1.1 作用

将数据仓库的元数据（表结构、字段信息、指标定义）同步到三层存储：MySQL 元数据库 + Qdrant 向量库 + ES 全文索引，为后续检索阶段提供数据基础。

### 1.2 为什么这么设计

元数据是 NL2SQL 的"字典"——LLM 必须知道有哪些表、哪些字段、字段的含义和取值，才能生成正确的 SQL。三层存储各自解决不同问题：

| 存储 | 解决什么问题 | 对应的查询方式 |
|------|-------------|---------------|
| MySQL 元数据库 | 结构化存储所有元数据，支持精确查询 | ORM 精确查询 |
| Qdrant 向量库 | 语义匹配用户问题和字段/指标 | 向量相似度搜索 |
| ES 全文索引 | 匹配用户问题中的维度值（如"华北"） | 关键词模糊匹配 |

### 1.3 替代方案对比

| 方案 | 优点 | 缺点 | 为什么选/不选 |
|------|------|------|-------------|
| **MySQL + Qdrant + ES（当前）** | 三层各司其职，检索精度高 | 架构复杂，需要维护 3 个系统 | ✅ 选：覆盖语义+精确+模糊三种检索需求 |
| 仅用 Qdrant | 架构简单 | 无法做精确的字段值匹配 | ❌ 不选：维度值召回效果差 |
| 仅用 ES | 全文检索强 | 语义理解弱，无法匹配同义词 | ❌ 不选：无法处理"销售额"→"order_amount" |
| 用 PgVector 替代 Qdrant | 少一个系统 | 向量检索性能不如专用向量库 | ❌ 不选：Qdrant 性能更好 |

### 1.4 核心代码

```python
# 构建入口脚本核心逻辑
async def start_build():
    # 初始化所有客户端
    embedding_client_manager.init_client()
    es_client_manager.init_client()
    # ... 其他客户端
    
    # 创建 Session 和 Service
    async with (dw_session, meta_session):
        service = MetaKnowledgeService(...)
        await service.build(meta_config)  # 一键构建三层索引
        await meta_session.commit()       # 统一提交事务
```

### 1.5 面试追问

- **Q：为什么不把所有元数据都存到一个数据库？**
  → MySQL 擅长结构化查询，Qdrant 擅长向量相似度，ES 擅长全文模糊。三者互补，各自发挥优势。

- **Q：向量化的是什么内容？**
  → 字段的 name、description、alias 分别生成向量，一个字段会生成多条向量记录，确保从不同角度都能召回。

## 2. LangGraph 工作流编排

### 2.1 作用

将整个 NL2SQL 流程编排为 12 个节点的有向图，实现：并行召回 → 合并过滤 → 生成校验 → 执行查询。支持流式输出、条件分支、状态传递。

### 2.2 为什么这么设计

NL2SQL 流程有明确的阶段划分，且某些步骤可以并行（三路召回），某些步骤需要条件分支（校验通过/失败）。LangGraph 天然适合这种"有向图 + 条件分支 + 状态传递"的场景。

### 2.3 替代方案对比

| 方案 | 优点 | 缺点 | 为什么选/不选 |
|------|------|------|-------------|
| **LangGraph（当前）** | 图结构清晰，支持并行/条件分支，状态自动传递 | 学习曲线较陡 | ✅ 选：完美匹配多阶段+并行+分支的流程 |
| LangChain Chain | 简单易用 | 不支持并行节点、条件分支弱 | ❌ 不选：无法实现三路并行召回 |
| 纯 Python 函数调用 | 最灵活 | 无状态管理、无流式支持、代码耦合高 | ❌ 不选：缺乏工程化能力 |
| 自研框架 | 完全可控 | 开发成本高，缺乏社区支持 | ❌ 不选：不需要造轮子 |

### 2.4 核心代码

```python
# 图结构定义核心
state_graph = StateGraph(state_schema=DataAgentState, context_schema=DataAgentContext)

# 三路并行召回
state_graph.add_edge("extract_keywords", "recall_column")
state_graph.add_edge("extract_keywords", "recall_metric")
state_graph.add_edge("extract_keywords", "recall_value")

# 条件分支：校验通过→执行，失败→校正
state_graph.add_conditional_edges(
    "validate_sql",
    lambda state: "execute_sql" if state["error"] is None else "correct_sql",
    {"execute_sql": "execute_sql", "correct_sql": "correct_sql"}
)
```

### 2.5 面试追问

- **Q：为什么用 LangGraph 而不是 LangChain？**
  → LangGraph 支持图结构编排，可以定义并行节点和条件分支。三路召回需要并行执行，SQL 校验需要条件分支，LangChain 的线性 Chain 无法满足。

- **Q：状态是怎么在节点间传递的？**
  → State 是 TypedDict，每个节点返回一个 dict（更新的部分），LangGraph 自动合并到全局 State。下一个节点读取合并后的 State。

## 3. 多路召回机制

### 3.1 作用

根据用户问题，从三层索引中并行召回相关的字段信息、指标信息、字段值信息，为 SQL 生成提供上下文。

### 3.2 为什么这么设计

单一召回方式有局限：
- 纯向量召回：语义匹配强，但无法精确匹配"华北"这样的维度值
- 纯全文召回：精确匹配强，但无法理解"销售额"和"order_amount"的语义关系

三路互补设计：向量召回（语义）+ 全文召回（精确）+ LLM 扩展（同义词）。

### 3.3 替代方案对比

| 方案 | 优点 | 缺点 | 为什么选/不选 |
|------|------|------|-------------|
| **三路并行召回（当前）** | 覆盖语义+精确+模糊，召回率高 | 每路都调用 LLM 扩展关键词，延迟略高 | ✅ 选：NL2SQL 对召回精度要求高 |
| 仅向量召回 | 架构简单 | 维度值匹配差 | ❌ 不选："华北"匹配不到 |
| RRF 融合排序 | 统一排序 | 增加复杂度，当前规模不需要 | ❌ 不选：数据量小，去重即可 |

### 3.4 核心代码

```python
# 字段召回核心逻辑
async def recall_column(state, runtime, config):
    # 1. LLM 语义扩展关键词
    result = chain.invoke({"query": query})
    keywords = list(set(keywords + result))
    
    # 2. 批量向量化
    keyword_vectors = await embedding_client.aembed_documents(keywords)
    
    # 3. 遍历向量去 Qdrant 搜索，按 column_id 去重
    for keyword_vector in keyword_vectors:
        column_infos = await column_qdrant_repo.search(keyword_vector)
        for column_info in column_infos:
            if column_info["id"] not in recall_columns_dict:
                recall_columns_dict[column_info["id"]] = column_info
```

### 3.5 面试追问

- **Q：为什么要把用户原始问题也加入 keywords？**
  → jieba 分词是字面分词，可能丢失语义。比如"华北地区销售总额"分词后可能丢失"销售总额"。加入原始问题作为兜底，确保向量化时保留完整语义。

- **Q：字段值召回为什么用 ES 而不用 Qdrant？**
  → 字段值是精确的维度值（如"华北"、"iPhone"），需要字面模糊匹配，ES 的 IK 分词器 + 倒排索引更适合。向量召回对短文本的精确匹配效果差。

## 4. SQL 生成与校验校正

### 4.1 作用

将召回的元数据 + 用户问题交给 LLM 生成 SQL，通过 EXPLAIN 校验语法，失败时自动触发校正。

### 4.2 为什么这么设计

LLM 生成的 SQL 不一定正确，需要验证闭环：
1. **EXPLAIN 校验**：不执行 SQL，只检查语法和表/字段是否存在
2. **LLM 校正**：将错误信息反馈给 LLM，让它根据上下文重新生成

这个闭环最多执行一次校正（避免无限循环）。

### 4.3 替代方案对比

| 方案 | 优点 | 缺点 | 为什么选/不选 |
|------|------|------|-------------|
| **EXPLAIN + LLM 校正（当前）** | 不执行就能发现语法错误，校正成本低 | 无法发现逻辑错误 | ✅ 选：覆盖最常见的错误类型 |
| 直接执行 SQL | 能发现所有错误 | 执行错误 SQL 有风险 | ❌ 不选：生产环境不安全 |
| 语法解析器校验 | 精确 | 只能检查语法，无法检查表/字段是否存在 | ❌ 不选：需要语义级别的校验 |
| 多轮校正循环 | 更鲁棒 | 可能无限循环，延迟不可控 | ❌ 不选：加最大重试次数更可控 |

### 4.4 核心代码

```python
# 校验节点
async def validate_sql(state, runtime):
    sql = state["sql"]
    try:
        await dw_mysql_repo.validate_sql(sql)  # EXPLAIN {sql}
        return {"error": None}  # 无错误 → 走执行分支
    except Exception as e:
        return {"error": f"SQL语法错误：{str(e)}"}  # 有错误 → 走校正分支

# 校正节点
async def correct_sql(state, runtime):
    # 将 SQL + 错误信息 + 上下文一起交给 LLM
    sql = await chain.ainvoke({
        "query": query, "sql": sql, "error": error,
        "table_infos": ..., "metric_infos": ...
    })
    return {"sql": sql}  # 返回新 SQL，回到校验节点
```

### 4.5 面试追问

- **Q：EXPLAIN 能发现什么错误？**
  → 表不存在、字段名错误、JOIN 语法错误、数据类型不匹配。但无法发现逻辑错误（如 WHERE 条件写反了）。

- **Q：校正会不会死循环？**
  → 当前设计 validate → correct → validate 只执行一轮。如果第二次校验仍失败，错误会传播到 execute_sql 节点抛出异常。

## 5. 流式输出与 API 层

### 5.1 作用

通过 SSE（Server-Sent Events）实时推送每个节点的执行进度和最终查询结果，提升用户体验。

### 5.2 为什么这么设计

NL2SQL 流程涉及多次 LLM 调用和数据库查询，总耗时可能 5-10 秒。如果不做流式输出，用户会长时间看到空白页面。通过 `runtime.stream_writer` 在每个节点输出进度，前端实时展示当前执行到哪一步。

### 5.3 核心代码

```python
# 节点内输出进度
runtime.stream_writer({"stage": "召回字段"})

# API 层 SSE 推送
async def search(self, query: str):
    async for chunk in compiled_graph.astream(
        input=state, context=context, stream_mode="custom"
    ):
        yield f"data: {json.dumps(chunk, ensure_ascii=False)} \n\n"
```

### 5.4 面试追问

- **Q：为什么选 SSE 不选 WebSocket？**
  → 数据流是单向的（服务端→客户端），SSE 更轻量，基于 HTTP 协议，不需要额外的连接升级。WebSocket 适合双向通信场景。
