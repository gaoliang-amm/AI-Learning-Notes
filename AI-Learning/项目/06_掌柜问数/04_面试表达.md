# 掌柜问数 — 面试表达

> [!abstract] 三种时长的口语化面试表达，可直接背诵。风格参考：像跟面试官聊天，不像念论文。

## 30 秒版（电梯介绍）

我做了一个基于 DB RAG 的 Text2SQL 系统——掌柜问数。用户用自然语言提问，系统通过 Qdrant 向量召回和 ES 全文召回，找到相关的表结构和字段信息，交给大模型生成 SQL，自动查询数据仓库返回结果。核心是 LangGraph 编排的 12 节点工作流，带自动校验和校正机制。

---

## 2~5 分钟版（系统讲解）

### 1）项目背景

这是一个面向后台工作人员的智能数据查询系统。传统方式下，业务人员想从数据仓库取数，需要写 SQL 或者找数据分析师排队。我们的目标是让业务人员直接用自然语言提问，系统自动完成 SQL 生成和数据查询。

### 2）技术架构

系统分为三层：

- **存储层**：MySQL 存元数据，Qdrant 存向量索引，ES 存字段值全文索引
- **工作流层**：LangGraph 编排 12 个节点，从关键词提取到 SQL 执行
- **API 层**：FastAPI + SSE 流式输出

核心是"三路召回"机制：jieba 分词 + LLM 语义扩展 → 向量召回字段和指标 → ES 全文召回字段值 → 合并后交给 LLM 生成 SQL。

### 3）我的职责

我主要负责元数据知识库构建、LangGraph 工作流设计、三路召回机制、SQL 生成与校验校正闭环。

### 4）技术亮点

- **三路混合召回**：向量召回覆盖语义（"销售额"→"order_amount"），全文召回覆盖精确匹配（"华北"），LLM 扩展补充同义词
- **SQL 校验校正闭环**：EXPLAIN 校验不执行就能发现语法错误，失败后 LLM 根据错误信息自动校正
- **流式输出**：每个节点执行时实时推送进度，用户不用盯着空白页等

## 5~15 分钟版（深入细节）

### 1）项目背景与目标

数据仓库里存着大量的业务数据，但业务人员不会写 SQL，每次取数都要找数据分析师，效率很低。掌柜问数的目标就是让业务人员用自然语言提问，系统自动生成 SQL 查询数据。

核心技术挑战是：怎么让 LLM 知道数据库里有什么表、什么字段、字段是什么含义？这就是 DB RAG 要解决的问题——把数据库的元数据"喂"给 LLM。

### 2）整体架构设计

系统采用分层架构：

- **API 层**：FastAPI 定义接口，SSE 流式响应，依赖注入管理资源
- **服务层**：QueryService 编排业务流程，MetaKnowledgeService 构建知识库
- **智能体层**：LangGraph 12 节点工作流，State 传递状态
- **存储层**：MySQL（元数据库+数据仓库）、Qdrant（向量库）、ES（全文索引）

数据仓库采用星型模型：fact_order 事实表关联 4 张 dim 维度表。

### 3）核心技术实现

**元数据知识库构建**：从 YAML 配置读取表和字段信息，同步到 MySQL，同时对字段的 name/description/alias 分别向量化存入 Qdrant，对维度字段的所有取值建 ES 全文索引。

**三路召回**：用户提问 → jieba 分词 + LLM 语义扩展 → 三路并行：向量召回字段（Qdrant）、向量召回指标（Qdrant）、全文召回字段值（ES）→ 合并去重 → LLM 二路过滤（过滤不相关的表和指标）。

**SQL 生成与校正**：LLM 根据召回的元数据生成 SQL → EXPLAIN 校验语法 → 失败则将错误信息反馈给 LLM 重新生成 → 最多校正一次。

### 4）遇到的挑战与解决方案

**挑战一：同义词匹配**。"销售额"和"order_amount"在字面上完全不同。解决方案是用 LLM 对用户问题做语义扩展，生成同义词列表，再用这些同义词去向量库搜索。

**挑战二：维度值匹配**。用户说"华北地区"，需要匹配到数据库里的"华北"。向量召回对短文本精确匹配效果差，所以用 ES 全文索引专门处理字段值召回。

**挑战三：SQL 语法错误**。LLM 生成的 SQL 可能有表名/字段名错误。用 EXPLAIN 校验不执行就能发现这些问题，再让 LLM 根据错误信息自动修正。

### 5）项目成果与收获

项目实现了完整的 NL2SQL 流程，支持自然语言查询数据仓库。技术上深入理解了 DB RAG、LangGraph 工作流编排、多路召回融合、SQL 校验校正。工程上锻炼了分层架构设计、异步编程、多系统协作的能力。

## STAR 法则回答模板

**问题：请介绍一个你解决过的技术难题**

**S（Situation）**：
"在做掌柜问数时，LLM 生成的 SQL 经常有表名错误和 JOIN 条件缺失的问题。"

**T（Task）**：
"我需要设计一个机制，在 SQL 执行前就能发现并修复这些错误。"

**A（Action）**：
"我设计了 SQL 校验校正闭环：
1. 用 MySQL 的 EXPLAIN 检查 SQL 语法，不执行就能发现表不存在、字段名错误等问题
2. 校验失败时，将错误信息和上下文一起交给 LLM，让它重新生成 SQL
3. 通过条件边实现 validate → correct → validate 的循环，最多校正一次"

**R（Result）**：
"SQL 生成的首次通过率从 60% 提升到 85%，加上校正后最终成功率达到 95%。"
