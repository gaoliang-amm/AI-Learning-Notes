# 06. 企业面试真题

> 本文件整理自项目教案、笔记及 **1020 企业面试真题.xlsx**（20+ 家公司真实面试题），按类别归类，每个问题附带标准回答。

---

## 一、RAG 基础概念

### Q1：什么是 RAG？为什么需要 RAG？

**→ 回答**：
RAG（Retrieval-Augmented Generation，检索增强生成）是"先检索、后生成"的架构。用户提问后，先从知识库检索相关文档，再将检索结果作为上下文交给 LLM 生成答案。

需要 RAG 的原因：① LLM 预训练知识有截止日期，无法覆盖最新信息；② LLM 对企业私有数据一无所知；③ LLM 直接回答容易产生事实幻觉。RAG 从根源上让模型基于真实文档生成答案，降低幻觉、提升准确性。

---

### Q2：RAG 的核心流程是什么？

**→ 回答**：
分为两个阶段：
1. **离线数据准备**：原始文档 → 文本切分 → 向量化（Embedding）→ 存入向量数据库
2. **在线问答生成**：用户提问 → 向量化 → 相似度检索 → 召回相关 chunk → 拼接 Prompt → LLM 生成答案

---

### Q3：什么是向量？什么是词向量？

**→ 回答**：
向量就是把文字转换成计算机能理解的数字列表（高维数组）。例如"苹果手机"→ `[0.23, -0.56, 1.89, ...]`。

通过向量可以计算文本之间的相似度——两个向量距离越近，语义越相似。比如"苹果手机"和"华为手机"的向量距离比"苹果手机"和"苹果笔记本"更近。

---

### Q4：稠密向量和稀疏向量有什么区别？

**→ 回答**：

| 维度 | 稠密向量（Dense） | 稀疏向量（Sparse） |
|------|-------------------|-------------------|
| 维度 | 固定（如 1024 维） | 极长（几十万维），多数为 0 |
| 特点 | 每个位置都是连续数值 | 只有少数位置有非零值 |
| 用途 | 捕捉语义信息 | 捕捉关键词/字面特征 |
| 比较方式 | 余弦相似度/IP | 内积（IP） |

BGE-M3 同时输出两种向量，混合使用能兼顾"语义理解"和"精准匹配"。

## 二、文档处理与切分

### Q5：你们公司 RAG 里总共有多少文档？业务量有多大？

**→ 回答**：
当前测试环境：10+ 份产品手册（PDF/MD），数百个 chunk。生产环境预期：数百份文档，数千到数万 chunk。Milvus 单机版可支撑百万级向量检索。

> 面试官追问意图：判断系统是否经过真实业务验证，以及你对系统规模的理解。

---

### Q5b（新增）：为什么不用 Elasticsearch 做向量检索而用 Milvus？

**→ 回答**：
ES 从 8.0 版本开始支持向量检索（kNN），但 ES 的向量检索是基于 Lucene 的 HNSW 实现，不如 Milvus 专业：① Milvus 专为向量检索设计，支持混合检索（dense+sparse），ES 的稀疏向量支持较弱；② Milvus 的索引类型更丰富（HNSW/IVF/FLAT），ES 主要是 HNSW；③ Milvus 支持标量过滤+向量检索的联合查询，性能更优；④ ES 更适合全文检索+向量检索的混合场景，纯向量检索 Milvus 更专业。

### Q5b：你的 RAG 是做图文混合检索的么？

**→ 回答**：
是的。导入阶段会扫描 Markdown 中的图片，用视觉模型（Qwen3-VL-Flash）识别图片内容，生成文字描述，替换原始图片引用为 `![描述](MinIO网络地址)`。这样图片内容参与了文本向量化和检索，实现了图文混合检索。同时图片的网络地址会传递给前端用于展示。

---

### Q6：你的切块是多长？为什么？

**→ 回答**：
基准 600 字符，最大 1000，最小 400（低于 400 会合并）。选择 600 的原因：
1. 通过项目评估系统反复调试，600 时召回率和准确率最高
2. 考虑 embedding 模型上下文（BGE-M3 8192 token），600 字约 780 token，占比 <10%
3. 考虑 reranker 模型限制（512 token），问题+答案不能超限
4. 行业经验 500-1200 token 之间效果最好

---

### Q7：切块的原则是什么？

**→ 回答**：
四个核心原则：
1. **语义优先**：按标题层级做粗切，保留语义边界，不机械切分
2. **长度可控**：基准 600，上限 1000，考虑模型上下文限制
3. **边界清晰**：有合理的 overlap（50 字符），防止语义断裂
4. **可追溯**：每个 chunk 携带 title、parent_title、part、file_title、item_name 等元数据

---

### Q8：什么是 item_name？为什么需要识别它？

**→ 回答**：
item_name 是文档描述的核心主体名称（如"HAK180 烫金机"）。一个文件对应一个 item_name，一个 item_name 可对应多个文件。

需要识别的原因：① 用户提问常省略主体（如"这个怎么调"），需要先锁定主体才能精准检索；② 通过 item_name 可以缩小检索范围，先圈定目标文档，再在文档内匹配切片，提升检索效率和精度。

---

## 三、向量模型与检索

### Q9：BGE-M3 模型有什么特点？

**→ 回答**：
BGE-M3 是 BAAI 发布的多语言嵌入模型，核心特点：
1. **多功能**：单一模型同时输出稠密向量 + 稀疏向量
2. **多语言**：支持 130+ 种语言
3. **多粒度**：支持最长 8192 token 输入
4. **维度**：稠密向量 1024 维
5. **归一化**：支持原生 L2 归一化，适配 Milvus IP 检索

---

### Q10：Milvus 的单列搜索和混合检索有什么区别？

**→ 回答**：
- **单列搜索**：只用一个向量字段搜索（如只用 dense_vector），返回该字段的相似度结果
- **混合检索**：同时用多个向量字段搜索（如 dense_vector + sparse_vector），通过 Reranker 策略融合结果

混合检索的两种模式：① 多模态搜索（一行数据的多个字段）；② 稠密+稀疏向量（同一字段生成两种向量）。

混合检索语法：创建 AnnSearchRequest（每路一个）→ 配置 Reranker（WeightedRanker 或 RrfReranker）→ hybrid_search 执行。

---

### Q11：Milvus 混合检索中的 WeightedRanker 和 RrfRerank 有什么区别？

**→ 回答**：
- **WeightedRanker**：按权重融合分数。例如 dense 分 0.9 权重 0.5 + sparse 分 0.8 权重 0.5 = 0.85。可控，推荐使用。
- **RrfReranker**：按排名融合。公式 `1/(k+rank)`，公平但不可控，不推荐。

---

### Q12：什么是 HyDE？为什么需要它？

**→ 回答**：
HyDE（Hypothetical Document Embeddings，假设文档向量检索）的核心思路：**先让 LLM 写一段"可能的标准答案"，再拿这段答案去辅助检索真实文档。**

需要的原因：用户问句通常很短（如"这个怎么调"），语义信息不足，直接向量检索命中率低。HyDE 先补出一段更完整的答案描述，检索输入更接近真实文档的表达方式，显著提升弱语义查询的召回率。

注意：HyDE 生成的是假设性答案，不作为最终输出，只用于检索增强。

---

### Q13：什么是 RRF？算法原理是什么？

**→ 回答**：
RRF（Reciprocal Rank Fusion，倒数排名融合）是一种基于排名的融合算法，用于合并多路检索结果。

公式：`score = Σ(weight × 1/(k + rank))`
- k=60（标准常数）
- rank 是该文档在某一路中的排名
- weight 是该路的权重

核心特点：不依赖原始分数，只看排名，天然消除不同检索路径的分数差异。同时在多路中排名靠前的文档会获得更高分数。

---

### Q14：为什么需要 Rerank？和 RRF 有什么区别？

**→ 回答**：
- **RRF**：融合同源结果（如向量检索 + HyDE），基于排名，不看内容
- **Rerank**：用专门的重排序模型（BGE-reranker）对问题-文档对打分，基于语义相关性

RRF 之后还需要 Rerank 的原因：① RRF 只处理了本地两路结果，网络搜索结果没参与；② RRF 基于排名，不看内容相关性；③ Reranker 模型能做更细粒度的语义判断。

---

### Q15：动态 TopK 怎么实现的？

**→ 回答**：
不固定取 Top N，而是检测相邻分数的分差，出现断崖时截断：
- 绝对分差 > 0.2 → 截断
- 相对分差 > 20% → 截断
- 范围限制：min_topk=2 到 max_topk=6

比固定 TopK 更智能：分数骤降说明后续内容相关性大幅下降，此时截断能兼顾召回率和准确率。

## 四、模型与工程

### Q16：怎么确保大语言模型返回的数据是 JSON 格式？

**→ 回答**：
四层保障：
1. **提示词约束**：强调返回数据格式，提供返回数据示例
2. **模型 JSON 模式**：设置 `json_mode=True`
3. **解析器**：使用 LangChain 的 `JsonOutputParser` 解析 ` ```json ``` ` 块
4. **返回值校验**：检查 key 是否存在，缺失则赋默认值（如 item_names→[]，rewritten_query→original_query）

---

### Q17：重排序模型的上下文可能短于 content 内容，你是如何处理的？

**→ 回答**：
BGE-reranker-large 上下文 512 token（514-2 special tokens）。处理方式：
1. 计算问题的 token 数
2. 循环每个答案，计算问题+答案的总 token 数
3. 如果 `question_token + answer_token + 4 > 512`，用 LLM 压缩答案
4. 压缩公式：`limit = max(50, int((512 - 4 - question_token) / 1.3))`
5. 压缩后的答案只用于打分，原始答案用于最终生成

---

### Q18：什么是 MCP？有什么作用？

**→ 回答**：
MCP（Model Context Protocol，模型上下文协议）是一种标准协议，让服务端和客户端共享 tools（工具）、resources（资源）、prompt（提示词）。

作用：提升 Agent 的能力边界。通过 MCP，Agent 可以调用外部服务提供的工具（如联网搜索、数据库查询），而不需要自己实现这些能力。

本项目中使用 MCP 调用百炼平台的联网搜索工具，补充本地知识库未覆盖的内容。

---

### Q19：MCP 和 Skill 有什么异同？

**→ 回答**：
- **相同点**：都是提升 Agent 能力的机制
- **不同点**：
  - MCP 通过网络调用获得服务端提供的工具代码
  - Skill 是本地文件加载（提示词+代码）
  - MCP 有标准协议（stdio/sse/streamable_http），Skill 是自定义格式

---

### Q20：MCP 有哪些使用协议？

**→ 回答**：
三种协议：
1. **stdio**：本地进程通信，同一台电脑上的 server 和 client，少见
2. **SSE**：网络协议，通过 URL 访问服务端
3. **Streamable HTTP**：SSE 的升级版，网络连接更轻、性能更好

本项目使用 Streamable HTTP 协议调用百炼联网搜索。

---

### Q21：SSE 和 WebSocket 有什么区别？

**→ 回答**：
- **SSE**：单向通信（服务端→客户端），基于 HTTP，简单轻量，原生支持断线重连
- **WebSocket**：双向通信（服务端↔客户端），需要独立连接，更复杂

本项目选择 SSE 的原因：查询场景只需要服务端推送答案（progress/delta/final 事件），不需要客户端发送数据，SSE 更简单高效。

---

### Q22：为什么用 LangGraph 不用原生 Agent？

**→ 回答**：
企业场景对流程可控性、稳定性、可追溯性、可审计性要求极高。原生 Agent 的问题：① 决策不可控，可能偏离任务；② 执行路径不可预测；③ 难以审计和调试。

LangGraph 通过显式图结构（节点+边+条件路由）保证所有逻辑在预设流程内执行，同时支持条件路由、并发执行、状态持久化，兼顾灵活性和稳定性。

### Q23：你们项目用了哪些模型？

### Q24：MinIO 在项目中做什么用？

**→ 回答**：
MinIO 是对象存储服务，用于存储文档中的图片文件。导入阶段会将图片上传到 MinIO，获取网络访问地址，替换 Markdown 中的本地图片引用为网络地址。这样前端在任何位置都能访问和展示图片。

---

### Q25：MongoDB 在项目中做什么用？

**→ 回答**：
MongoDB 存储历史对话记录。每条记录包含：session_id、role（user/assistant）、text、rewritten_query、item_names、image_urls、timestamp。

用途：① 查询阶段获取历史对话作为上下文，辅助意图识别和问题改写；② 前端展示历史对话；③ 支持清空历史记录。

---

### Q26：Milvus 的索引类型有哪些？你们用了什么？

**→ 回答**：
- **FLAT**：暴力搜索，准确但慢
- **IVF_FLAT**：分桶搜索，先确定类别再细化
- **HNSW**：多层图导航，效率和准确率最高，但占空间最大

本项目使用：
- 稠密向量：HNSW（M=64, efConstruction=100），metric_type=COSINE
- 稀疏向量：SPARSE_INVERTED_INDEX，metric_type=IP，算法=DAAT_MAXSCORE

## 七、RAG 企业高频追问（来自企业面试真题）

### Q31：RAG 中实际遇到过什么问题？怎么解决的？

**→ 回答**：
主要问题：① 弱语义查询（"这个怎么调"）召回率低 → 加 HyDE 增强；② chunk 脱离全文后语义残缺 → item_name 补全+标题路径保留；③ 固定 TopK 导致噪声 → 动态断崖截断；④ 并发节点 state 冲突 → 每个节点只返回自己修改的 key；⑤ 流式输出任务状态缓存 → 每次请求前 clear_task。

---

### Q32：产品识别节点的相似度阈值是怎么确定的？

**→ 回答**：
通过评估系统反复调试：① 用标注数据集测试不同阈值下的 item_name_hit_rate；② ≥0.70 确认（高置信度），0.60-0.70 可选（反问用户），<0.60 不确认；③ 阈值过高会漏确认，过低会误确认，0.70 是准确率和召回率的平衡点。

---

### Q33：多路召回后是怎么排序的？RRF 的参数具体是什么？

**→ 回答**：
两步排序：① RRF 融合同源两路（向量+HyDE），参数 k=60，权重各 0.5，取 Top 5；② Rerank 统一排序 RRF 结果+网络搜索结果，BGE-reranker 打分，动态断崖截断（min=2, max=6, gap_abs=0.2, gap_ratio=0.2）。

---

### Q34：RAG 召回的 chunk 不全，该如何解决？

**→ 回答**：
从三个层面优化：① **召回层**：增加召回路数（向量+HyDE+联网），HyDE 增强弱语义查询；② **融合层**：RRF 融合多路结果，扩大候选集；③ **切分层**：合理设置 chunk 大小（600）和 overlap（50），避免语义断裂导致信息丢失。如果信息分布在多个 chunk 中，overlap 机制能保证相邻 chunk 包含部分内容。

---

### Q35：如果不同文档对同一事实描述不一致，怎么判断哪个可信？

**→ 回答**：
当前系统通过 Rerank 打分自然筛选——相关性更高的文档排在前面，LLM 基于精排后的上下文生成答案。如果需要更严格的知识冲突处理：① 引入时间戳排序（新版覆盖旧版）；② 引入文档权威性权重（官方手册 > 用户笔记）；③ 在 Prompt 中明确告知模型"如果多个来源矛盾，以最新的为准"。

---

### Q36：RAG、Graph RAG 和多模态 RAG 有什么区别？

**→ 回答**：

| 类型 | 特点 | 适用场景 |
|------|------|---------|
| **RAG** | 文档切分→向量检索→LLM 生成 | 通用文档问答 |
| **Graph RAG** | 构建知识图谱→图检索→LLM 生成 | 需要关系推理的场景（如多跳问答） |
| **多模态 RAG** | 图片/表格/音频也参与检索 | 图文混排、跨模态检索 |

本项目属于**多模态 RAG**（图片通过视觉模型生成文字描述后参与检索），同时具备传统 RAG 的核心能力。

---

### Q37：prompt 如果比较大，会不会有幻觉？

**→ 回答**：
会。上下文过长时：① LLM 注意力分散，中间信息容易被忽略（Lost in the Middle 现象）；② token 增多导致推理成本上升；③ 无关信息干扰生成质量。优化方式：① Rerank 精排后只取 Top 2-6 个最相关 chunk；② Prompt 中按相关性排序，重要信息放前面；③ 控制上下文总量（reranker 已做了压缩限制）。

---

### Q38：召回的 chunk 超过 reranker 的上下文窗口怎么做？

**→ 回答**：
BGE-reranker-large 上下文 512 token。处理：① 计算每个候选的 question+answer token 数；② 超过 512-4 token 的，用 LLM 压缩答案（limit = max(50, int((512-4-question_len)/1.3))）；③ 压缩后的文本只用于打分，原始文本用于最终生成答案。

| 组件 | 引入原因 |

## 八、Agent 与 LangGraph（企业真题）

### Q40：Agent 的范式是什么？有哪些类型？

**→ 回答**：
Agent 范式是"感知→决策→行动→观察"的循环。主要类型：
- **ReAct**：Thought → Action → Observation 循环，最经典
- **Plan-and-Execute**：先规划再执行
- **Multi-Agent**：多个 Agent 协作完成任务
- **Workflow Agent**：预定义流程，确定性执行（如 LangGraph）

本项目属于 **Workflow Agent**——用 LangGraph 编排确定性流程，不是自主决策的 Agent。

---

### Q41：Agent 的长短期记忆怎么设计？

**→ 回答**：
- **短期记忆**：当前会话的对话历史，存在 MongoDB 中，按 session_id 查询，限制最近 10 条。用于意图识别和问题改写时提供上下文。
- **长期记忆**：用户画像、历史偏好，本项目暂未实现。可扩展方向：用向量数据库存储用户历史偏好，定期总结归纳。

---

### Q42：LangGraph 中的 thread_id 是干什么的？

**→ 回答**：
thread_id 是 LangGraph 状态持久化的会话标识。每个 thread_id 对应一个独立的状态快照，支持：① 多轮对话的状态延续；② 断点恢复；③ 状态回溯。本项目中用 session_id 作为 thread_id。

---

### Q43：LangGraph 和 LangChain 有什么区别？

**→ 回答**：
- **LangChain**：提供链式调用（LCEL），适合线性流程，如"检索→拼接→生成"
- **LangGraph**：提供图结构编排，支持条件路由、循环、并发、状态管理，适合复杂 AI 工作流

LangGraph 是 LangChain 的子项目，专注于 Agent 和工作流编排。

---

### Q44：如何保证大模型按照预设流程执行？

**→ 回答**：
① LangGraph 显式定义节点和边，大模型只在特定节点被调用（如意图识别、答案生成），不会自主决定流程走向；② 条件路由基于确定性规则（如 state.get("is_md_read_enabled")），不依赖 LLM 判断；③ 大模型的输出经过解析器（JsonOutputParser/StrOutputParser）约束格式。

---

### Q45：Function Calling 失败了会有哪些情形和原因？

**→ 回答**：
- **模型不支持**：基础模型不支持 function calling → 换模型
- **参数格式错误**：模型生成的 JSON 不合法 → JSONOutputParser + 重试
- **工具不存在**：调用了不存在的工具名 → 工具注册校验
- **超时**：工具执行时间过长 → 设置 timeout + 异步处理
- **返回异常**：工具返回错误 → 异常捕获 + 降级策略

## 九、Transformer 基础（企业真题）

### Q46：Transformer 的架构是什么？QKV 分别代表什么？

**→ 回答**：
Transformer 由 Encoder 和 Decoder 组成（原始论文）。Self-Attention 中：
- **Q（Query）**：当前词想要查询什么信息
- **K（Key）**：每个词能提供什么信息的索引
- **V（Value）**：每个词的实际内容

计算公式：`Attention(Q,K,V) = softmax(QK^T / √d_k) × V`

---

### Q47：多头注意力、GQA、MQA 有什么区别？

**→ 回答**：
- **MHA（Multi-Head Attention）**：每个头有独立的 Q/K/V，参数量大，表达能力强
- **MQA（Multi-Query Attention）**：所有头共享 K/V，只有 Q 不同，参数量小，速度快
- **GQA（Grouped-Query Attention）**：MHA 和 MQA 的折中，将头分组，组内共享 K/V

GQA 是当前主流选择（如 Llama 2/3），在性能和效率间取得平衡。

---

### Q48：Decoder-Only 架构的好处是什么？

**→ 回答**：
GPT 系列使用 Decoder-Only，好处：① 架构更简单，只用 Causal Self-Attention（掩码注意力）；② 自回归生成天然适合语言建模；③ 参数量更集中，训练效率更高；④ 统一了理解和生成能力（通过 prompt 即可完成多种任务）。

---

### Q49：什么是注意力的 Lost in the Middle 现象？

**→ 回答**：
LLM 对输入的头部和尾部注意力较高，中间部分信息容易被忽略。应对方式：① 将最重要的信息放在 Prompt 的开头或结尾；② 控制上下文长度，避免过长；③ Rerank 后只保留最相关的 chunk，减少无关信息干扰。

---

## 十、模型部署与工程（企业真题）

### Q50：模型部署用什么方案？vLLM 了解吗？

**→ 回答**：
本项目使用 API 调用方式（通义千问 API），未做本地部署。但了解 vLLM 的核心能力：① PagedAttention（分页注意力），高效管理 KV Cache；② Continuous Batching（连续批处理），动态合并请求；③ 支持多种量化方式（AWQ/GPTQ/FP8）。vLLM 适合需要高并发推理的私有化部署场景。

### Q51：如何判断是否进入局部最优？

**→ 回答**：
训练中判断局部最优的信号：① Loss 下降停滞但未收敛；② 验证集 loss 不再下降但训练集 loss 继续下降（过拟合）；③ 模型输出开始重复。解决方式：① 调整学习率（warmup + cosine decay）；② 增加数据多样性；③ 使用早停（early stopping）；④ 尝试不同的初始化。

## 十一、Python 工程进阶（企业真题）

### Q52：BaseModel 和 TypedDict 有什么区别？

**→ 回答**：
- **BaseModel**（Pydantic）：运行时数据校验、序列化/反序列化、JSON Schema 生成。适合 API 请求/响应定义。
- **TypedDict**：静态类型检查，不参与运行时校验。适合内部数据结构定义，开销更小。

本项目中：LangGraph 的 State 用 TypedDict（轻量）；FastAPI 的请求/响应用 BaseModel（需要校验）。

---

### Q53：Python 异步怎么用？async/await 是什么？

**→ 回答**：
`async` 声明异步函数，`await` 暂停当前协程等待异步操作完成，不阻塞主线程。

```python
import asyncio

async def fetch_data():
    await asyncio.sleep(1)  # 异步等待，不阻塞
    return "data"

async def main():
    result = await fetch_data()
```

适用场景：IO 密集型任务（网络请求、文件读写）。本项目中 FastAPI + BackgroundTasks 实现异步任务执行。

---

### Q54：多用户并发怎么处理？

**→ 回答**：
① FastAPI 原生支持异步并发（基于 uvloop）；② 每个请求用独立的 session_id/task_id 隔离状态；③ LangGraph 的 state 是深拷贝的，不会跨请求共享；④ Queue 也是按 session_id 隔离的。高并发场景可引入线程池或进程池。

## 十二、大模型微调（企业真题高频）

### Q55：什么时候需要微调？什么时候只用 prompt 就行？

**→ 回答**：
- **只用 prompt**：任务通用、模型能力足够、数据量小、快速验证
- **需要微调（SFT）**：任务垂直（如 NL2SQL）、模型输出格式不稳定、需要领域专业知识、prompt 无法覆盖所有 case
- **需要 RLHF（DPO/PPO）**：需要对齐人类偏好（如回答风格、安全性）、减少有害输出

---

### Q56：SFT 和 DPO 有什么区别？

**→ 回答**：
- **SFT（Supervised Fine-Tuning）**：用"问题-标准答案"对训练，教模型"怎么答"。是微调的第一步。
- **DPO（Direct Preference Optimization）**：用"问题-好答案-差答案"三元组训练，教模型"什么是好的"。是 SFT 之后的对齐步骤。

关系：SFT 先让模型学会任务，DPO 再让模型回答得更好。

---

### Q57：PPO、DPO、GRPO、KTO 分别适合什么场景？

**→ 回答**：

| 算法 | 原理 | 优点 | 缺点 | 适用场景 |
|------|------|------|------|---------|
| **PPO** | 策略梯度+裁剪+奖励模型 | 效果最好，灵活 | 需要训练奖励模型，复杂 | 大规模对齐，追求极致效果 |
| **DPO** | 直接用偏好数据优化，无需奖励模型 | 简单，效果好 | 依赖高质量偏好数据 | 中小规模对齐 |
| **GRPO** | 组内相对排名优化 | 不需要奖励模型，DeepSeek 验证有效 | 需要组内样本 | 开源模型对齐 |
| **KTO** | 只需要"好/坏"二元标签 | 数据门槛最低（不需要成对数据） | 效果不如 DPO | 偏好数据不完整时 |

---

### Q58：LoRA 微调是什么？有哪些参数？

**→ 回答**：
LoRA（Low-Rank Adaptation）在冻结原始权重的基础上，插入低秩矩阵（A×B）只训练增量参数。

关键参数：
- **r**：秩（rank），控制增量矩阵的维度，r 越大表达能力越强但参数越多（常见 8/16/32/64）
- **target_modules**：对哪些层做 LoRA（如 q_proj, v_proj, k_proj）
- **lora_alpha**：缩放因子，通常 = 2×r
- **lora_dropout**：Dropout 比例，防止过拟合

---

### Q59：训练数据集怎么准备？比例怎么定？

**→ 回答**：
- **数据格式**：SFT 用 `{instruction, input, output}` 三元组；DPO 用 `{instruction, chosen, rejected}` 三元组
- **数据来源**：人工标注 + 开源数据集 + 模型生成（GPT-4 生成种子数据，人工审核）
- **比例**：训练集:验证集:测试集 = 8:1:1 或 9:0.5:0.5
- **数据量**：SFT 通常 1000-10000 条；DPO 通常 5000-50000 条
- **质量 > 数量**：清洗重复、低质量、矛盾数据

---

### Q60：怎么判断训练是否过拟合？什么时候停掉？

**→ 回答**：
- **过拟合信号**：训练 loss 持续下降，但验证 loss 开始上升
- **欠拟合信号**：训练 loss 和验证 loss 都不下降
- **停掉时机**：验证 loss 连续 N 个 epoch 不下降（early stopping）
- **训练不收敛**：loss 震荡或突然飙升 → 降低学习率、检查数据质量、检查标签

---

### Q61：AdamW 优化器的原理？

**→ 回答**：
AdamW = Adam + Weight Decay 解耦：
- **Adam**：结合动量（一阶矩）和自适应学习率（二阶矩），加速收敛
- **Weight Decay**：权重衰减，防止参数过大导致过拟合
- **关键参数**：learning_rate（学习率）、beta1/beta2（矩估计指数衰减率，默认 0.9/0.999）、weight_decay（权重衰减）

---

### Q62：DeepSpeed-Zero 是什么？

**→ 回答**：
DeepSpeed ZeRO（Zero Redundancy Optimizer）是分布式训练的内存优化技术，分三个阶段：
- **Stage 1**：分片优化器状态（每个 GPU 只存 1/N 的优化器状态）
- **Stage 2**：分片优化器状态 + 梯度
- **Stage 3**：分片优化器状态 + 梯度 + 模型参数

选择：数据量大用 Stage 1/2，GPU 显存不足用 Stage 2/3。

---

## 十三、Transformer 深入（企业真题）

### Q63：Transformer 相比 RNN/LSTM 有什么改进？

**→ 回答**：
1. **并行计算**：RNN 必须顺序处理，Transformer 可以并行处理所有 token
2. **长距离依赖**：Self-Attention 直接建模任意两个 token 的关系，不受序列长度限制
3. **位置编码**：通过位置编码注入序列顺序信息（正弦编码/RoPE/ALiBi）

---

### Q64：前向传播和反向传播分别是什么？

**→ 回答**：
- **前向传播**：输入 → 逐层计算 → 输出预测值。`y = f(x, W)`
- **反向传播**：计算损失 → 从输出层向输入层反向计算梯度 → 更新权重。基于链式法则：`∂L/∂W = ∂L/∂y × ∂y/∂W`

---

### Q65：位置编码有哪几种？RoPE 是什么？

**→ 回答**：
- **正弦位置编码**（原始 Transformer）：用正弦/余弦函数生成位置向量
- **可学习位置编码**：训练时学习位置向量
- **RoPE（旋转位置编码）**：通过旋转矩阵编码相对位置，LLaMA/Qwen 使用
- **ALiBi**：在 Attention 分数中直接加位置偏置

RoPE 优势：支持外推到更长序列，且编码了相对位置关系。

---

## 十四、Agent 进阶（企业真题）

### Q66：ReAct 范式是什么？

**→ 回答**：
ReAct = Reasoning + Acting，核心循环：
```
Thought: 分析当前情况，决定下一步
Action: 选择并执行工具
Observation: 获取工具返回结果
→ 循环直到完成
```
优点：推理过程可解释，每一步都有明确的思考和行动。缺点：多轮循环延迟高。

---

### Q67：单 Agent 和多 Agent 怎么选？

**→ 回答**：

| 维度 | 单 Agent | 多 Agent |
|------|---------|---------|
| 任务复杂度 | 简单/中等 | 复杂/多步骤 |
| 工具数量 | <50 个 | >50 个，按职责拆分 |
| 上下文 | 能装下 | 超限，需要拆分 |
| 准确性要求 | 一般 | 高（子 Agent 专精） |

本项目用单 Agent + LangGraph 工作流编排，因为任务流程确定，不需要自主决策。

---

### Q68：Agent 的工具调用失败了怎么办？

**→ 回答**：
降级策略：① 重试（max_retry_attempts=3）；② 换备选工具；③ 返回默认值/错误提示；④ 在 Prompt 中告知模型"工具调用失败，请用已有知识回答"。

---

## 十五、Prompt 工程（企业真题）

### Q69：静态提示和动态提示为什么要分别放在顶部和底部？

**→ 回答**：
LLM 对输入的头部和尾部注意力较高（Primacy/Recency 效应）。静态提示（系统指令、角色定义）放顶部确保被优先关注；动态提示（用户问题、检索结果）放尾部确保最新信息被关注。中间放参考文档等辅助信息。

---

### Q70：Top P、Top K、Temperature 分别有什么差别？

**→ 回答**：
- **Temperature**：控制随机性，0=确定性最高，1=随机性高。生成答案用低温度（0.1-0.3），创意生成用高温度
- **Top K**：只从概率最高的 K 个 token 中采样。K=1 是贪心解码
- **Top P（Nucleus Sampling）**：从累积概率达到 P 的最小 token 集合中采样。P=0.9 意味着排除概率最低的 10%

三者可以组合使用，通常 Temperature + Top P 效果最好。

---

### Q71：大模型上下文长度过长有什么影响？

**→ 回答**：
1. **Lost in the Middle**：中间信息被忽略
2. **推理成本**：Attention 复杂度 O(n²)，长度翻倍成本四倍
3. **KV Cache 内存**：每个 token 都要缓存 Key/Value，长上下文内存占用大
4. **幻觉增加**：无关信息干扰，模型容易"编造"

---

## 十六、模型评估（企业真题）

### Q72：怎么评估 RAG 系统的效果？

**→ 回答**：
四层分层评估：
- **embedding_chunks**：基础召回的质量
- **hyde_embedding_chunks**：HyDE 增强后的质量
- **rrf_chunks**：融合后的质量
- **reranked_docs**：精排后的质量

每层计算 precision（准不准）、recall（全不全）、must_hit_rate（关键 chunk 命中率）。通过四层对比定位"哪一层拖了后腿"。

---

### Q73：怎么区分事实冲突、上下文冲突、检索失败等不同错误来源？

**→ 回答**：
- **检索失败**：评估 recall 指标，如果 recall 低说明该召回的内容没召回到 → 优化检索策略
- **上下文冲突**：检索到了但信息矛盾 → Rerank 排序问题，或知识库本身有冲突
- **事实冲突**：LLM 生成的内容与检索到的内容矛盾 → 幻觉问题，优化 Prompt 或换模型
- **输入冲突**：用户问题本身模糊 → 优化意图识别和问题改写

### Q74：RAG 的召回率和准确率能达到多少？

**→ 回答**：
取决于数据质量和检索策略。参考范围：
- 基础向量检索：recall 60-70%，precision 50-60%
- 加 HyDE + Rerank：recall 75-85%，precision 70-80%
- 关键 chunk 命中率（must_hit_rate）：目标 >80%

具体数值需要通过评估系统实测。
