# 智能商品发布 — 面试表达模板

---

## 30 秒版

基于 BERT 预训练模型做电商商品标题分类。输入一条标题，输出所属类目。工程上做了几件事：动态 Padding 省 40-60% 计算，AMP 混合精度显存减半加速，Checkpoint 保存完整训练状态实现断点续训，Early Stopping 防过拟合。最终部署为 FastAPI HTTP 服务。

---

## 2 分钟版

**背景**：电商平台有大量商品需要自动分类，人工标注成本高。我用 BERT 做了微调分类系统。

**技术方案**：数据层用 HuggingFace datasets 处理，原始 TSV 经过 load_dataset、cast_column 固定标签映射、tokenize 后以 Arrow 格式存储。训练时 DataLoader 用 DataCollatorWithPadding 做动态 Padding，比静态 Padding 省 40-60% 计算。

**训练**：模型是 bert-base-chinese，Adam lr=5e-5。用了 AMP 混合精度加速，每 20 步评估一次验证集，Early Stopping patience=3 防过拟合。Checkpoint 保存 model+optimizer+step+scaler，支持断点续训。

**部署**：FastAPI + Pydantic 校验，模型启动时全局加载一次，支持单条和批量预测。

**亮点**：标签固定映射保证训练/推理 id 一致，动态 Padding 高效利用 GPU，Checkpoint 完整状态保存实现续训。

## 5 分钟版

### 背景（1 分钟）

电商平台商品类目繁多，人工标注成本高且效率低。我负责了一个基于 BERT 微调的商品标题自动分类系统，目标是给定商品标题，自动预测所属类目（如"酒水饮料"、"个护"等）。

技术选型上，我选了 bert-base-chinese 作为预训练模型，因为它在中文文本理解上已经很好，微调就能达到不错的效果。框架用 PyTorch + HuggingFace transformers。

### 架构（1 分钟）

系统分为六层：
- **CLI 入口层**：main.py 用 argparse 做统一路由
- **配置层**：config.py 用 pathlib 从文件位置反推根目录，所有路径零配置
- **数据层**：离线预处理 + Arrow 格式存储，训练时直接加载
- **模型层**：BertForSequenceClassification（BERT Encoder + [CLS] → Linear → CE）
- **执行层**：Trainer 封装训练循环、AMP、早停、Checkpoint
- **服务层**：FastAPI + Pydantic

### 核心模块（1.5 分钟）

**数据预处理**：原始 TSV → load_dataset → cast_column 固定标签映射 → tokenize（不 padding） → Arrow 存储。关键决策是用 `cast_column` 而非 `class_encode_column`，因为后者顺序不确定，会导致训练/推理 id 不一致。

**DataLoader**：DataCollatorWithPadding 做动态 Padding，每个 batch 只 pad 到该 batch 最长序列。电商标题平均长度远小于 512，所以能省 40-60% 计算。

**Trainer**：dataclass 管理超参数，训练循环包含 AMP 混合精度（autocast fp16 + GradScaler 防下溢）、每 save_step 步评估验证集、Early Stopping 基于 score 统一化（loss 取负，metric 直接比较）、Checkpoint 保存完整状态（model+optimizer+step+count+score+scaler）。

### 工程亮点（0.5 分钟）

1. **标签固定映射**：sorted(set(labels)) + cast_column，保证每次运行 id 一致
2. **动态 Padding**：比静态 Padding 省 40-60% 计算
3. **AMP 混合精度**：显存减半，速度提升 ~1.5-2x
4. **Checkpoint 完整状态**：断点续训，不丢失任何训练状态
5. **配置管理**：pathlib 反推根目录，任意机器 clone 即用

### 收获（0.5 分钟）

这个项目让我深入理解了 BERT 微调的工程细节。最大的收获是：模型效果不仅取决于算法设计，更取决于工程实现的正确性。比如标签 id 不一致这种问题，模型 accuracy 看起来很高但推理结果全是错的。还有 AMP 的 GradScaler，不理解原理就加 AMP 很容易训练崩溃。

## STAR 法则版

### 问题 1：标签一致性问题

**S（情境）**：训练时模型 accuracy 达到 98%，但上线推理结果明显错误，很多标题被分到错误类目。

**T（任务）**：排查并修复标签映射不一致的问题。

**A（行动）**：
1. 打印训练时的 label id 和推理时的 id2label，发现顺序不同
2. 分析原因：`class_encode_column` 的标签顺序取决于数据遍历顺序，每次运行可能不同
3. 修复方案：用 `sorted(set(labels))` 排序后 `cast_column`，保证固定顺序
4. 同时将标签顺序写入 `labels.txt`，推理时从文件读取

**R（结果）**：训练/推理 id 一致，推理结果正确，accuracy 从"假 98%"变为真实的 96%。

---

### 问题 2：断点续训问题

**S（情境）**：训练过程中 GPU 被抢占或断电，之前训练的进度全部丢失，需要从头训练。

**T（任务）**：实现断点续训，从上次中断处继续训练。

**A（行动）**：
1. 设计 Checkpoint 保存 6 个状态：model、optimizer、step、early_stop_count、best_score、scaler
2. 续训时 `_load_checkpoint()` 恢复所有状态
3. DataLoader shuffle seed 固定为 42，续训时遍历 dataloader 但跳过已训练步数

**R（结果）**：GPU 被抢占后自动从上次 checkpoint 恢复，续训效果与连续训练一致。

---

### 问题 3：训练崩溃（AMP）

**S（情境）**：开启 AMP 混合精度训练后，loss 突然变成 NaN，训练崩溃。

**T（任务）**：排查原因并修复。

**A（行动）**：
1. 分析原因：fp16 数值范围有限，梯度容易下溢
2. 引入 GradScaler：放大 loss 使梯度数值更大，更新参数前再缩回来
3. 实现动态 scale：检测到 inf/nan 时跳过此步并降低 scale_factor
4. Checkpoint 中保存 scaler 状态，断点续训时恢复

**R（结果）**：AMP 稳定运行，显存减半，训练速度提升 ~1.5-2x。
