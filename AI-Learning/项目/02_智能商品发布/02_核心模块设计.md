# 智能商品发布 — 核心模块设计

> 每个模块按统一模板分析：**作用 → 为什么这样设计 → 替代方案对比 → 面试追问 → 核心代码**

---

## 1. 配置管理 — config.py

### 作用
统一管理项目所有路径和超参数，是唯一的配置源。

### 为什么这样设计

```python
ROOT_DIR = Path(__file__).parent.parent.parent
# config.py 位于 src/configuration/ 所以上溯 3 级到项目根
```

- `pathlib.Path` 从文件位置反推项目根目录，避免硬编码
- 任意机器 clone 后无需改路径
- 所有模块 `from configuration import config` 共享同一套路径

### 替代方案对比

| 方案 | 缺点 |
|------|------|
| 硬编码绝对路径 | 换机器就崩 |
| 环境变量 | 需要额外配置，容易漏 |
| YAML 配置文件 | 多一个文件依赖，路径还是要硬编码或从环境变量读 |
| **pathlib 反推根目录** | **零配置，clone 即用** |

### 面试追问
> Q: 如果项目目录结构变了怎么办？
> A: 只要 config.py 的相对位置不变（始终在 src/configuration/ 下），上溯级数不变即可。这是约定优于配置的思路。

## 2. 数据预处理 — process.py

### 作用
离线一次性预处理：原始 TSV → Arrow 格式的 tokenized dataset。

### 核心调用链

```
load_dataset("csv", delimiter="\t")
  → filter()                                    # 过滤 None
  → cast_column("label", ClassLabel(names=...)) # 固定标签映射
  → map(tokenize, batched=True)                  # 批量分词
  → save_to_disk()                               # Arrow 格式存储
```

### 为什么这样设计

1. **`cast_column` 而非 `class_encode_column`**：后者顺序不确定，训练/推理 id 可能错位。先 `sorted(set(labels))` 再 `cast_column` 保证固定顺序。
2. **`datasets.map(batched=True)`**：自动批处理 + 自动缓存 + Arrow 内存映射 + 多进程加速。
3. **离线预处理**：避免每次训练都重复 tokenize。

### 替代方案对比

| 方案 | 缺点 |
|------|------|
| 每次训练 tokenize | 重复计算，浪费 GPU 等待时间 |
| 手写 for 循环 | 无缓存，无并行，慢 |
| `class_encode_column` | 标签顺序随机，id 不一致 |
| **cast_column + sorted** | **固定顺序，训练/推理一致** |

### 面试追问
> Q: 为什么用 Arrow 格式？
> A: Arrow 是列式存储，支持内存映射（mmap），不一次性加载进内存。大数据集也能高效读取。

## 3. Dataset/DataLoader — dataset.py

### 作用
Dataset 和 DataLoader 的工厂函数，构建训练/评估用的数据加载器。

### 核心设计

```python
def get_dataset(dtype="train"):
    return load_from_disk(config.PROCESSED_DATA_DIR / dtype)

def get_dataloader(tokenizer, dtype="train"):
    dataset = load_from_disk(...)
    dataset.set_format("torch")          # HuggingFace → Tensor
    return DataLoader(dataset,
                      collate_fn=DataCollatorWithPadding(...))
```

### DataCollatorWithPadding vs tokenizer padding=True

| 方案 | 行为 | 效率 |
|------|------|------|
| `tokenizer(padding=True)` | 所有序列 pad 到固定长度（如 512） | 浪费 40-60% 计算 |
| `DataCollatorWithPadding` | 每个 batch 动态 pad 到该 batch 最长序列 | **高效，按需 padding** |

### 面试追问
> Q: 动态 Padding 为什么能省 40-60%？
> A: 电商标题平均长度远小于 512（BERT 最大长度）。静态 padding 把所有序列 pad 到 512，而动态 padding 只 pad 到 batch 内最长（如 30），attention_mask 标记 padding 位置让 BERT 忽略。

## 4. Trainer — train.py（最核心模块）

### 作用
封装完整的训练生命周期：训练循环、评估、Checkpoint、早停。

### Training_Config（dataclass）

```python
@dataclass
class Training_Config:
    epochs: int = 10
    learning_rate: float = 5e-5
    batch_size: int = 16
    save_step: int = 20          # 每多少步评估一次
    early_stop_metric: str = 'loss'
    patience: int = 3
    amp_enabled: bool = True
```

### 核心方法

| 方法 | 作用 |
|------|------|
| `train()` | 主训练循环，含断点续训逻辑 |
| `_train_one_batch()` | 单批次前向+反向+AMP |
| `evaluate()` | 验证集推理，无梯度 |
| `_should_early_stop()` | 早停判断 + 最优模型保存 |
| `_save_checkpoint()` | 保存完整训练状态 |
| `_load_checkpoint()` | 恢复训练状态 |

### AMP 混合精度

```python
# 初始化
self.scaler = torch.amp.GradScaler("cuda", enabled=True)

# 训练一批
with torch.autocast(device_type="cuda", dtype=torch.float16, enabled=True):
    outputs = self.model(**inputs)   # fp16 前向传播

loss = outputs.loss
self.scaler.scale(loss).backward()   # 放大梯度，防止 fp16 下溢
self.scaler.step(self.optimizer)     # 缩回梯度，更新参数
self.scaler.update()                 # 动态调整缩放系数
```

**数据变化**：autocast 内权重 fp32、计算 fp16（显存减半，速度提升 ~1.5-2x）

### 早停统一化

```python
# 统一化：loss 越小越好取负，accuracy/f1 越大越好
score = -metric if self.training_config.early_stop_metric == 'loss' else metric

if score > self.best_score:
    self.best_score = score
    self.early_stop_count = 0
    self.model.save_pretrained(...)  # 保存最优模型
    return False
else:
    self.early_stop_count += 1
    if self.early_stop_count > self.training_config.patience:
        return True  # 触发早停
```

### Checkpoint 完整状态

```python
checkpoint = {
    "model": self.model.state_dict(),       # 模型权重
    "opt": self.optimizer.state_dict(),     # Adam m/v
    "step": self.step,                      # 全局步数
    "count": self.early_stop_count,         # 早停计数
    "score": self.best_score,               # 历史最优分数
    "scaler": self.scaler.state_dict()      # AMP 缩放系数
}
```

### 面试追问
> Q: 为什么保存 optimizer 状态？
> A: Adam 的 momentum（m/v）是随训练积累的状态，不保存会导致续训初期参数更新行为与正常训练不同，影响稳定性。

## 6. Web 服务 — app.py / service.py / schemas.py

### 分层设计

```
schemas.py   →  数据校验层（Pydantic 请求/响应模型）
app.py       →  路由层（FastAPI 路由定义）
service.py   →  业务层（Title_Predict 调用 Predictor）
predict.py   →  模型推理层（Predictor 类）
```

### 模型在 app 启动时加载（全局单例）

```python
# service.py 中实例化一次
predictor = Predictor(...)  # app 启动时加载

# 每次请求直接调用
@app.post("/product_classify")
def classify(title: Title):
    result = predictor.predict(title.name)
    return {"category": result}
```

**为什么不在每次请求时加载？** BERT 模型 ~400MB，每次请求加载耗时数秒，启动时加载一次是标准做法。

### 面试追问
> Q: 如何支持高并发？
> A: 当前是单线程，可扩展为：1) uvicorn 多 worker；2) 模型推理异步化；3) 请求队列 + GPU 批量推理。
