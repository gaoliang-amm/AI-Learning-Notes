# 智能商品发布 — 面试追问与标准答案

---

## Q1: BERT 微调学习率为什么设 5e-5 这么小？

**答案**：BERT 预训练权重已经学到了很好的中文语义表示，微调本质是在已有语义空间中做小幅调整。如果 lr 太大（如 1e-3），会破坏预训练权重，导致"灾难性遗忘"（Catastrophic Forgetting）——模型忘记预训练学到的知识，效果反而变差。

BERT 微调推荐 lr 范围是 2e-5 ~ 5e-5，这是经验值。如果数据量很小（<1000），可以更小（1e-5）；数据量大可以稍大（3e-5）。

**追问方向**：如果面试官问"那为什么不设更小？"——太小收敛太慢，训练效率低，且容易陷入局部最优。

## Q2: 动态 Padding 的原理是什么？DataCollatorWithPadding 怎么工作的？

**答案**：

1. Tokenize 阶段只做 truncation（截断到 max_length=512），**不做 padding**
2. 每个 batch 构建时，DataCollatorWithPadding 找到该 batch 中最长的序列长度
3. 所有序列 pad 到这个长度（短序列补 0）
4. 自动生成 attention_mask，标记 padding 位置（0=padding，1=有效 token）
5. BERT 内部 attention 不会关注 padding token

**为什么省 40-60%？** 电商标题平均长度约 20-30 字，远小于 512。静态 padding 把所有序列 pad 到 512，大部分 token 是无用的 padding，attention 在这些 token 上浪费计算。动态 padding 只 pad 到 batch 内最长（如 30），大幅减少无效计算。

## Q3: AMP 混合精度训练原理？GradScaler 解决什么问题？

**答案**：

**AMP 原理**：
- `torch.autocast` 将部分运算（如矩阵乘法）降为 float16 加速
- 权重本身仍以 fp32 存储，计算时临时转 fp16
- 效果：显存减半，速度提升 ~1.5-2x

**GradScaler 解决的问题**：
- fp16 数值范围有限（最小正值约 6e-8），梯度容易下溢（变成 0）
- GradScaler 在 backward 前放大 loss（乘以 scale_factor，如 65536），使梯度数值更大
- step 时再缩回梯度，更新参数
- 如果检测到 inf/nan，跳过此步并降低 scale_factor

**三步曲**：
```python
scaler.scale(loss).backward()   # 放大梯度
scaler.step(optimizer)           # 缩回梯度，更新参数
scaler.update()                  # 动态调整缩放系数
```

## Q4: Checkpoint 保存了什么？为什么每一项都必须保存？

**答案**：

保存 6 项：
1. **model**（模型权重）：最基本的，续训需要
2. **optimizer**（Adam 的 m/v）：Adam 的 momentum 是随训练积累的状态，不保存会导致续训初期参数更新行为异常
3. **step**（全局步数）：续训时跳过已训练的步数
4. **early_stop_count**（早停计数）：恢复早停逻辑的连续性
5. **best_score**（历史最优分数）：恢复早停的比较基准
6. **scaler**（AMP 缩放系数）：scaler 有内部状态（当前 scale_factor），不保存续训时 AMP 行为不一致

**追问方向**：如果面试官问"为什么不保存 learning rate？"——因为 lr 是超参数，可以从 Training_Config 重新获取，不是运行时状态。

## Q5: 早停的 patience 应该怎么设置？与 save_step 的关系？

**答案**：

patience 和 save_step 联动决定实际的耐心步数：

```
实际耐心 = patience × save_step
```

例如：`save_step=20`，`patience=3`，意味着连续 60 步（3 次评估 × 20 步/次）无提升才停止。

设置原则：
- 数据集小（<5000）：save_step=20，patience=3（快速判断）
- 数据集大（>50000）：save_step=50，patience=5（给更多时间收敛）
- 关键：patience 太小容易过早停止，太大浪费训练时间

**追问方向**：如果面试官问"为什么不基于 epoch 早停？"——基于 step 的早停更细粒度，能更快检测到过拟合。

## Q6: 为什么用 cast_column 而不是 class_encode_column？

**答案**：

`class_encode_column` 的标签顺序取决于数据遍历顺序（即数据在数据集中的出现顺序），每次运行可能不同。这会导致：
- 训练时 label 0 = "酒水"，推理时 label 0 = "个护"
- 模型 accuracy 看起来很高但推理结果全错

`cast_column` + `sorted(set(labels))` 的做法：
1. 先对所有标签排序（字母序），得到固定顺序
2. 用 `ClassLabel(names=all_labels)` 创建固定映射
3. `cast_column` 按固定顺序编码

**关键**：排序保证每次运行标签 id 相同，这是工程正确性的基础。

## Q7: BertForSequenceClassification 内部结构是什么？

**答案**：

```
输入: input_ids + attention_mask
  ↓
Embedding Layer: token_embedding + position_embedding + segment_embedding
  ↓
Transformer Encoder: 12 层 Self-Attention + FFN
  ↓
[CLS] token 的 hidden state (768 维)
  ↓
Dropout (p=0.1)
  ↓
Linear(768, num_labels)
  ↓
logits (num_labels 维)
  ↓
CrossEntropyLoss (训练时，传入 labels 自动计算)
```

关键点：
- `[CLS]` token 的 hidden state 代表整个序列的语义
- `num_labels` 从 labels.txt 动态读取
- `id2label`/`label2id` 写入模型 config，`save_pretrained` 后推理无需外部文件

## Q8: 为什么模型在 app 启动时加载，而不是每次请求时加载？

**答案**：

BERT 模型 ~400MB，加载一次需要数秒。如果每次请求都加载：
- 100 QPS = 每秒加载 100 次 = 巨大开销
- 内存频繁分配/释放，GC 压力大

启动时加载一次（全局单例）：
- 加载开销分摊到所有请求
- 模型常驻内存，推理只需前向传播（毫秒级）
- 支持高并发（多 worker 时每个 worker 一份模型）

**追问方向**：如果面试官问"那模型更新怎么办？"——可以重启服务，或实现热更新（加载新模型后替换旧实例）。

## Q9: 如何扩展到分布式训练？

**答案**：

当前是单卡训练，扩展到多卡：

1. **DDP（DistributedDataParallel）**：最常用的多卡方案
   - 每张卡一个进程，模型复制到每张卡
   - 前向传播各卡独立，反向传播梯度 AllReduce 同步
   - 需要 `torch.distributed.init_process_group`

2. **改动点**：
   - DataLoader 加 `DistributedSampler`：每张卡只读部分数据
   - 模型包 `DistributedDataParallel(model)`
   - Checkpoint 只在 rank 0 保存
   - 评估只在 rank 0 做

3. **注意事项**：
   - Batch size 需要乘以 GPU 数量（每张卡 batch_size=16，4 卡总 batch=64）
   - 学习率可能需要相应调整
   - 混合精度在 DDP 下仍然有效

## Q10: 如果训练时 loss 不下降怎么办？

**答案**：

排查顺序：

1. **检查学习率**：是否太大（尝试 1e-5）或太小（尝试 1e-4）
2. **检查标签映射**：打印几个 batch 的 labels，确认 id 与文本对应
3. **检查数据加载**：打印 input_ids 对应的 decoded text，确认数据正确
4. **检查模型结构**：确认 num_labels 正确，分类头维度匹配
5. **检查 loss 计算**：确认 labels 传入了模型，outputs.loss 非 None

常见原因：
- lr 太大导致梯度爆炸
- 标签 id 错位（训练/推理不一致）
- 数据没有正确 shuffle
- 模型没有调用 model.train()

## Q11: 为什么用 Adam 而不是 AdamW？有什么区别？

**答案**：

Adam = 梯度一阶矩估计 + 二阶矩估计 + 偏差修正
AdamW = Adam + 解耦权重衰减（Decoupled Weight Decay）

**区别**：Adam 的 weight decay 实际上是 L2 正则化（加到梯度上），但理论证明这与真正的权重衰减不等价。AdamW 将 weight decay 从梯度更新中解耦，效果更好。

**本项目用 Adam 的原因**：简化实现。面试时可以指出这是一个优化点：
```python
# 当前
optimizer = torch.optim.Adam(model.parameters(), lr=5e-5)
# 优化
optimizer = torch.optim.AdamW(model.parameters(), lr=5e-5, weight_decay=0.01)
```

## Q12: 如何判断模型是否过拟合？怎么缓解？

**答案**：

**判断方法**：
- 监控训练 loss 和验证 loss 的差值
- 如果训练 loss 持续下降但验证 loss 上升 → 过拟合
- 如果训练 accuracy 和验证 accuracy 差距很大 → 过拟合

**缓解措施**（按优先级）：

1. **Early Stopping**（本项目已实现）：检测到验证集不再提升时停止
2. **Weight Decay**：AdamW + weight_decay=0.01
3. **数据增强**：同义词替换、随机删除、回译
4. **减少微调轮数**：BERT 微调通常 2-4 epoch 即可
5. **增大训练数据**：最有效但成本最高
6. **Dropout 调参**：增大 BERT 的 dropout rate（默认 0.1）

## Q13: Arrow 格式是什么？为什么用它？

**答案**：

Arrow 是 Apache Arrow 的列式内存格式，HuggingFace datasets 底层使用它：

1. **内存映射（mmap）**：数据在磁盘上，按需加载到内存，不一次性全读
2. **列式存储**：同一列数据连续存储，读取效率高
3. **零拷贝**：不同进程可以共享同一份 Arrow 数据
4. **支持大数据集**：10GB 数据也能高效处理

**替代方案的问题**：
- Python list：占内存大（每个元素是 Python 对象），无法 mmap
- Pandas DataFrame：内存效率不如 Arrow，且不支持 mmap
- NumPy：只支持数值类型，不适合混合类型数据

## Q14: 如果要上线这个模型，还需要做什么？

**答案**：

1. **模型量化**：INT8 量化减少推理显存，提速 2-3x
2. **推理优化**：ONNX Runtime 或 TensorRT 加速
3. **监控**：推理延迟、QPS、错误率、模型漂移检测
4. **A/B 测试**：灰度验证新模型效果
5. **数据飞轮**：线上错误 case 回流训练集，持续迭代
6. **高可用**：多副本、负载均衡、故障转移
7. **日志**：推理请求日志、模型版本管理

## Q15: 这个项目你最大的收获是什么？

**答案**：

最大的收获是理解了**工程正确性比算法设计更重要**。

具体来说：
1. **标签 id 一致性**：模型 accuracy 看起来 98%，但推理结果全错，原因是标签映射不一致。这让我意识到，算法效果再好，工程实现有 bug 就是零。
2. **AMP 的 GradScaler**：不理解原理就加 AMP，训练直接崩溃。这让我养成了"先理解原理再用工具"的习惯。
3. **Checkpoint 完整状态**：一开始只保存了 model，续训时 optimizer 状态丢失导致训练不稳定。后来补全了 6 项状态，续训效果才与连续训练一致。

这些经验让我形成了一个认知：**做 ML 工程，不仅要让模型 work，还要让系统 robust**。
