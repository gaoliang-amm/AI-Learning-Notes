# 电商智能客服系统 - 面试追问

## 设计决策类

### Q1：为什么用 LLM 做路由而不是意图分类模型？

→ 思路：考虑准确率、维护成本、扩展性

→ 回答：LLM 的理解能力更强，可以处理模糊表达和多意图混合场景。虽然意图分类模型更快更便宜，但需要标注数据训练，且难以处理新意图。LLM 只需要更新 prompt 就能支持新场景，维护成本更低。而且本项目的路由逻辑较复杂（需要理解上下文、任务状态），传统分类模型难以胜任。

---

### Q2：三轨可以同时执行吗？

→ 思路：考虑业务需求和实现复杂度

→ 回答：设计上是互斥的，任何一句话只走一条轨道。这是因为同一时刻用户只有一个主要意图。如果同时填充多条轨道，执行引擎一次只能处理一个，反而增加复杂度。而且多轨道并发执行会导致状态管理混乱。

---

### Q3：为什么用 YAML 描述流程而不是写在代码里？

→ 思路：考虑可维护性、可扩展性

→ 回答：三个原因：
1. **可维护性**：业务人员可以直接修改 YAML，无需懂代码
2. **可扩展性**：新增业务只需加 YAML 文件，无需改代码
3. **可测试性**：流程定义和执行逻辑分离，便于独立测试

---

### Q4：为什么需要白名单校验？

→ 思路：考虑 LLM 的不可控性

→ 回答：LLM 可能输出不存在的流程 ID、未注册的意图、同时填充多条轨道等。这些都会导致执行失败或产生错误结果。白名单校验可以提前拦截，配合澄清兜底，保证系统稳定性。

---

### Q5：为什么用 JSON 整份存储而不是拆表？

→ 思路：考虑实现成本和调试便利性

→ 回答：学习阶段为了调试方便，可以直接查看数据库记录。整份 JSON 序列化/反序列化实现简单，支持复杂嵌套结构。生产环境可能需要拆表以支持按字段查询和并发更新。

---

## 方案对比类

### Q6：为什么不直接用 RAG 处理所有问题？

→ 思路：考虑业务场景差异

→ 回答：RAG 适合"咨询"场景（只需回答问题），但"办事"场景（如退款申请）需要多步操作、状态管理、调用外部 API。这些是 RAG 无法处理的，需要流程编排。所以三轨分离，各司其职。

---

### Q7：为什么不直接用 Agent 框架（如 LangChain Agent）？

→ 思路：考虑可控性和学习成本

→ 回答：Agent 框架虽然灵活，但可控性较差，难以保证每次执行结果一致。本项目的业务流程是确定性的（查订单、退款），不需要 Agent 的自主决策能力。用 YAML 流程编排更可控，且学习成本更低。

---

### Q8：为什么不微调一个专门的意图分类模型？

→ 思路：考虑数据、成本、灵活性

→ 回答：三个原因：
1. **数据不足**：没有足够的标注数据
2. **成本高**：微调需要 GPU 资源
3. **灵活性差**：新意图需要重新训练

LLM 只需要更新 prompt 就能支持新场景，更适合探索阶段。

---

### Q9：FlowExecutor 的两层循环可以用状态机框架替代吗？

→ 思路：考虑复杂度和适用性

→ 回答：可以，但没必要。状态机框架（如 transitions）更规范，但学习成本高，且本项目的流程逻辑相对简单（顺序执行 + 条件分支），两层循环已经足够清晰。项目规模不需要引入重型框架。

---

### Q10：pending_turn 的两步提交可以用消息队列替代吗？

→ 思路：考虑异步和可靠性

→ 回答：可以，但本项目是同步处理（一次请求处理一条消息），不需要消息队列。pending_turn 的目的是保证数据完整性（处理失败时丢弃），不是为了解耦。如果未来需要异步处理，可以考虑引入消息队列。

---

## 调试能力类

### Q11：如果 LLM 一直输出格式错误的 JSON，你怎么 debug？

→ 思路：考虑调试方法和工具

→ 回答：
1. **打印 LLM 原始输出**：查看是否是格式问题
2. **检查提示词**：是否明确要求 JSON 格式
3. **使用更稳定的模型**：如 qwen-plus 比 qwen-turbo 更稳定
4. **添加重试机制**：格式错误时重试
5. **使用 Function Calling**：更可靠的结构化输出

---

### Q12：如何排查意图识别不准确的问题？

→ 思路：考虑分析方法

→ 回答：
1. **收集失败案例**：记录校验失败的 TurnPlan
2. **分析原因**：是提示词问题、历史干扰、还是模型能力不足
3. **优化提示词**：添加示例、明确轨道定义
4. **限制历史长度**：只取最近 10 轮，减少干扰
5. **A/B 测试**：对比不同提示词的效果

---

### Q13：如果用户说"刚才的订单"，系统不知道是哪个，怎么处理？

→ 思路：考虑上下文理解

→ 回答：
1. **检查 focused_object**：用户是否点击了订单卡片
2. **检查对话历史**：之前的对话中是否提到过订单号
3. **槽位继承**：如果 active_task 中有 order_number，自动填充
4. **澄清询问**：如果都不行，友好地询问用户

---

## 异常处理类

### Q14：如果 LLM API 不可用，系统怎么降级？

→ 思路：考虑容灾方案

→ 回答：
1. **返回友好提示**："系统繁忙，请稍后再试"
2. **降级到规则引擎**：用关键词匹配处理简单场景
3. **缓存常用回复**：高频问题直接返回缓存
4. **人工接管**：转接人工客服

---

### Q15：如果电商后端 API 超时，系统怎么处理？

→ 思路：考虑超时处理

→ 回答：
1. **设置合理超时**：httpx 超时 10 秒
2. **返回错误信息**：告诉用户"暂时无法查询，请稍后再试"
3. **记录日志**：便于排查问题
4. **重试机制**：网络抖动时自动重试

---

### Q16：如果数据库连接失败，系统怎么处理？

→ 思路：考虑数据持久化失败

→ 回答：
1. **降级到内存**：对话状态保存在内存，重启后丢失
2. **返回错误**：告诉用户"系统异常，请稍后再试"
3. **记录日志**：便于排查问题
4. **告警通知**：及时发现并修复

## 量化指标类

### Q17：意图识别准确率是多少？怎么评估？

→ 思路：考虑评估方法

→ 回答：
- **评估方法**：收集 100 条真实用户输入，人工标注正确轨道，对比系统输出
- **当前指标**：未正式评估（学习阶段）
- **优化目标**：> 90%
- **提升方法**：优化提示词、使用更强模型、微调

---

### Q18：系统响应延迟是多少？瓶颈在哪？

→ 思路：考虑性能分析

→ 回答：
- **当前延迟**：1-5 秒
- **瓶颈**：LLM 调用（1-3 秒）
- **优化方向**：
  - 使用更快模型（qwen-turbo）
  - 缓存常用意图
  - 流式输出

---

### Q19：系统能支持多少并发用户？

→ 思路：考虑并发能力

→ 回答：
- **当前**：单用户测试
- **瓶颈**：LLM API 并发限制、数据库连接池
- **优化方向**：
  - 异步处理（asyncio）
  - 连接池优化
  - LLM API 并发配额提升
- **目标**：100+ 并发用户

---

### Q20：数据规模有多大？

→ 思路：考虑系统容量

→ 回答：
- **对话状态**：每个用户一个 JSON 记录
- **会话历史**：每个会话包含多个 Turn
- **流程定义**：2 个 YAML 文件（user_flows + system_flows）
- **知识库**：当前为占位实现，实际项目中可能有 1000+ 文档
