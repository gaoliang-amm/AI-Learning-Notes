# 电商智能客服系统 - 面试表达

## 30秒版（电梯介绍）

> 我做了一个电商智能客服系统，核心设计是"LLM 路由 + YAML 流程编排"。
>
> 用户说一句话，LLM 判断走哪条轨道：任务流程、知识问答、还是闲聊。任务流程用 YAML 描述业务步骤，代码只负责执行，新增业务只需加 YAML 文件。
>
> 关键创新是用工程化方式驯服 LLM 的不确定性——通过白名单校验防止幻觉，通过澄清兜底处理歧义。支持查订单、查物流、退款申请等 7 种业务场景。

---

## 2~5分钟版（系统讲解）

### 开场（30秒）

> 这是一个电商智能客服系统，解决的问题是：电商客服每天处理大量重复咨询，传统关键词机器人答非所问，人工成本又太高。
>
> 我的方案是用 LLM 理解用户意图，用代码执行具体动作，让系统既能理解自然语言，又能稳定完成业务操作。

### 架构（1分钟）

> 系统采用分层架构：API 层 → Service 层 → Engine 层 → Domain 层。
>
> 核心设计是"三轨分离"：任何一句话只走一条轨道——任务流程、知识问答、或者闲聊。
>
> - **任务轨道**：处理"办事"场景，如查订单、退款。用 YAML 描述业务流程，FlowExecutor 按步骤执行。
> - **知识轨道**：处理"咨询"场景，如商品信息、政策问题。用 RAG 检索知识，LLM 生成回复。
> - **闲聊轨道**：兜底，处理打招呼等非业务对话。

### 核心模块（1.5分钟）

> 最核心的是三个模块：
>
> **第一，TurnPlanner**。这是"LLM 路由器"，把对话上下文喂给 LLM，让它输出结构化的"行动计划"。比如用户说"退款"，LLM 输出 Task 轨道 + StartFlowCommand。
>
> **第二，TurnPlanValidator**。这是"守门员"，校验 LLM 输出是否合法。防止它幻觉出不存在的流程或意图。校验失败会触发澄清兜底，友好地引导用户重新表达。
>
> **第三，FlowExecutor**。这是"工人"，沿 YAML 流程图一步步推进。采用两层循环：内层推 Step，外层执行 Action。遇到等待用户输入时停下来。

### 亮点（30秒）

> 几个设计亮点：
>
> 1. **流程与代码分离**：YAML 描述流程，代码只负责执行。新增业务只需加 YAML 文件，无需改代码。
> 2. **防幻觉机制**：白名单校验 + 澄清兜底，驯服 LLM 的不确定性。
> 3. **任务栈管理**：支持任务打断和恢复，用户体验更自然。

## 5~15分钟版（深入细节）

### 背景与问题（2分钟）

> 电商客服每天处理大量重复咨询：查订单、查物流、退款申请、商品咨询。传统方案有两种问题：
>
> 1. **人工坐席**：成本高，需要养大团队
> 2. **关键词机器人**：理解能力差，稍微复杂的问法就答非所问
>
> 随着大模型成熟，"用 LLM 理解意图 + 用代码执行动作"成为新范式。本项目就是这样一套系统。

### 系统架构（3分钟）

> 系统采用分层架构，核心是 Engine 层的"三轨分离"：
>
> ```mermaid
> graph LR
>     A[用户消息] --> B[TurnPlanner<br/>LLM 路由]
>     B --> C{三轨路由}
>     C --> D[Task<br/>YAML 流程]
>     C --> E[Knowledge<br/>RAG 检索]
>     C --> F[Chitchat<br/>LLM 对话]
> ```
>
> **为什么三轨分离？**
> - Task 轨道处理"办事"，步骤明确，用 YAML 编排
> - Knowledge 轨道处理"咨询"，需要检索外部信息
> - Chitchat 轨道兜底，处理非业务对话
>
> 三轨互斥，任何一句话只走一条。这样每条轨道的职责清晰，便于独立优化。

### 核心技术实现（5分钟）

> **1. LLM 路由 + 白名单校验**
>
> TurnPlanner 调用 LLM 输出 TurnPlan（JSON 格式），TurnPlanValidator 校验是否合法。
>
> ```
> LLM 输出 → 白名单校验 → 澄清兜底
>     ├─ 校验通过 → 执行
>     └─ 校验失败 → 友好提示
> ```
>
> 这是驯服 LLM 不确定性的关键：LLM 可能幻觉出不存在的流程，白名单校验提前拦截。
>
> **2. YAML 流程编排**
>
> 用 YAML 描述业务流程：
>
> ```yaml
> refund_request:
>   name: 退款申请
>   steps:
>     - id: start
>       type: start
>       next: ask_order_number
>     - id: ask_order_number
>       type: collect
>       slot_name: order_number
>       response:
>         text: "请告诉我你的订单号。"
> ```
>
> FlowExecutor 是解释器，沿流程图推进。采用两层循环：内层推 Step，外层执行 Action。
>
> **3. 状态管理**
>
> DialogueState 是聚合根，管理所有状态：
> - active_task：当前活跃任务
> - paused_task：挂起任务栈（支持 LIFO 恢复）
> - pending_turn：两步提交的中间态
>
> 两步提交保证数据完整性：处理失败时丢弃 pending_turn，turns 始终干净。

### 挑战与方案（3分钟）

> **挑战 1：LLM 输出不可控**
> - 问题：LLM 可能输出不存在的流程、同时填充多条轨道
> - 方案：白名单校验 + 澄清兜底
> - 效果：所有输出必须通过校验，否则触发澄清
>
> **挑战 2：多轮对话状态管理**
> - 问题：任务中断后需要恢复，会话超时需要重置
> - 方案：任务栈（LIFO）+ 会话超时机制
> - 效果：支持任务打断和恢复，用户体验自然
>
> **挑战 3：流程与代码耦合**
> - 问题：新增业务需要改代码，维护成本高
> - 方案：YAML 描述流程，代码只负责执行
> - 效果：新增业务只需加 YAML 文件，无需改代码

### 成果与收获（2分钟）

> **成果**：
> - 支持 7 种业务场景（查订单、查物流、退款、商品咨询等）
> - 响应时间 1-5 秒
> - 工程化保障稳定性
>
> **收获**：
> - 理解了 LLM 应用的工程化挑战
> - 掌握了"LLM + 规则"的混合架构设计
> - 学会了用状态机管理复杂对话流程

## STAR 法则版（追问准备）

### 情境（Situation）

> 电商客服每天处理大量重复咨询，传统关键词机器人理解能力差，人工成本高。需要一套既能理解自然语言，又能稳定执行业务动作的系统。

### 任务（Task）

> 设计并实现一套智能客服系统，核心挑战是：
> 1. 如何让 LLM 理解用户意图并路由到正确轨道
> 2. 如何保证 LLM 输出的可控性（防幻觉）
> 3. 如何支持多轮对话和状态管理

### 行动（Action）

> 1. **三轨分离**：Task（YAML 流程）/ Knowledge（RAG）/ Chitchat（LLM）
> 2. **防幻觉机制**：TurnPlanValidator 白名单校验 + ClarifyResponder 澄清兜底
> 3. **状态管理**：DialogueState 聚合根 + 任务栈 + 两步提交
> 4. **流程编排**：YAML 描述流程，FlowExecutor 解释执行

### 结果（Result）

> - 支持 7 种业务场景
> - 响应时间 1-5 秒
> - 工程化保障稳定性
> - 新增业务只需加 YAML 文件，维护成本低

## 表达技巧

### 1. 数字化表达

| ❌ 模糊表达 | ✅ 数字化表达 |
|------------|--------------|
| 支持多种场景 | 支持 7 种业务场景 |
| 响应很快 | 响应时间 1-5 秒 |
| 准确率很高 | 意图识别准确率 > 90% |

### 2. 对比表达

| ❌ 单一描述 | ✅ 对比描述 |
|------------|------------|
| 用 YAML 描述流程 | 相比硬编码，YAML 描述流程维护成本降低 50% |
| 用 LLM 路由 | 相比关键词匹配，LLM 路由理解能力提升显著 |

### 3. 架构表达

| ❌ 细节描述 | ✅ 架构描述 |
|------------|------------|
| 我写了一个函数处理用户消息 | Engine 层采用三轨分离架构 |
| 我用了数据库存状态 | Domain 层采用聚合根模式管理状态 |
