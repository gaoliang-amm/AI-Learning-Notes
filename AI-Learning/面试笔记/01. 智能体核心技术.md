## 1. Python 基础

### 1.1 数据结构相关

#### 1.1.1 list 和 tuple 有什么区别？

列表（list）是可变的，可执行添加、删除或修改元素等操作；元组（tuple）不可变，创建后内容不能更改。且元组能被哈希，可用作字典的键，但列表不行。

### 1.2 闭包相关

#### 1.2.1 什么是闭包？请简述其定义和形成条件。

闭包是一种特殊的函数嵌套结构，指在外部函数内部定义的内部函数，引用了外部函数的变量（非全局变量），且外部函数返回该内部函数。

> [!important] 闭包三条件
> - 存在函数嵌套（内部函数定义在外部函数中）；
> - 内部函数引用了外部函数的变量；
> - 外部函数返回内部函数的引用。
> [!warning] 易错点
> 在闭包中，内部函数默认只能读取外部函数的变量，若直接修改会被 Python 判定为 “定义局部变量”，导致报错。需使用 `nonlocal` 关键字声明变量，明确其来自外部函数的作用域，允许内部函数修改。

示例：

```python
# 错误示例：直接修改外部变量
def outer():
    x = 10
    def inner():
        x += 5  # 报错：局部变量x在赋值前被引用
        print(x)
    return inner

# 正确示例：使用nonlocal
def outer():
    x = 10
    def inner():
        nonlocal x  # 声明x来自外部函数
        x += 5
        print(x)
    return inner

func = outer()
func()  # 输出15
```

#### 1.2.2 闭包为什么能保留外部函数的变量？

> [!note] 闭包保留变量的原理
> 正常情况下，函数执行结束后，其内部变量会被销毁。但闭包中，内部函数引用了外部函数的变量，形成 “变量捕获”，使得这些变量不会随外部函数的结束而销毁，而是被内部函数 “保留” 在内存中，直到内部函数被销毁。
>
> 这种机制依赖 Python 的作用域链：内部函数在查找变量时，会先在自身作用域查找，若未找到则向上级（外部函数）作用域查找，闭包通过这种链式查找保留了对外部变量的引用。

#### 1.2.3 闭包有哪些实际应用场景？请举例说明。

闭包的核心价值是 “保留状态” 和 “封装数据”，常见应用场景包括：

**装饰器（Decorator）**

装饰器本质是闭包，用于在不修改原函数代码的前提下，添加额外功能（如日志、计时）。

```python
def log_decorator(func):
    def wrapper(*args, **kwargs):
        print(f"调用函数: {func.__name__}")
        result = func(*args, **kwargs)
        print("函数执行完毕")
        return result
    return wrapper  # 闭包返回包装后的函数

@log_decorator
def add(a, b):
    return a + b

print(add(2, 3))  # 输出日志并返回5
```

**数据封装与隐藏**

模拟类的私有变量，通过闭包隐藏内部状态，只暴露操作接口。

```python
def create_counter():
    count = 0  # 隐藏的状态变量
    def increment():
        nonlocal count
        count += 1
        return count
    def reset():
        nonlocal count
        count = 0
    return increment, reset  # 返回操作接口

inc, res = create_counter()
print(inc())  # 1
print(inc())  # 2
res()
print(inc())  # 1
```

**函数工厂**

动态生成具有不同参数的函数，避免重复代码。

```python
def make_multiplier(factor):
    def multiply(num):
        return num * factor  # 保留factor的值
    return multiply

double = make_multiplier(2)
triple = make_multiplier(3)
print(double(5))  # 10
print(triple(5))  # 15
```

#### 1.2.4 闭包可能导致什么问题？如何避免？

**问题**

闭包会保留外部函数的变量，若变量是大型对象或未及时释放，可能导致内存泄漏（变量长期占用内存不释放）。

**避免方式**

- 不再使用闭包时，手动将其引用设为None（触发垃圾回收）；
- 避免在闭包中引用过大的对象；
- 若需频繁创建闭包，考虑用类替代（类的__del__方法可主动释放资源）。

### 1.3 迭代器和生成器和装饰器

#### 1.3.1 什么是Python中的迭代器？

能被循环逐个取值，同时拥有 __iter__() ，__next__()两个函数的对象。

例如：列表，字符串，字典本身不是迭代器，需要使用iter()函数转换为迭代器

> [!important] 循环的本质
> 1. 调用 `iter()` 获取迭代器
> 2. 不断调用 `next()` 取值
> 3. 取完后抛出 `StopIteration`

**特点**

- 懒加载，用到才取
- 只能往前取
- 取完不能自动重来

**使用场景**

- 超大文件读取、百万行日志逐条读取，避免一次性加载内存溢出
SSE流式传输：将大模型生成的文本实时推送给前端，提升用户体验

在工作流执行过程中，实时获取每个节点的状态

```python
# LangGraph 的 stream() 是典型的状态迭代器
for event in workflow.stream(initial_state):
    # event 包含当前节点的输出状态
    # 可以实时追踪进度

# stream() 返回迭代器：
# ┌─────────────────────────────┐
# │ 第一次迭代: entry_node完成   │ ← event = {entry_node: state}
# ├─────────────────────────────┤
# │ 第二次迭代: document_load完成│ ← event = {document_load: state}
# ├─────────────────────────────┤
# │ 第三次迭代: document_split完成│
# ├─────────────────────────────┤
# │ ...                         │
# └─────────────────────────────┘
# 迭代结束，获取最终状态
```

#### 1.3.2 什么是 Python 中的生成器？

生成器（Generator） 是一种特殊的迭代器，使用 yield 关键字实现，能够惰性生成数据，而不是一次性将所有数据加载到内存。

**特点**

- 本质上是迭代器
- 可以用 next() 取值
- 每次只生成一个值
- 不一次性加载所有数据
- 适合大数据、大范围、流式处理场景

**案例**

```python
# ❌ 普通函数：一次性返回所有数据（内存占用大）
def get_all_numbers():
    result = []
    for i in range(1000000):
        result.append(i * 2)
    return result  # 占用约16MB内存

# ✅ 生成器函数：惰性生成数据（内存占用极小）
def get_numbers_generator():
    for i in range(1000000):
        yield i * 2  # 每次只生成一个，内存占用几乎为0
```

**使用场景**

**SSE流式传输（核心场景）**

```python
def retry(max_attempts=3, delay=1):
    def decorator(func):
        def wrapper(*args, **kwargs):
            for attempt in range(max_attempts):
                try:
                    return func(*args, **kwargs)
                except Exception as e:
                    if attempt == max_attempts - 1:
                        raise
                    time.sleep(delay)
        return wrapper
    return decorator

@retry(max_attempts=3, delay=2)
def call_external_api():
    # 调用外部API
    pass
```

#### 1.3.3 什么是 Python中的装饰器？

装饰器是Python的一种语法糖，用于在不修改原函数代码的情况下，为函数添加额外功能。

**特点**

- 不修改原函数代码
- 代码复用性强
- 支持嵌套使用

**案例**

```python
# 装饰器本质是一个函数
def my_decorator(func):  # 接收被装饰的函数
    # 可变参数位置：将接收任意数量的位置参数打包成元组
    # 可变参数位置：将接收任意数量关键字参数打包成字典
    def wrapper(*args, **kwargs):
        print("函数执行前")
        result = func(*args, **kwargs)  # 执行原函数
        print("函数执行后")
        return result
    return wrapper

# 使用装饰器
@my_decorator
def say_hello():
    print("Hello!")

# 调用函数
say_hello()
# 输出:
# 函数执行前
# Hello!
# 函数执行后
```

**使用场景**

记录日志

```python
import time

def timer(func):
    def wrapper(*args, **kwargs):
        start = time.time()
        result = func(*args, **kwargs)
        end = time.time()
        print(f"{func.__name__} 执行耗时: {end - start:.2f}秒")
        return result
    return wrapper

@timer
def query_database():
    # 数据库查询
    pass
```

性能计时

```python
def log_execution(func):
    def wrapper(*args, **kwargs):
        logger.info(f"开始执行: {func.__name__}")

            return result
        except Exception as e:
            logger.error(f"执行失败: {func.__name__}, 错误: {e}")
            raise
    return wrapper

@log_execution

    # 处理文件

```

重试机制

> [!tip] 面试一句话
> 迭代器是解决遍历问题，生成器是解决内存问题，装饰器是解决监控问题。

```python
async def sse_generator(task_id: str, request: Request) -> AsyncGenerator:
    """
    异步生成器：从队列中持续获取数据并yield出去
    """
    sse_queue = _task_stream.get(task_id)  # 获取队列
    loop = asyncio.get_event_loop()

    while True:
        # 检测客户端是否断开连接
        if await request.is_disconnected():
            return

        try:
            # 从队列阻塞获取消息

            event_type = msg.get('event')
            event_data = msg.get('data')

            # ✅ 关键：使用yield将数据推送给前端
            yield _sse_pack(event_type, event_data)

        except queue.Empty:
            continue  # 队列为空，继续等待
```

### 1.4 并发、异步与多任务

#### 1.4.1 同步和异步是什么意思？

同步：你点完菜，站在柜台等厨师做完端给你，期间什么也不干。

异步：你点完菜拿个小票，回去刷手机，做好了叫号你再去取。

| 概念 | 一句话 | 适合场景 |
| --- | --- | --- |
| 同步 | 发起任务-等待结果-再往下走 | 逻辑简单，步骤必须按照顺序执行 |
| 异步 | 发起任务-不等结果-结果好了再处理 | 网络请求，文件读写，消息处理 |

#### 1.4.2 进程、线程、协程有什么区别？

进程：操作系统分配资源的独立单元。 每个进程有自己独立的地址空间（代码、数据、堆、栈），进程之间默认完全隔离

线程：进程内部的操作系统调度的执行流。 同一进程的多个线程共享地址空间，各自有独立的调用栈和寄存器上下文。

协程：用户态程序自己管理的协作式执行单元。 不依赖操作系统调度，由程序显式让出控制权（yield / await）。

#### 1.4.3 什么是 GIL（全局解释器锁）？

> [!important] GIL（全局解释器锁）
> GIL 是 CPython 解释器里的一把**全局锁**，同一时刻只允许一个线程执行 Python 字节码。
>
> **影响分两种情况：**
> - I/O 密集型：影响不大。线程在等网络/磁盘时会主动释放 GIL，多线程仍有价值。
> - CPU 密集型：影响严重。多线程没法真正并行跑在多个 CPU 核上。

#### 1.4.4 线程、协程、多进程分别适合什么场景？

使用场景：CPU 密集 → 多进程；高并发 I/O → 协程；简单后台并发 → 线程。

|  | 适合 | 不适合 | 典型任务 |
| --- | --- | --- | --- |
| 线程 | I/O 密集、需要共享内存、任务量中等（几十到几百） | CPU 密集（GIL 限制）、超高并发（内存爆炸） | 文件读写、接口调用、后台轮询 |
| 协程 | 高并发 I/O、连接数多（成千上万）、单任务计算量小 | CPU 密集（会堵住事件循环）、需大量同步库的项目 | HTTP 客户端、WebSocket、SSE、大模型流式输出 |
| 多进程 | CPU 密集、需绕开 GIL、需强隔离（一挂不影响其他 | I/O 密集（杀鸡用牛刀）、需频繁共享数据（IPC 成本高） | 图像/视频处理、批量特征计算、模型并行 |

#### 1.4.5 为什么 I/O 操作常用协程而不是线程？

> [!important] 核心结论
> 核心原因：I/O 任务大部分时间都在等，协程正擅长处理"等待"。

| 对比维度 | 协程                   | 线程               |
| ---- | -------------------- | ---------------- |
| 调度开销 | 用户态自己切换，极低           | 操作系统内核态切换，较高     |
| 内存占用 | 一个协程 ~KB级别           | 一个线程 ~MB级别       |
| 并发效率 | 等I/O时主动让出，事件循环调度其他任务 | 等I/O时有OS调度，切换成本高 |

不过线程也没被淘汰：当你依赖同步库、任务量不大、或者改造异步成本太高时，线程仍然是好选择。

#### 1.4.6 async 和 await 在 Agent 实现中起什么作用？

async 用于定义异步函数

await 用于等待异步任务完成并释放当前协程的执行权。

在 Agent 系统中，它们常用于并发工具调用、流式输出、模型接口请求、检索请求和多 Agent 并行执行。

**典型场景**

| 场景 | 作用 |
| --- | --- |
| 并发工具调用 | 同时调用搜索、数据库、RAG 检索等工具 |
| 流式输出 | 边生成边返回 token 或事件 |
| 超时控制 | 对外部工具和模型请求设置等待时间 |
| 多 Agent 协作 | 并发执行多个子任务后汇总结果 |
| WebSocket/SSE | 保持连接期间持续推送中间结果 |

answer = await call_llm(docs)

## 2. LangChain & LangGraph

### 2.1 什么是 LangChain，它有哪些核心组件，在项目里起什么作用

LangChain 是一个面向 LLM 应用编排的开发框架，重点解决提示词组织、模型调用、工具调用、检索增强、输出解析和链式执行这些问题。常见组件有：

- Models：统一封装不同大模型的调用
- Prompts：管理提示词模板和变量注入
- Output Parsers：把模型输出转成结构化结果
- Tools：让模型可以调用外部能力
- Retrievers / VectorStores：接检索、向量库、RAG
- Chains：把多个步骤串起来
- Memory：管理对话上下文
在项目里，LangChain 更适合做线性流程、单次问答、RAG 链路、工具封装这类结构比较稳定的场景，优势是上手快、组件化强、开发效率高。

### 2.2 什么是 LangGraph，状态、节点、边、条件边分别是什么

LangGraph 是“面向 Agent 和复杂工作流的状态机框架”，适合处理多步骤、可分支、可循环、可恢复的流程。

**核心概念**

- State：整个流程共享的数据上下文
- Node：一个执行步骤，可以是模型调用、工具执行、检索、判断逻辑
- Edge：节点之间的固定流转关系
- Conditional Edge：根据状态或节点输出决定下一步走向
如果说 LangChain 更像“链”，LangGraph 更像“图”。它适合复杂编排，支持分支、循环、重试、暂停和恢复。

在langgraph可以使用langchain的组件。

### 2.3 LangChain 和 LangGraph 的区别是什么，分别适合什么场景

> [!important] 核心区别
> 核心区别在于抽象层级和流程复杂度。

**LangChain 更偏**

- 线性流程
- 组件封装
- 快速搭 RAG、工具链、问答链
- 流程固定、分支少的场景

**LangGraph 更偏**

- 状态驱动
- 多分支、多轮决策
- Agent 工作流
- 需要循环、回退、重试、暂停恢复的场景

**适用关系**

> [!tip] 面试一句话
> - 简单链路优先 LangChain
> - 复杂工作流、Agent 编排优先 LangGraph
比如电商小二如果偏单轮问答、工具链固定，用 LangChain 就够；如果掌柜智库涉及多路检索、判断、反复修正、状态流转，那用 LangGraph 更合适。

### 2.4 LangGraph 和 YAML 配置工作流有什么不同

YAML 更适合“固定流程编排”，LangGraph 更适合“有状态的动态决策流程”。

### 2.5 怎么避免 LangGraph 死循环

防死循环一般会从几个层面做：

- 设置最大轮次
- 将改进结果/失败结果反馈给下次的处理
- 给模型明确退出条件（服务挂掉）
- 对工具失败设置兜底分支（拒答）
> [!important] 核心结论
> 循环必须有边界，失败必须有出口。

## 3. Agent 与 RAG

### 3.1 基础概念与架构

#### 3.1.1 Agent 是什么，和纯提示词、RAG、套壳大模型有什么区别

> [!note] Agent 定义
> Agent 是带有目标、规划、工具调用和状态管理能力的 LLM 应用。它能够围绕目标拆解任务、调用工具、读写状态，并根据执行结果继续决策。
- 纯提示词：只靠一轮输入输出，没有外部执行能力
- RAG：重点是检索增强回答，核心是找资料，复杂决策能力依赖额外流程编排
- 套壳大模型：只是把聊天界面接到模型上，没有完整执行闭环
> [!important] 核心结论
> 成熟 Agent 的核心是模型、工具、状态、流程控制、记忆、校验和兜底。

#### 3.1.2 一个成熟的 Agent 架构通常包含哪些部分

**脑：LLM / ChatModel**

负责理解问题、推理下一步该做什么。

**手：Tools 工具**

Agent 可调用的外部能力，比如搜索、数据库、API、计算器、RAG 检索等。

**记忆：Memory / State**

保存上下文、历史对话、中间步骤或业务状态，让 Agent 能连续处理任务。

**流程：Agent Executor / Runtime**

负责执行循环：

接收任务 -> 调用模型思考 -> 选择工具 -> 执行工具 -> 观察结果 -> 再次决策 -> 输出答案。

#### 3.1.3 RAG 是什么，完整链路是什么

RAG 是 Retrieval-Augmented Generation，检索增强生成。它把外部知识库中的内容检索出来，作为上下文交给大模型生成答案。

> [!important] RAG 完整链路
> 完整链路包括文档解析、清洗、切分、向量化、索引入库、查询处理、召回、融合重排、上下文组装、答案生成和评测监控。

#### 3.1.4 大模型为什么需要外挂知识库，RAG 和微调有什么区别

大模型外挂知识库用于补充时效性知识、私有领域知识和可追溯来源，也用于降低训练和微调成本。

> [!note] RAG vs 微调
> RAG 主要解决外部知识接入问题，知识保存在数据库、向量库或文档库中，更新知识时更新知识库即可。
>
> 微调主要改变模型行为、表达风格、任务格式或垂直任务能力，知识和模式会进入模型参数，更新成本更高。

### 3.2 任务执行与流程编排

#### 3.2.1 Workflow、 ReAct和 Plan-and-Execute 有什么区别

ReAct、Workflow 和 Plan-and-Execute 是常见的 Agent 或工作流组织方式。

- ReAct：推理和行动交替进行，适合动态工具调用和逐步探索
- Workflow：预定义节点和边，适合确定性强、稳定性要求高的业务链路
- Plan-and-Execute：先生成任务计划，再逐步执行，适合较长任务和可拆解目标
ReAct 适合开放探索，Workflow 适合稳定生产流程，Plan-and-Execute 适合复杂长任务。

#### 3.2.2 ReAct 的结构是什么，action 的职责是什么

- ReAct 的价值在于让模型围绕“思考、查找、执行、观察”持续推进任务，也因此更依赖工具质量和循环控制。
ReAct 的基本结构：

- Thought：当前如何理解问题
- Action：决定调用哪个工具（比如查知识库、调接口、跑 SQL、做检索。）
- Observation：工具返回的结果
- 再进入下一轮 Thought

### 3.3 工具调用与能力封装

#### 3.3.1 Function Calling 是什么，执行机制是什么？

Function Calling 是让模型按约定格式选择并调用函数。模型本身不会执行外部函数，只会输出要调用的函数名和参数。

执行机制的本质是 装饰器 + 工具映射表

```python
tools = {}
def tool(func):
tools[func.__name__] = {
"function": func,
"name": func.__name__,
"description": func.__doc__,
"parameters": func.__annotations__,
}
return func
```

使用：

```python
@tool
def add(a: int, b: int) -> int:
"""计算两个数的和"""
return a + b
```

等价于把 add 注册进工具表：

```python
tools["add"] = add。
```

#### 3.3.2 Function Calling、MCP 和 Skill 有什么区别

- Function Calling：一次工具调用机制
- MCP：一组工具或资源的标准接入方式
- Skill：一类可复用的能力封装，而能力可以是各种形式可能是文本，可能是脚本、应用程序或者网络服务。

#### 3.3.3 普通 HTTP 接口怎么包装成 MCP

常见步骤：

- 按能力拆分 HTTP 接口
- 为每个工具定义名称、描述、参数 schema 和返回结构
- 在服务端处理认证、超时、重试和错误
- 通过 MCP server 统一暴露工具
- 在客户端或 Agent 运行时加载 MCP 工具
这样模型侧看到的是标准化工具，接口细节由 MCP server 屏蔽。

服务发布端

```python
import os
import httpx
from mcp.server.fastmcp import FastMCP
mcp = FastMCP(
"business-api",
stateless_http=True,
json_response=True,
)
BUSINESS_API_URL = os.getenv(
"BUSINESS_API_URL",
"http://127.0.0.1:8080",
)
@mcp.tool()
async def query_order(order_no: str) -> dict:
"""
根据订单号调用订单系统HTTP接口，查询订单详情。
"""
async with httpx.AsyncClient(
base_url=BUSINESS_API_URL,
timeout=10.0,
) as client:
response = await client.get(
f"/api/orders/{order_no}"
)
response.raise_for_status()
result = response.json()
return result["data"]
if __name__ == "__main__":
mcp.run(transport="streamable-http")
```

### 3.4 记忆、上下文与输出控制

#### 3.4.1 Agent 记忆怎么设计，短期记忆和长期记忆分别解决什么问题

短期记忆：存储在对话状态对象中。

长期记忆：存储MongoDB或MySQL或向量存储。

- 短期记忆：保存当前对话窗口和最近几轮上下文，解决代词指代、条件延续和当前任务连续性
- 长期记忆：保存用户偏好、历史事实、长期画像和可复用知识，支持跨会话复用

#### 3.4.2 LangChain 中常见记忆类型有哪些

- ConversationBufferMemory：保存完整对话历史，简单直接，token 消耗高
- ConversationBufferWindowMemory：只保留最近 N 轮对话，适合控制上下文长度
- ConversationSummaryMemory：把历史对话压缩成摘要，适合长对话
- VectorStoreRetrieverMemory：把历史内容向量化，需要时按语义召回
- ConversationKnowledgeGraphMemory：抽取实体和关系，适合需要实体关系追踪的复杂对话

**选择方式**

- 短对话用 BufferMemory
- 多轮任务用 WindowMemory
- 长对话用 SummaryMemory
- 历史跨度大、需要按需召回用 VectorStoreRetrieverMemory 向量存储
- 需要关系推理和矛盾检测用 KnowledgeGraphMemory 图谱记忆（不推荐）

#### 3.4.3 token优化怎么做

- 去除寒暄、重复内容和无效确认。通过改写问题完成。
- 控制获取历史对话数量，长期记忆通过向量总结，并向量召回。
- 优化提示词模板，减少无用冗余的词句。
- 在保证召回率的情况下优化topk测率 （风险）
- 利用FAQ和缓存 减少调用llm的次数

#### 3.4.4 提示词如何管理和热更新

- 提示词放在变量或者缓存中，如果不再则从配置中读取。
- 通过页面控制台更新维护提示词
- 一旦更新数据库中的提示词，再失效缓存。

#### 3.4.5 怎么避免幻觉、复读机和格式不稳定

**幻觉**

根据可能出现的原因进行排查·

证据没有召回：检查 RAG 流程，排查证据丢失节点。

证据提供太多稀释真相：优化切片保留长度和个数。

提示词约束力不足。

模型能力不足。

**复读机**

模型能力有关，现在的模型出现概率不高，如果小模型出现频繁，可以增加重复词检测，即使终止。

**格式不稳定**

利用官方模型的 JSON 格式选项。

增加提示词约束，给出明确示例。

可以考虑增加结果的 JSON 校验，如果格式有问题退回重试。

### 3.5 多智能体协作与状态管理

#### 3.5.1 什么是多智能体，什么场景下需要多智能体

多智能体是把复杂任务拆给多个角色化 Agent 协同完成。每个 Agent 负责自己擅长的一段，比如规划、检索、执行、审核、总结。

适合多智能体的场景：

- 职责不同：提示词定位不同
- 技能不同：各自的工具集
- 能力不同：需要不同能力级别的模型
- 进程不同：需要并行处理。

#### 3.5.2 多智能体之间怎么通信，消息里通常包含什么

多智能体通信是在 Agent 之间传递结构化上下文。

常见消息字段：

- 当前任务目标
- 上游结论
- 关键中间结果
- 任务状态
- 置信度
- 下一步要求
- 错误信息
- 输出 schema

#### 3.5.3 多智能体如何做任务规划、协调和编排

生产中常见的是“主控 + 流水线”，因为边界清晰，监控和调试更稳定。

主 Agent 通常负责理解目标、拆解任务、选择子 Agent、确定执行顺序、汇总结果和控制全局状态。子 Agent 负责执行明确范围内的专业任务。

#### 3.5.4 多智能体和并发怎么考虑

拆分多线程，也可以做多进程。

状态隔离，不能出现并发写入同一状态的问题。

超时等待处理，不能永久等待。

结果汇总合并。

#### 3.5.5 多Agent如何做全局状态管理

核心共享状态，推荐交给主Agent或者某个专职Agent管理。其他子Agent只维护自己部分的状态。

#### 3.5.6 子Agent故障如何隔离和降级

每个子Agent 应设置超时、重试、异常捕获和独立日志，失败不应阻断整个系统。

降级方式包括：

- 使用备用模型（如果调用模型超时）
- 简化工具链（绕过有问题的工具）
- 跳过非关键子任务
主 Agent 需要在全局状态中记录失败原因和降级结果。

#### 3.5.7 多Agent系统如何监测和打破死循环

最大轮数、最大工具调用数。

增加退出策略

### 3.6 文档解析与知识库建设

#### 3.6.1 PDF文档怎么用MinerU解析

MinerU可以本地部署，调用它的API，就可以将 PDF转为MD，文档中的图片也能提取出来。

MinerU底层混合了OCR技术和VLM进行结合，OCR用于提取文字，VLM用于识别版面结构和元素。

#### 3.6.2 文本为什么需要分块，Chunk 怎么设计

**为什么**

因为大模型的窗口有限，不能可能把全部知识库都交给大模型，让大模型去找。

而且太多的信息会稀释关键信息。

所以把知识切碎，然后从中找到关键的碎片交给大模型，来加工总结。

**怎么设计**

先按段落切。

粒度控制，要考虑 reranker 的敏感长度，要考虑跨分片语义是否会丢失，最终要通过 RAGAS 评分进行微调。太长再按句子切，太短做合并。

每个切片要携带元数据和业务标签。

表格内容要做线性化处理。

#### 3.6.3 常用向量数据库有哪些，怎么选

常用向量数据库和检索组件包括 Milvus、PGVector、Elasticsearch、Weaviate、Pinecone 和 Faiss。

- Milvus：适合大规模向量检索和企业级 RAG，实现了存算分离，分布式部署
- Qdrant: 适合中小型项目单点部署。
- Pinecode: 云服务，省心，不需要运维，对数据的安全不敏感可以考虑。

### 3.7 检索、召回与重排

#### 3.7.1 什么是向量，维度和相似度怎么理解

- 向量：把一段文字变成一串数字，相当于文字的“语义坐标”。意思越接近，坐标越接近。
- 维度：这串数字的长度。例如 768 维，就是用 768 个数字描述语义特征。维度越高，表达通常越细致，但计算和存储成本也越高。
- 相似度：衡量两个向量有多接近。分数越高，表示两段文字的含义越相似。

### 3.8 评测与数据闭环

#### 3.8.1 自动化评估怎么做，准确率怎么计算

准备问题集。

基于 RAGAS 编写评估程序。

运行评估程序，观察指标。

找到 bad case 进行分析优化。

再次评估。

准确率 = 上下文中与期望答案相关的条数 / 总上下文条数

召回率 = 期望答案且被上下文覆盖到的事实点个数 / 期望答案的事实点个数

#### 3.8.2 测试集怎么来

真实历史对话记录。

专业业务人员编写。

AI 生成可用于自测。

#### 3.8.3 bad case 怎么收集、分析和优化

**线上环境**

- 收集通过用户交互动作：AI拒答，点击无帮助，转人工
- 模拟重跑问题，分析召回情况，根据日志追查流程，确定问题，进行修改。

**测试环境**

- 做RAGAS 测试根据评分，比如正确性、召回率低的评分作为bad case。
- 根据评分分析可能原因，追查各个环节的日志，确定问题，进行修改。

#### 3.8.4 RAGAS是什么，RAG 评估指标有哪些

RAGAS是用于评估RAG系统的开源评估框架，重点评估检索质量、生成质量以及答案和上下文的一致性。

**常见指标**

- Context Recall：标准相关内容是否被召回
- Context Precision：召回内容中有多少是真正相关的
- Answer Relevance：生成与用户问题的相关程度
- Faithfulness：答案是否忠实于给定上下文
- Answer Relevance：答案是否回答用户问题
RAG评估要同时看检索、重排和生成。只看最终回答准确率，定位不了是召回问题、排序问题还是生成问题。

## 4. OpenClaw & Hermes & Loop Engineering

### 4.1 Loop Engineering工程和Hermes的关系是什么

**Loop 工程：把智能体执行任务设计成持续闭环**

- 输入目标
- 规划任务
- 调用工具
- 观察结果
- 校验输出
- 沉淀记忆或技能
- 进入下一轮优化
Hermes这类 Agent 框架强调任务执行后的记忆沉淀、技能复用和反馈闭环，属于 Loop 工程的一种落地形态。

**OpenClaw 和 Hermes 的关注点**

- OpenClaw：更偏智能体编排、任务入口、工具生态和人工控制
- Hermes：更偏长期记忆、执行反馈、技能沉淀和闭环学习
- Loop工程：关注整个“执行、反馈、沉淀、复用”的工程闭环

**落地时要看四个能力**

- 状态是否可持久化
- 工具调用是否可观测
- 错误是否能进入反馈闭环
- 经验是否能沉淀为规则、记忆或 Skill

### 4.2 怎么理解 Claude Code Hooks 和 Software Development Vibe

Claude Code Hooks 是 Claude Code 生命周期里的自动化机制，可以在特定事件发生时执行脚本、HTTP 调用或模型判断。

**典型用途**

- PreToolUse：工具执行前检查权限、阻止危险命令
- PostToolUse：工具执行后自动格式化、跑测试、记录日志
- Notification：需要用户输入时发送提醒
- SessionStart：会话开始时注入项目上下文
- Stop：任务结束时生成报告、更新记录
Hooks 的价值是把工程规则变成稳定执行的自动动作，减少只依赖模型自觉执行规则的问题。

Software Development Vibe 指的是 AI 参与开发时的整体协作方式，包括需求描述、上下文组织、任务拆解、代码生成、测试验证、代码审查和持续迭代。

**两者关系**

- Vibe Coding 更偏自然语言驱动开发和快速探索
- Software Development Vibe 更偏完整软件工程协作流程
- Hooks 是把这种流程工程化、自动化和可控化的机制
成熟的 AI 开发流程通常是“清晰需求 + 足够上下文 + 自动校验 + Hooks 控制 + 人工审核”组合使用。

### 4.3 Harness

#### 4.3.1 什么是 Harness 工程

Harness 工程是围绕智能体或 AI 编程工具搭建的一套“约束、上下文、工具、反馈和评测环境”。它关注模型之外的工程控制层，让智能体在明确边界内完成任务。

> [!note] Harness 五大组成
> - **上下文**：需求文档、架构说明、接口规范、代码规范、业务规则
> - **工具**：测试命令、格式化命令、代码扫描、日志查询、检索工具、MCP 工具
> - **约束**：权限控制、禁止危险操作、输出格式要求、代码边界
> - **反馈**：单元测试、集成测试、lint、类型检查、评测集、人工审核
> - **闭环**：失败案例沉淀成规则、脚本、测试或新的文档

#### 4.3.2 Harness 和 RDD、DDD、TDD 的关系是什么

RDD、DDD、TDD 都可以放进 Harness 里，作为智能体执行任务时的输入和反馈。

- RDD：需求或文档驱动开发，先把目标、边界、验收标准写清楚
- DDD：领域驱动设计，用领域模型、实体、聚合、服务边界约束系统结构
- TDD：测试驱动开发，用测试定义功能行为和验收条件
- Harness：把需求、领域模型、测试、规范、工具和反馈机制组合成智能体可用的工作环境
在项目里，RDD 提供任务目标，DDD 提供业务边界，TDD 提供可验证反馈，Harness 把这些内容组织成智能体能执行、能校验、能回滚的工程流程。

#### 4.3.3 Harness 工程怎么用，应用中靠谱吗

**Harness 的使用方式**

- 给智能体提供项目说明、目录结构、接口文档和业务规则
- 用测试、lint、类型检查、静态扫描约束输出质量
- 用 hooks 或脚本在关键节点自动执行校验
- 对高风险操作加入审批、白名单和回滚机制
- 对失败案例沉淀规则、测试用例和补充文档
Harness 工程适合多人协作、长期维护、质量要求高的项目。它能降低 AI 输出的不确定性，提高代码、流程和业务结果的可控性。

**应用中的边界**

> [!warning] Harness 应用边界
> - 需求模糊时，Harness 只能约束执行，不能替代需求澄清
> - 测试覆盖不足时，反馈信号会不完整
> - 业务规则没有文档化时，智能体仍然容易误判
> - 高风险场景需要人工审核和权限控制

#### 4.3.4 如果用 Harness 工程重构 AI 客服，哪些地方能做得更好

AI 客服适合用 Harness 工程做重构，因为它涉及知识检索、工具调用、权限控制、回复质量、人工兜底和持续评测。

**重构方向**

- 场景与规则：沉淀客服场景、意图分类、话术边界、禁答规则、转人工规则
- 知识库治理：规范文档导入、chunk 切分、召回评测、来源引用和知识更新流程
- 工具接入：封装订单查询、退款查询、物流查询、工单创建等工具
- 安全控制：敏感信息脱敏、危险操作审批、退款等高风险动作拦截
- 质量评测：建立 FAQ 测试集、bad case 集、幻觉检测、转人工率和满意度指标
- 运行观测：记录意图识别、检索结果、工具调用、模型输入输出和耗时

**重构后的 AI 客服流程**

- 用户输入进入意图识别
- 根据意图选择知识库、工具或固定流程
- 检索或工具调用后做结果校验
- 生成回复时引用来源并遵守话术边界
- 低置信度、高风险或多次失败时转人工
- bad case 回流到测试集、规则和知识库
这种方式能让 AI 客服从“能回答”提升到“可观测、可评测、可控制、可持续优化”。

## 5. AI Coding / Vibe Coding

### 5.1 AI Coding和Vibe Coding是什么，常用工具有哪些

AI Coding是把 AI 编码工具用于需求分析、代码生成、重构、测试、排错和文档编写。

Vibe Coding更偏自然语言驱动开发，通过描述目标、约束和反馈，让 AI 快速生成方案和代码，再由开发者验证和修正。

常用工具：

- Claude Code
- Cursor
- Codex
- GitHub Copilot
- 通义灵码
- CodeGeeX
- Trae
- Continue
工具选择看代码理解能力、上下文窗口、代理执行能力、IDE 集成、成本和团队使用习惯。

### 5.2 如何用AI从模糊需求落地到具体功能

流程：

- 把模糊需求整理成目标、边界、输入输出和验收标准
- 让 AI 帮助拆分模块、接口、数据结构和流程
- 先生成技术方案和任务清单
- 人工确认关键设计和风险点
- 分步骤让 AI 生成代码
- 每一步都运行测试、lint 和本地验证
- 对生成代码做人工 review
- 补充异常处理、日志、权限和边界条件
- 生成接口文档和使用说明
AI 适合提高方案探索和代码初稿效率，最终质量要靠测试、评审和真实运行结果保证。

### 5.3 什么时候会让 Claude Code 开启代理跑任务

**适合开启代理任务的场景**

- 需要跨多个文件修改
- 需要先读代码再制定实现方案
- 需要自动运行测试和修复问题
- 需要重构、补测试、批量改名、整理文档
- 任务目标明确，验收标准清楚

**不适合直接交给代理的场景**

- 需求还没确认
- 涉及高风险生产操作
- 涉及敏感数据
- 需要产品或业务决策
- 缺少测试和验证条件
代理执行时要限制范围，要求它先理解代码结构，再小步修改和验证。

### 5.4 如何保证 AI 生成代码的稳定性

> [!important] 核心结论
> 稳定性来自约束、测试和审查。

做法：

- 提供清晰需求、代码上下文和已有规范
- 要求复用项目现有公共类、工具函数和风格
- 让 AI 小步修改，避免一次生成过多代码
- 生成后运行单元测试、集成测试、lint 和类型检查
- 人工 review 核心逻辑、异常处理和安全问题
- 对关键路径补充测试用例
- 检查日志、监控、事务、幂等和权限
- 让 AI 解释关键实现，再对照源码验证
> [!tip] 面试一句话
> AI 生成代码只能作为初稿，合并前必须经过工程化验证。

### 5.5 怎么判断 AI 生成的代码是否瞎写

判断方式：

> [!important] 判断 AI 代码是否瞎写的 9 个标准
> - 是否能编译或运行
> - 是否符合需求和边界条件
> - 是否调用了真实存在的类、方法和字段
> - 是否符合项目目录结构和代码风格
> - 是否有异常处理和日志
> - 是否有测试覆盖
> - 是否引入安全问题
> - 是否有重复造轮子
> - 是否和现有业务规则冲突
发现可疑代码时，要回到源码、接口文档、测试结果和运行日志验证，不能只看 AI 的解释。

### 5.6 AI 没有按公共类或公共方法调用怎么办

处理方式：

- 明确告诉 AI 先检索项目已有实现
- 在提示里指定必须复用的类、方法和模块
- 提供相关文件路径和接口签名
- 让 AI 先输出调用方案，再写代码
- 生成后检查是否重复造轮子
- 把错误示例反馈给 AI 重新修改
- 把公共能力整理进项目文档或规则文件
团队使用时，把常用公共类、异常规范、返回格式、日志规范写进项目说明，让 AI 每次任务都能读取。

### 5.7 AI Coding 出现幻觉怎么处理

**常见幻觉**

- 编造不存在的 API
- 编造依赖库方法
- 错用业务字段
- 忽略权限和异常
- 生成看似合理但不可运行的代码

**处理方式**

- 要求 AI 引用真实文件和方法
- 让 AI 先搜索代码再修改
- 运行测试和静态检查
- 缩小任务范围
- 给出报错信息让 AI 修复
- 对关键逻辑人工复核
- 把幻觉案例沉淀为规则或测试

### 5.8 AI 生成代码后开发者还要做什么

开发者要负责最终质量。

后续工作：

- 读懂生成代码
- 检查业务逻辑
- 补充异常处理
- 补充测试用例
- 运行测试和本地验证
- 做性能和安全检查
- 对关键逻辑做 code review
- 调整命名、结构和风格
- 提交前确认没有无关改动
AI 负责提升初稿速度，开发者负责判断、取舍、验证和交付。

### 5.9 为什么选择 Claude Code、Cursor 或 Codex

**工具选择要看场景**

- Claude Code：适合命令行代理、跨文件修改、长上下文理解、自动执行任务
- Cursor：适合 IDE 内联编辑、代码补全、快速改局部文件
- Codex：适合代码库任务、补丁生成、测试驱动修复、协作式开发
- Copilot：适合日常补全和小段代码生成

**选择标准**

- 是否能理解整个仓库
- 是否能安全执行命令
- 是否方便 review diff
- 是否支持团队工作流
- 成本是否可控
- 输出是否稳定

### 5.10 Claude Code 的工作原理是什么

Claude Code 是面向代码任务的代理式工具。它通过读取项目文件、理解上下文、规划任务、编辑代码、执行命令和根据结果继续修正来完成开发任务。

基本流程：

- 读取用户需求
- 扫描项目结构和相关文件
- 制定修改计划
- 编辑代码
- 运行测试或命令
- 根据报错继续修复
- 输出变更说明
关键能力是工具调用和上下文管理。它会结合本地仓库、命令输出和测试结果完成开发闭环。

### 5.11 AI Coding的使用程度、费用和价值怎么评估

使用程度按任务占比说明，比如需求分析、代码初稿、重构、测试、排错、文档各占多少。

费用要按真实情况说明，包括订阅费、API token、公司额度或个人开销。

价值评估：

- 节省开发时间
- 提升方案探索速度
- 减少重复劳动
- 提高测试和文档覆盖
- 加快排错和重构
- 降低新人理解代码成本
成本是否值得，要看节省的人力时间、交付速度、代码质量和返工率。

### 5.12 怎么查看 token 消耗和历史会话

不同工具查看方式不同。

常见方式：

- 在工具控制台查看用量统计
- 在 API 平台查看 token、请求数和费用
- 在本地 CLI 查看历史会话或日志
- 在团队管理后台查看成员用量
- 对重要任务记录输入、输出、模型和耗时
团队使用时要设置预算、额度、模型选择规则和高成本任务审批。
