## 1. 知识库项目

### 1.1 项目架构图

### 1.2 项目串讲稿

#### 1.2.1 项目介绍

掌柜智库这个项目主要做的是商品资料知识库问答，面向客服、运营和业务人员，解决他们查询产品手册、说明书、维修资料时效率低、资料分散、人工翻文档成本高的问题。系统会把 PDF、Markdown、图片、表格这些非结构化资料统一导入知识库，用户后续直接用自然语言提问，就能从知识库里召回相关资料，并生成有依据的答案。

我在项目里主要负责后端 RAG 核心链路，可以分成存储和查询两部分来讲。存储侧负责把原始文档解析成 Markdown，处理图片和表格，再做文档切片、商品名识别、BGE-M3 向量化，最后写入 Milvus和 MinIO。查询层负责对用户问题做商品名确认和问题改写，然后走向量检索、HyDE 检索和 MCP 网络检索，经过 RRF 融合、Rerank 精排和断崖截断后，交给大模型生成答案，并通过 SSE 流式返回给前端。

#### 1.2.2 存储流程

**整体流程**

```text
用户上传 PDF/Word/Markdown
  ↓
FastAPI 创建 task_id，保存原文件到本地 + MinIO
  ↓
LangGraph 导入图启动
  ↓
PDF → MinerU 解析为 Markdown；Markdown → 直接读取
  ↓
图片处理：提取上下文 → VLM 生成摘要 → 上传 MinIO → 替换链接
  ↓
文档切分：按标题层级切分 → 表格线性化 → 长段递归切 → 短内容合并
  ↓
商品名识别：LLM 提取 item_name → BGE-M3 向量化 → 写入商品名集合
  ↓
切片向量化：item_name + content → BGE-M3 生成 dense/sparse
  ↓
Milvus 入库：创建集合 + 索引 → 批量插入
```

掌柜智库的存储流程可以理解为”文档导入、内容结构化、向量入库”三步。用户在前端选择 PDF 、Word或 Markdown 文档后，FastAPI 导入接口创建 task_id，ImportFileService 先把原文件保存到本地任务目录，再把原文件归档到 MinIO，TaskService 负责记录上传、处理中、完成、失败等任务状态，前端通过任务状态看到导入进度。

导入任务启动后，后端把 task_id、file_dir、import_file_path 放进 LangGraph 的 ImportGraphState，进入导入图。入口节点判断文档类型，PDF 文档先经过 MinerU 解析成 Markdown，Markdown 文档直接进入读取链路。图片处理节点读取 Markdown 和 images 目录，提取图片所在段落的上下文，调用 VLM 生成图片摘要，把图片上传到 MinIO，并把 Markdown 中的本地图片链接替换成远程图片 URL 和图片摘要。

文档内容统一成 Markdown 后，文档切分节点DocumentSplitNode 按标题层级切分文档，保留 title、parent_title、file_title、content 等元数据。表格内容会先做线性化处理，长段落会按最大长度继续切分，短内容会按相邻上下文合并，最终形成适合检索的 chunk。商品名识别节点会取前几个 chunk 和文件标题调用 LLM 提取 item_name，再用 BGE-M3 生成商品名的稠密向量和稀疏向量，保存到商品名向量集合，同时将提起的item_name回填到chunks中。

切片向量化节点会把 item_name 和 chunk 内容拼接成 embedding 内容，按 batch 调用 BGE-M3 生成 dense_vector 和 sparse_vector。Milvus 入库节点负责创建 chunks 集合、稠密向量索引、稀疏向量索引和标量字段，把 chunk 批量插入 Milvus

> [!important] 核心结论
> 这一条链路结束后，系统里会形成三类核心资产：MinIO 中的原文件和图片对象，Milvus 中的商品名向量、切片向量。后续查询链路就是围绕这些资产做召回、融合和生成。

#### 1.2.3 查询流程

**整体流程**

```text
用户输入问题 → QueryService 生成 task_id + session_id
  ↓
商品名确认：LLM 抽取 item_names + rewritten_query → BGE-M3 向量对齐
  ↓
确认成功 → 进入多路召回；失败 → 返回确认提示
  ↓
并行多路召回：
  ├─ 普通向量检索（rewritten_query → dense/sparse → Milvus 标量过滤）
  ├─ HyDE 检索（LLM 生成假设文档 → 向量化检索）
  └─ MCP 网络检索（bailian_web_search）
  ↓
RRF 融合：本地两路按 chunk_id 去重融合，k=60
  ↓
Rerank 精排：本地 + MCP 结果 → BGE-Reranker 交叉编码 → 断崖截断
  ↓
答案生成：reranked_docs + 历史 + 商品名 + 问题 → LLM 生成 → SSE 流式返回
  ↓
保存会话历史到 MongoDB
```

掌柜智库的查询流程可以理解为”商品名确认、多路召回、融合重排、答案生成”四步。用户在前端输入问题后，QueryService 生成 task_id 和 session_id；如果是流式查询，就为 task_id 创建 SSE 队列。后端把 original_query、session_id、task_id、is_stream 放进 QueryGraphState，进入 LangGraph 查询图。

查询图的入口是商品名确认节点。这个节点先从 MongoDB 读取最近的历史对话，把历史和当前问题一起交给 LLM，抽取 item_names 并生成 rewritten_query。抽到商品名后，系统用 BGE-M3 生成商品名向量，再到 Milvus 商品名集合中做混合向量对齐。确认成功时，item_names 和 rewritten_query 写入 state；只找到候选项时，直接返回“您是在询问哪款产品”的确认提示；完全识别不到商品时，返回补充商品名称的提示。多轮对话里，如果前面历史消息缺失 item_names，确认成功后会回填历史记录。

商品名确认后，查询图进入 multi_search 并行召回。第一路是普通向量检索，使用 rewritten_query 生成稠密向量和稀疏向量，在 Milvus chunks 集合里按 item_name 标量过滤检索。第二路是 HyDE 检索，先让 LLM 根据问题生成一段假设性技术文档，再把原问题和假设文档一起向量化检索。第三路是 MCP 网络检索，通过 MCP 客户端调用 bailian_web_search，拿到外部网页标题、摘要和 URL。

多路结果返回后，本地两路结果先进入 RRF 融合节点。RRF 按 chunk_id 对向量检索、HyDE 检索的结果去重融合，向量和 HyDE 权重是 1.0，k 值是 60，最终保留靠前的候选 chunk。Rerank 节点再把 RRF 后的本地 chunk 和 MCP 网页结果合并，构造成 query-doc pair，交给 BGE-Reranker 做交叉编码精排，并通过断崖检测动态截断候选结果。

答案生成节点会把 reranked_docs、历史对话、商品名和用户问题组装成最终 prompt，调用 LLM 生成答案。非流式模式下，答案写入任务结果；流式模式下，LLM 每生成一段内容就通过 SSE 推送 delta 事件，结束时推送 final 事件。最后系统把用户问题和助手答案写入 MongoDB，形成可追溯的会话历史。

#### 1.2.4 项目整体总结

掌柜智库是一个面向商品资料的 RAG 知识库系统，主要解决客服、运营和业务人员查询商品说明书、操作手册、维修资料、FAQ 时效率低、信息分散、人工翻文档成本高的问题。用户可以直接用自然语言提问，系统会从知识库里检索相关内容，再结合大模型生成答案。

我在这个项目里主要负责后端 RAG 核心链路，包括文档导入、文档切片、向量化入库、商品名确认、多路召回、RRF 融合、Rerank 精排、答案生成和 SSE 流式返回。整体架构上，Web 层用 FastAPI，对导入和查询分别封装接口；流程编排用 LangGraph，把导入流程和查询流程拆成多个可追踪的节点；存储层用 MinIO 保存原文件和图片，用 Milvus 保存商品名向量、切片向量和实体名向量，用 MongoDB 保存多轮会话历史。

从存储流程看，用户上传 PDF 或 Markdown 后，系统会生成导入任务，先把原文件保存到本地和 MinIO。PDF 会通过 MinerU 转成 Markdown，图片会提取上下文、生成摘要并上传到 MinIO，表格会做文本线性化。之后系统按标题层级和长度阈值进行文档切片，再用 LLM 提取商品名，用 BGE-M3 生成稠密向量和稀疏向量，最终把切片写入 Milvus。这样导入完成后，系统里既有向量索引，也有原文件和图片资源。

从查询流程看，用户提问后，系统先读取历史会话，用 LLM 做商品名抽取和问题改写，再通过商品名向量库做商品对齐。如果商品不明确，会先返回候选商品让用户确认；如果商品明确，就进入多路召回。召回链路包括普通向量检索、HyDE 检索和 MCP 网络检索。本地两路结果先通过 RRF 做融合去重，网络结果和本地结果再一起进入 BGE-Reranker 精排，最后通过断崖检测动态截断候选上下文，把最终上下文、历史对话、图谱关系和用户问题组装成 prompt 交给 LLM 生成答案。流式模式下，答案会通过 SSE 一边生成一边推送给前端。

这个项目的亮点是把一个普通的文档问答系统做成了比较完整的工程化 RAG 系统。导入侧不光实现了文本入库，也处理了 PDF、图片、表格、商品名、向量和图谱；查询侧不只有单路向量检索，也通过商品确认、多路召回、RRF 融合、Rerank 精排和流式生成提升答案质量和用户体验。整体上，它把非结构化商品资料沉淀成可检索、可追踪、可复用的知识库，能支撑业务人员更快地查资料和回答用户问题。

### 1.4 项目背景与使用情况

#### 1.4.1 请简单介绍一下这个 RAG 知识库项目。

这是一个面向企业产品文档的智能知识库系统，核心能力是文档自动导入和智能问答。导入侧把 PDF、Markdown 等文档解析成 Markdown，处理图片和表格，再切片、识别商品名、生成 BGE-M3 混合向量，写入 Milvus。查询侧先确认商品名，再并行做向量检索、HyDE 检索和 MCP 网络搜索，之后用 RRF 融合、Rerank 精排，最后由大模型基于检索上下文生成答案。后端使用 FastAPI + LangGraph，存储包括 Milvus、MongoDB、MinIO，前端支持文件导入进度和 SSE 流式问答。

#### 1.4.2 RAG 知识库项目解决什么问题？整体设计难点是什么？

这个项目解决的是企业产品资料多、格式复杂、人工查找效率低、客服回答不稳定的问题。系统把非结构化文档转成可检索知识，并通过 RAG 方式让回答基于企业自己的资料。> [!important] 设计难点
> 设计难点主要有四类：复杂 PDF 的解析和图片语义补全、文档切片粒度控制、多路召回结果融合、LLM 回答准确性控制。工程上还要处理异步导入、任务进度、流式输出、向量库的一致性。

#### 1.4.3 RAG 知识库的用户量大概是多少？

项目按独立 AI 服务来规划，面向电商业务侧的客服和运营场景。压测和资源估算按注册用户 20 到 80 万、日活 2 到 3 万来估算，AI 客服触达 25% 到 40%，日咨询约 4000 到 7000 次，每次平均 8 轮。换算成问答调用大约每天 3.2 万到 5.6 万次，集中在 8 小时内平均 QPS 约 1 到 2，生产预留 3 到 5 倍峰值，按 5 到 10 QPS 准备资源。

#### 1.4.4 RAG项目做完后是否真正有人使用？使用效果怎么样？

有使用

效果上，常见产品操作、参数说明、故障排查类问题能直接从知识库召回资料并生成答案，减少人工翻文档时间。

上线后，重点观察召回命中率、答案正确率、用户追问率、人工转接率和 bad case 数量。项目上线后还会持续通过问题集评测和 bad case 回流优化切片、召回、重排和提示词。

### 1.5 数据来源与知识整理

#### 1.5.1 QA 知识库里的问题和答案由谁提供？

本项目是文档型知识库，不是以问题和答案的方式存储，而是把现有的手册文档，以切片的形式保存在知识库里。

#### 1.5.2 文档导入是怎么做的？是人工整理后导入，还是自动化导入？

有人工导入页面，提供批量导入功能。

#### 1.5.3 文档是否做去重？如何保证文档唯一性？

有去重：根据设备名称进行幂等性处理（删除原有的，重新导入）。

进阶：根据文件的sha码进行识别，提醒导入用户已有重复的文档。

未来：不覆盖，做版本管理。

#### 1.5.4 新增文档或原文档更新后，切分和索引如何更新？

- 目前做的是幂等性更新：

- “更新文档时，当前项目按商品名清理旧向量”

- “然后重新切片、向量化、入 Milvus”

- 更好的处理是：

先导入新的内容，标识为“未生效”，但不删除旧的，一直到新的内容完全导入完成后。标识新内容“有效”，然后给旧切片标识“作废”。主要避免在导入一半的过程中有人临时查询。

#### 1.5.5 Milvus 和 ES 分别存储了多少数据？业务量多大时选择 Milvus 而非直接用 ES？

数据量本身不大，主要是看重其业务功能，Milvus主要偏向向量匹配，语义匹配。ES是 全文匹配更精确

### 1.6 文档解析与内容处理

#### 1.6.1 PDF 是如何解析和提取内容的？

- PDF 不直接检索，先用 MinerU 转成 Markdown。

- 转完以后，文本、标题、表格、图片引用就比较结构化。

- 后续所有格式都统一走 Markdown 图片处理和切片链路。

- MinerU 可以理解成复杂 PDF 到 Markdown 的解析工具。

- 它解决 PDF 文本顺序乱、表格难抽、图片引用难保留的问题。

- 有了 Markdown 结构，后面的切片和检索就好处理了。

#### 1.6.2 MinerU 和 VLM 图片识别有什么区别？

> [!important] MinerU vs VLM 职责区分
> - MinerU 负责把 PDF 拆出来转成 md，其中图片的部分只做引用不做解读。
> - VLM 负责看懂图片，生成图片的概要，用户提问的时候引用图片，和回答问题。

#### 1.6.3 你们处理的文本复杂情况大概是什么样的？

主要是产品说明手册，长文档、有标题段落、有图片、有参数表格。

#### 1.6.4 表格内容是怎么提取和处理的？

- mineru会把pdf中的表格转为Html `&lt;table&gt;`

- 为了让LLM更好识别，在切片时会把文本中的Html `&lt;table&gt;` 格式利用行列交叉合并进行线性化处理，把表格变为自然语言

#### 1.6.5 图片内容是怎么处理的？

- 系统会扫描 Markdown 里的图片引用。

- 拿图片前后的标题、上文、下文作为上下文。

- 调用 VLM 生成图片标题或摘要，再上传 MinIO。

- 后面图片摘要会作为文本参与检索，答案里如果带图片 URL，前端也能展示。

#### 1.6.6 你们处理的文件大概有多长？

项目主要处理产品手册和说明书，常见是几十页到上百页，也会遇到两三百页的长 PDF。长文档会先按标题层级和内容长度切片，再通过检索找相关片段。

#### 1.6.7 如果要从两三百页的 PPT/PDF 里精准提取关键信息，会怎么做？

- 先结构化，把 PDF 变成带标题、表格、图片引用的 Markdown。

- 再切片，保留标题、父标题、商品名这些元数据。

- 查询时用商品过滤、多路召回、RRF 和 Rerank 找关键片段。

- 特别重要的故障码、参数表、警告，可以额外结构化抽取为图谱，这是优化方向。

#### 1.6.8 什么是混合检索，BM25 和向量检索权重怎么定

目前设置的两种索引的权重是各自一半。

确定方法是准备测试集，包含常规问题和期望匹配的切片。

然后按照多种权重进行测试，找到分值更高的。

#### 1.6.9 查询改写是什么

查询改写是把用户原始问题转换成更适合检索的问题表达。同时可以把上几次的对话信息，提炼到本次问题中。

常见方式：

- 纠错：修正错别字和口语表达
- 标准化：把简称、别名转成标准术语
- 补充主语：通过追问获得的主语与原始问题进行合并
- 拆解：把复杂问题拆成多个子问题

#### 1.6.10 HyDE 是什么，偏了怎么处理

HyDE是Hypothetical Document Embeddings，假设性文档检索。它先让模型根据用户问题生成一段可能的答案或假设文档，再用这段假设文档做向量检索。

- 通过HyDE的提示限制它必须围绕原问题生成假设性答案
- HyDE只是一路，还会和原问题合并
- 后面还有rerank节点进行重排序

#### 1.6.11 为什么需要多路查询和RRF

主要的目的就是为了让检索能够从不同的角度进行召回，然后再通过 rrf的评分从多路搜索结果获得统一的排序。

#### 1.6.12 RRF和rerank是什么，重排怎么做

RRF是Reciprocal Rank Fusion，倒数排名融合。它用文档在多路召回结果里的排名计算融合分数。

rank_i(d) 是文档在第 i 路检索结果中的排名，k 常用 60。排名越靠前，融合分越高。

rerank 是精排。它把 query 和候选文档成对输入 rerank 模型，模型输出相关性分数，再按分数重新排序。

#### 1.6.13 检索重排后返回Top多少，怎么减少中间信息丢失

TopK的参数包括最多条数，最少条数，断层相对差值，断层相对比值。

相关参数一开始都是用经验值，然后根据RAGAS评估后，再进行微调。

### 1.7 文档切片与上下文完整性

#### 1.7.1 文档切片是怎么做的？

- 先按 Markdown 1-6 级标题切。

- 太长的章节继续递归切，太短的同父标题下合并。

- 每个 chunk 会保留标题、父标题、文件标题、商品名。

- 向量化时会拼 `item_name + content`，让商品相关性更强。

- 每个切片都有item_name字段用于过滤，避免相似设备混淆

#### 1.7.2 文档切分长度阈值是怎么控制的？

- 项目里会设置最大长度、最小长度和重叠策略。

- 最大长度控制单个 chunk 不要太大，避免检索和 rerank 时关键信息被稀释,目前设置了1200字符，之前设置两千时发现rerank经常忽略关键信息；

- 最小长度控制 chunk 不要太小，避免缺上下文。过长内容递归切分，过短内容向前后合并。所以保留少量句子重叠，目前：300字符，1个overlap_sentences。

#### 1.7.3 如果同一个段落或语义超过最大块长度，检索时如何保证语义完整？

- 当前实现：

- 切分时尽量按标题、段落、句子边界切，避免从句子中间硬切。

- 通过overlap_sentences 增加边界的冗余。

- 进阶方案：

- 文本回填：其次每个切片保留parent_chunk_id。命中子块后回填父章节或相邻块。弊端：回填也可能增加较多的噪音，要结合实际文本内容，目前的手册型文本段落比较清晰，需要保留超大文本完整的语义的场景不多。

- 知识图谱：通过实体关系建立跨切片的语义关联，最终将图谱关系作为补充信息交给大模型最终回答。 弊端是：提取实体关系需要大模型，增加额外的token和时间损耗。

#### 1.7.4 文档切分导致语义丢失时，怎么定位和优化？

- 可以通过RAGAS进行评估，上下文召回率低就是明显的切片丢失。

- 先从 bad case 入手，看原文里是否有答案，再查召回结果中有没有包含关键切片。

- 如果原文有答案但召回没有命中，重点检查embedding、rrf、reranker筛选前后的日志。

优化手段包括：

- 调小 chunk
- 增加 overlap
- 保留更多 RRF 候选
- 提高 rerank TopK
- 增加标题和商品名上下文
优化后用同一批问题集复测 context_recall、context_precision 和 answer_correctness。

#### 1.7.5 PDF、Word、图表、扫描件及低质量文档是如何解析的？是否使用了 MinerU 等工具？图片信息如何进入知识库（如多模态生成 Caption）？

使用了MinerU，图片信息通过VLM识别生成说明文字（Caption）。

#### 1.7.6 如何处理多栏格式、图文错位、左文右图，以及工业文档中“大片图片+简短编号”的情况？如何规定大模型提取信息的顺序？

Mineru你内部有VLM，用于识别版面信息。

#### 1.7.7 文档包含跨页大表格或图片时，切片后检索效果差如何处理？

Mineru支持跨页表格合并，md的html格式的表格会做线性化处理。

图片使用vlm生成了说明文字。

#### 1.7.8 RAG 中的噪声是如何处理的？

在文档导入预处理阶段去除页眉、页脚、乱码和无意义字符。在检索阶段通过设置相似度阈值过滤低分结果，通过重排提升召回结果与Query的相关度。在生成阶段，通过 Prompt 指示模型过滤噪声信息。

#### 1.7.9 数千 Token 的规章制度文档切块后，用户简短提问只能召回局部内容怎么办？如果关键信息分布到多个块中，如何解决召回不全的问题？

上下文被切碎不全可以通过回填的方式，补充上下文。

长距离跨切片，可以考虑用知识图谱提取核心实体关系信息。

#### 1.7.10 拒答的触发条件和实现方式是什么？

Rerank的评分低于0.3时可以详情淘汰上下文，如果上下文都被淘汰可以拒答。

#### 1.7.11 召回的 chunk 超过 ReRanker 上下文窗口怎么处理？如果重排后相关度依然不高怎么处理？

目前的bge-reranker-large的上下文窗口是512 token。 我们每个切片主要也控制在500。

如果相关度依然不高，要查看具体原因，通过HyDE或者知识图谱增加信息匹配的方式。

#### 1.7.12 如果召回率低或大量不相关，从哪些方面排查和优化？

排查路径：

- 排查各路embedding的评分和筛选策略

- rrf的各路权重、平滑系数、筛选策略

- rerank 评分、topk的筛选策略相关参数。

召回率低则放宽筛选门槛，精确率低则收紧筛选门槛

#### 1.7.13 仅依靠相关度排序会导致切片重复、多样性不足，如何解决？

如果出现这种问题，则利用MMR策略进行筛选。

MMR（Maximal Marginal Relevance，最大边际相关性），在根据相关度评分排名时，会对与其他切片相近的切片进行权重惩罚，导致把太过接近的切片删除掉以保留多样性。

#### 1.7.14 向量相似度和语义相近是否等同？原因是什么？

不完全等同。

向量模型会把一篇文章的含义压缩成向量数据，这个过程会丢失大量的含义细节，就像把两副油画变为8位像素图，然后比较这些像素图的相似程度。

#### 1.7.15 RAG 向量化+文档切块的框架有什么问题？有没有更好的方式？

这种方式实现简单，但切块会破坏上下文完整性，导致语义断裂，从而无法建立跨文档实体关系。

可以考虑用回填切片或者知识图谱解决。

### 1.8 检索召回与排序生成

#### 1.8.1 文档检索是什么？整体流程是怎么做的？

- 先商品确认，再多路召回。

- 召回包括向量、HyDE，MCP是可选网络补充。

- 本地结果先进 RRF，之后统一交给 Rerank。

- 最后把截断后的上下文交给 LLM 回答。

#### 1.8.2 dense 和 sparse 为什么都要？

> [!important] dense vs sparse
> dense 擅长语义改写，sparse 擅长型号、参数、接口名和专有名词。企业文档两类问题都有，所以 BGE-M3 的 dense/sparse 混合更稳。

话术：dense only Recall@5 78.4%，dense/sparse 0.8/0.2 到 86.9%，HyDE+RRF 后到 90.8%。

#### 1.8.3 商品名确认机制是怎么做的？

- 先让 LLM 从当前问题和历史对话里抽商品名。

- 再把商品名向量化，到商品名向量集合里做混合检索。

- 高分直接确认，中间分返回候选，低分让用户补充型号。

- 确认后，商品名会作为后续 Milvus 检索过滤条件。

待优化：未来可以对商品名称进行缓存，对问题分词后与缓存进行匹配，如果命中则直接确定，避免经过llm和embedding比较。

#### 1.8.4 多轮对话后才确认商品名，历史记录里的商品名缺失怎么处理？

- 这个问题改写会带上之前用户的对话记录（如果之前的会话有商品名也会附在对话记录中）。

- 然后根据对话让大模型根据本次问题和历史对话提取商品名，并保存在本次会话中。

- 同时也会把商品名称回填之前没有确定商品的对话。

#### 1.8.5 智库中的三路召回分别是什么？各自解决什么问题？

- 本地三路是普通向量检索、HyDE 检索、MCP。

- 普通向量解决常规语义和关键词匹配。

- HyDE 解决用户表达不完整、缺少实体主语的问题。

- MCP 是额外网络补充。

#### 1.8.6 为什么要采用多路召回，不只依赖单纯的向量检索？

- 普通向量检索，就是常规按照问题查询答案的方式进行召回

- HyDE 解决用户表达不完整、缺少实体主语的问题。

- MCP 是额外网络补充。

多路结果再通过 RRF 和 Rerank 统一排序。这样召回更全，最终答案更稳。

#### 1.8.7 多路检索之间是如何协同的？

- LangGraph 里有一个虚拟 `multi_search` 节点，把多路检索并行发出去。

- 每一路只写自己的结果字段。

- join 后本地两路结果进 RRF（无图谱则两路），网络结果在 Rerank 阶段合并。

- 这样既能并行提速，又能统一排序。

#### 1.8.8 HyDE 检索是什么？为什么能提升召回率？

- HyDE 就是先让模型根据问题写一段假想答案或技术文档。

- 用户问题往往很短或缺实体，假想文档更像真实手册里的表达。

- 再拿问题加假想文档去向量检索，召回会更容易命中。

#### 1.8.9 RRF 融合算法是什么？

- 倒数排名融合算法，用来融合多路检索结果。

- 它不依赖不同召回源的原始分数可比性，主要根据每个文档在各路结果中的排名计算综合分。

- 公式是 score(d)=Σ weight_i/(k+rank_i(d))。同一个文档如果在多路召回中都排名靠前。

#### 1.8.10 RRF 的 k 值为什么选 60？

- 60 是 RRF 常用经验值。”

- “k 小，头部排名影响更大；k 大，排名差异更平滑。

- 有需要的化可以通过验证集调参，比如观察不同 k 值下的 context_recall、context_precision 和最终 answer_correctness。

#### 1.8.11 最终检索时，前两路检索通过 RRF 融合，加上 MCP 后走 rerank 重排；这个过程中可以直接用 rerank 模型重排吗？

- “能直接 rerank，但不建议把所有原始召回都丢进去。”

- “RRF 很便宜，先做去重和粗融合。”

- “Rerank 成本高，适合处理压缩后的候选。”

- “网络结果没有本地 chunk_id，所以放到 rerank 阶段统一精排更方便。”。

#### 1.8.12 检索并重排后，返回 Top多少给大模型？

- “当前不是固定 TopK。”

- “RRF 默认先保留 20 条本地候选。”

- “Rerank 后默认最少 6 条、最多 15 条，中间通过断崖检测截断。

#### 1.8.13 什么是断崖检测截断？

断崖检测是一种动态确定保留文档数量的方法。Rerank 后文档按分数从高到低排序。

- 当前默认是绝对差 0.5 或相对差 25%。”

- 这个值目前属于经验配置。

- 更严谨的做法是用验证集看 context_recall 和 context_precision，再调阈值。

#### 1.8.14 断崖检测的阈值是怎么确定的？

阈值来自验证集和 bad case 分析，项目里使用绝对差距 0.5 或相对差距 25% 作为经验阈值。

调阈值时主要观察两类指标：

- 如果截断太激进，会导致 context_recall 下降；

- 如果截断太宽松，会导致 context_precision 下降并增加模型幻觉风险。

最终阈值要结合 rerank 分数分布、文档长度、上下文预算和答案正确率来定。

#### 1.8.15 如果最终 Top 5 都给到大模型，但模型更关注头部和尾部内容，怎么防止中间数据丢失？

可以从排序、提示词、摘要三方面处理。

- 排序上保证 Rerank 分数最高的切片放在前面。

- 提示词要求模型逐条阅读参考资料。

- 长文本材料用大模型提取摘要放在考上的位置，但是有额外消耗。

#### 1.8.16 MCP 网络检索在查询链路里解决什么问题？

补充本地知识库缺失的信息以及实时信息。

### 1.9 模型、指标与评测

#### 1.9.1 智库项目用了哪些模型？分别用在什么节点？

四种模型：

- “文本 LLM 主要用千问flash，用在商品名抽取、问题改写、HyDE、图谱抽取和答案生成。”

- “VLM 用在图片摘要，走兼容 OpenAI/DashScope 的配置。”

- “Embedding 用 BGE-M3，生成 dense 和 sparse。”

- “Rerank 用 BGE reranker 远端 HTTP 服务。”。

#### 1.9.2 VLM 模型和文本大模型为什么没有独立部署？

- 项目初期访问量不算特别高，VLM 和文本大模型调用频率相对可控，使用成熟云端模型服务更稳定，也能减少运维成本。

- 独立部署 VLM 和大语言模型需要较高显存、模型服务治理和推理优化能力，投入更大。

- 项目中优先独立考虑的是 BGE-M3 和 reranker，因为它们在导入和检索中调用频率高，且本地部署成本更可控。

- 后续如果调用量上升，再评估独立部署文本模型或 VLM。

#### 1.9.3 RAG 知识库的召回率大概怎么样？

- 召回率要基于测试问题集评估，不能只凭主观感觉。

- 通过RAGAS评估优化过后能达到93%以上。

- 但是实测上线的问题，存在一些不在知识库的内容，召回率85%。

口径上可以说在核心产品手册类问题上召回效果较稳定，bad case 主要集中在切片过大、表格或图片信息缺失、商品名识别错误、rerank 丢弃关键切片等场景。具体数值要以评估集为准。

#### 1.9.4 智库准确率怎么评测？

先构建测试问题集。

利用RAGAS 框架，其中context_precision分数求平均。

context_precision这个分数就是用reranker后的上下文与参考答案的评分。

- 公式：准确率= sum( precision@k * relevance_k ) /检索的上下文数量
- Precision@K = 前 K 个检索结果中的相关结果占比
这个公式的算法会奖励排名靠前的命中的上下文。

#### 1.9.5 召回率是怎么评测的？

准确率通过ragas 中的context_recall 的评分观察。

context_ recall的用reranker后的上下文与参考答案的评分。

公式：召回率= 上下文支持的参考答案的事实点/ 参考答案的事实点

#### 1.9.6 如何保证 LLM 回答的准确性？

优化检索保证切片被找到、且噪音可控。

优化提示词回答语述。

#### 1.9.7 RAGAS 评估主要观察哪些指标？这些指标高低分别代表什么？

> [!important] RAGAS 五大指标
> - **faithfulness**：看答案是否被上下文支撑，低说明可能幻觉；
> - **answer_relevancy**：看回答是否切题，低说明模型理解或提示词有问题；
> - **context_precision**：看召回上下文是否干净，低说明噪声多；
> - **context_recall**：看证据是否召全，低说明召回链路有问题；
> - **answer_correctness**：看最终答案和标准答案是否一致，是整体效果指标。

#### 1.9.8 测试问题集是怎么来的？

- 开发会根据文档先整理一批自测问题。

- 业务再补高频真实问题。

- 上线后再收集真实用户问题和 bad case。

#### 1.9.9 bad case主要分析什么？分析步骤是什么？

- 先查评分，分情况分析

- 如果是召回率分低，首先检查原文是否有答案

- 然后检查几个会淘汰证据的节点，embedding\rrf\reranker

- 如果是是上下文准确分低，调整topk保留数量

- 如果正确性低其他都高，优先调整提示词，其次更换模型。

#### 1.9.10 项目里有哪些优化案例？

- 切片和重排优化：发现答案在原文后半段但 rerank 不敏感，就调小 chunk、增加 overlap、提高候选保留数量。

- 提示词优化：检索指标不差但答案发散，就要求只基于参考资料回答、控制回答长度、按对象分组输出。

- 脏数据优化：mineru转换pdf过程中有很多设备涉及的特殊符号公式，转换md后，增加规则过滤清洗转换脏数据。

- 性能优化：多用缓存和FAQ，减少llm的使用。

#### 1.9.11 是否有审计机制记录对话数据、模型输入输出及接口耗时？系统观测是如何实现的？

通常使用 LangSmith、Langfuse 或自研日志系统记录全链路 Trace。记录内容包括 User Query、检索到的 Chunks、ReRank 分数、Prompt、LLM 输出及耗时。

通过监控面板（Grafana）观测 QPS、P99 延迟、拒答率和用户负反馈率。

### 1.10 前后端交互与流式响应

#### 1.10.1 SSE 流式响应是怎么实现的？

- 流式查询会先生成task_id，并创建一个 queue。

- 后台跑查询图，答案节点调用LLM stream。

- 每出来一段就往队列里放delta 事件。

- 前端通过 `/stream/{task_id}` 接收，最后收到 final 事件。

#### 1.10.2 SSE 和 WebSocket 有什么区别？为什么这里选择 SSE？

- SSE是服务端到客户端的单向推送，基于 HTTP，浏览器原生支持，自动重连，适合进度通知和大模型流式输出。

- WebSocket是双向通信，适合实时协作、在线聊天、频繁双向交互，交互成本高。

- 知识库问答主要是客户端提交问题后，服务端持续推送进度和答案，不需要高频双向通信，所以SSE 更简单、成本更低，也更容易和 FastAPI StreamingResponse 结合。

#### 1.10.3 文件导入这种长任务，前端如何感知处理进度？

- 上传接口先返回 task_id。

- 导入流程放到后台任务跑。

- 前端轮询 `/status/{task_id}` 看状态和节点列表。

## 2. 掌柜问数项目

### 2.1 项目架构图

### 2.2 问数项目串讲稿

#### 2.2.1 项目开篇介绍

掌柜问数是一个面向数据仓库的智能问数系统，主要解决业务人员查数依赖开发或数据分析师写 SQL 的问题。用户可以直接用自然语言提问，比如“统计一下华北地区上个月的销售额”，系统会自动理解问题，找到相关表、字段和指标口径，生成 SQL，完成校验和执行，最后把查询结果返回给用户。

从技术上看，这个项目以 Text2SQL 为核心，并在 SQL 生成前后补充了元数据召回、上下文精筛、SQL 校验、权限控制和 bad case 评测闭环。项目里重点建设了一套元数据知识库，把数据仓库中的表信息、字段信息、指标定义和字段取值示例统一管理起来，再结合向量检索、全文检索和 LangGraph 编排，把自然语言问题稳定地转成可执行、可校验、可控的 SQL 查询。

#### 2.2.2 构建流程

系统构建时，第一步是做元数据治理。元数据主要分为表信息、字段信息和指标信息。表信息里记录表名、表角色和业务描述；字段信息里记录字段名、字段别名、字段类型、字段角色、业务描述和字段取值示例；指标信息里记录指标名、指标别名、业务含义、计算口径和依赖字段。

第二步是建设元数据知识库。完整元数据存储在 MySQL 中，形成结构化的元数据中心；字段信息和指标信息会写入 Qdrant 构建向量索引，用于语义召回；常用维度字段的取值会写入 Elasticsearch 构建全文索引，用于精确匹配地区、类目、状态这类具体字段值。

#### 2.2.3 查询流程

查询时，问数 Agent 会用 LangGraph 编排整个执行链路，节点包括问题理解、关键词提取、字段召回、指标召回、字段取值召回、上下文精筛、SQL 生成、SQL 校验、SQL 修正和 SQL 执行。用户提出自然语言问题后，系统会先做问题理解，抽取时间范围、查询指标、过滤条件、分组维度和核心实体。之后进入多路召回：通过向量索引召回相关字段，通过向量索引召回相关指标，通过全文索引召回字段取值。

召回完成后，系统会做信息整合。命中某个指标时，会补充这个指标依赖的字段；命中某个字段取值时，会把取值挂到对应字段的示例值里；字段再按所属表进行分组。整理后再进行精筛，只保留生成 SQL 真正需要的表结构、字段说明、指标口径和字段示例，形成最小充分上下文。

接着，系统把用户问题和精筛后的元数据上下文交给大模型生成 SQL。SQL 生成后先做 SQL 解析、EXPLAIN 校验、权限校验和安全校验。语法或字段错误会进入修正节点重新生成；权限错误、危险 SQL 或连续修正失败会直接中断或返回澄清。校验通过后再执行 SQL，并把查询结果返回给用户。

#### 2.2.4 项目整体总结

> [!important] 核心价值
> 这个项目的核心价值是把业务人员依赖数据开发写 SQL 的过程，变成了自然语言问数流程。业务层可以更快拿到数据结果，技术层也能通过元数据、检索、校验、权限和评测机制控制 SQL 的准确性和安全性。

> [!important] 四大技术重点
> 1. **元数据知识库**：让模型理解数据仓库里的表、字段和指标
> 2. **多路召回**：从大量元数据里筛出当前问题需要的信息
> 3. **LangGraph 编排**：把问题理解、召回、生成、校验、修正和执行串成稳定链路
> 4. **评测和 bad case 闭环**：持续补充元数据、优化召回和提升 SQL 生成准确率

### 2.4 请介绍一下问数项目的整体流程和你主要负责的内容

掌柜问数是一个面向数据仓库的智能问数系统，目标是让业务人员通过自然语言查询数据，不需要自己写 SQL。系统会完成问题理解、元数据召回、SQL 生成、SQL 校验、查询执行和结果返回。

整体流程是：用户提出问题后，系统先做关键词提取和语义理解，再从元数据知识库里召回相关表、字段、指标定义和字段取值，然后把精筛后的上下文交给大模型生成 SQL。SQL 生成后先做 EXPLAIN 校验和权限校验，校验通过后再执行查询，最后把查询结果返回给用户。

我主要参与的是问数智能体链路，包括元数据知识库建设、表字段和指标召回、SQL 生成、SQL 校验、异常修正以及 bad case 优化。

### 2.5 Text2SQL 链路是如何实现的

Text2SQL 链路主要分为六步：问题理解、元数据召回、上下文组装、SQL 生成、SQL 校验、SQL 执行。

- 召回阶段：用户提出自然语言问题后，系统会先识别问题里的时间、指标、维度、过滤条件等信息，再召回相关字段、指标和字段取值。

- 生成阶段：召回结果会按表进行整理，并补充字段角色、字段描述、字段别名、指标口径和依赖字段。之后把用户问题和精筛后的元数据上下文交给大模型生成 SQL。

- 执行阶段：SQL 生成后先做 EXPLAIN 校验，确认语法和执行计划没有明显问题，再执行查询并返回结果。

### 2.6 自然语言转 SQL 是直接交给 LLM 吗，还做了哪些前置处理

不是直接交给 LLM。直接生成很容易表选错、字段选错，尤其数据仓库表多的时候更明显，必须要和元数据进行对齐。

- 前面会先做关键词抽取，代码里用了 jieba，再结合大模型扩展召回关键词。

- 之后分别召回字段、指标和字段值，字段和指标走 Qdrant 向量检索，字段值走 Elasticsearch。

- 最后还会做上下文合并和精筛，只给模型当前问题真正需要的表结构和指标口径

### 2.7 用户问题涉及哪些表和字段，这些表字段是怎么确定的

表和字段主要来自元数据知识库，而不是让模型凭空猜。

- MySQL 里存表信息、字段信息、指标信息，字段和指标又同步到 Qdrant，字段取值同步到 ES。

- 查询时先根据问题从Qdrant召回字段和指标,从ES召回字段值，再根据字段所属表、指标依赖字段、字段值命中结果把表结构补齐。

这样模型拿到的是结构化上下文，知道有哪些表、哪些字段、字段含义和示例值。

### 2.8 SQL召回的是全部表字段信息，还是只召回相关字段

SQL 生成前只召回相关表字段和指标定义，不会把全量 schema 直接传给模型。

### 2.9 如何保证给 LLM 的表结构和字段信息足够干净

核心做法是控制最小充分上下文。

除了通过Qdrant和ES召回指标、字段、字段值后。从MySQL提取相关表后。

使用了LLM专门对数据表的字段进行精筛。

### 2.10 关键表和字段是自动筛选还是人工配置，人工成本如何控制

人工治理的是元数据，不是每次查询人工参与。每次查询从元数据中提取信息。

### 2.11 表过滤和字段过滤是怎么做的

表过滤和字段过滤分为召回、补全和精筛三层。

- 召回阶段，根据问题语义召回字段和指标，根据关键词召回字段取值。

- 补全阶段，根据指标依赖补充字段，根据字段所属关系补充表信息，根据字段取值补充字段示例。

- 精筛阶段，再判断哪些表字段和当前问题真正相关，把无关信息过滤掉，最后生成 SQL 上下文。

### 2.12 问数项目里用到了哪些关键词提取和语义理解技术

- 统计分词 用 jieba 的 TF-IDF 算法做初始关键词提取，同时做词性过滤——只保留名词、动词、形容词等

- LLM 语义扩展。在提示词中 针对字段、指标、字段值三种检索目标做不同的扩展策略—字段扩展要求推断"最小必要字段集合"，指标扩展专门做同义和缩写生成（比如"销售额"→"GMV"→"成交额"→"交易额"）值扩展提取用户问题中的实体名称和枚举值。三者并行执行，互不等

- 混合语义检索 用 BGE-large-zh-v1.5 做向量语义匹配；Elasticsearch 的 IK_MAX_WORD 做中文分词全文检索；

### 2.13 问数项目中的三路召回策略是什么，如何做融合和重排

**三路召回**

字段召回、指标召回、字段值召回。

字段召回负责找到可能用到的表字段，

指标召回负责找到业务指标。

字段值召回负责找到 SQL where 条件里的具体值。

**融合**

这三路召回的并不是同一种上下文，所以做的并不是rrf。把三种数据组合合并。

**三路合并**

融合时会把字段值挂回对应字段，把指标依赖字段补进字段集合。

然后按表分组，补充表描述和关键字段，最后再精筛一次，形成 SQL 上下文。

### 2.14 如何保证生成的 SQL 是用户想要的查询

方案：

#### 2.14.1 意图理解层：

在生成SQL之前，先用 LLM 把用户的自然语言解析成结构化意图（维度是什么、指标是什么、过滤条件是什么）如果存在歧义就主动反问用户，让用户确认。比如"上个月"可以理解为自然月或最近 30天

#### 2.14.2 生成过程的控制：

- 在提示词中写入根据用户问题检索 2-3 条最相似的历史正确 SQL 作为 Few-shot(少样本)示例，对LLM来说，实例比指令更有效

- 强制要求Chain-of-Thought(CoT, 思维链)让 LLM 先分析意图、匹配 Schema、再写SQL、最后自检。

#### 2.14.3 SQL 语义校验：

这是最核心的。生成 SQL 后，不只做 EXPLAIN 语法校验——我加了一个LLM语义校验节点，专门检查五件事：指标口径对不对（SUM 的是 order_amount 还是 order_quantity）、GROUP BY粒度对不对（按月还是按天）、过滤条件对不对、JOIN 对不对、时间范围对不对。还有一个反向校验——把SQL 给另一个LLM，问它"这条 SQL 在回答什么？"，然后和原问题对比，看是否一致。

#### 2.14.4 结果合理性校验：

SQL 执行完后，检查结果是否异常——空结果可能是因为WHERE 太严格，返回 10000 行可能忘了 GROUP BY，聚合值过大可能因为重复 JOIN 数据膨胀。发现有异常就主动提示用户。

#### 2.14.5 用户反馈闭环：

每次返回结果都附带"这个查询对吗？"的反馈入口。用户标记错误的 SQL 会被分析失败原因，用户纠正的SQL 会自动进入 Few-shot 示例库。这形成了一个持续改进的飞轮。

- 靠三路召回提取元数据让用户语义与数据库元数据尽量对齐。

- 粗筛精筛来压缩上下文

- explain做可执行校验

- 扩展：结果产生以后可以追加一步用llm对最终数据与原始问题进行审查反思。如果审查不合理，交给校正节点进行校正重新生成sql。

### 2.15 如何校验生成 SQL 的语法、权限和业务正确性

语法层面会使用 SQL 解析和 EXPLAIN，确认 SQL 可解析、表字段存在、执行计划能够生成。

权限层面在生成SQL前，讲登录用户的id、要查询的数据表传入后端的权限审查接口，如果通过则继续生成SQL，否则则提示用户数据权限不足。（扩展）

业务正确性可以在数据生成后让大模型对数据与原问题进行反思。（扩展）

### 2.16 EXPLAIN 能发现哪些 SQL 问题，哪些问题发现不了

EXPLAIN 能发现 SQL 语法错误 ，解决的是 SQL 能不能执行。

也可以得到Explain计划以后通过规则对性能指标做性能审查（扩展）。

发现不了业务需求是否对齐、约束是否遗漏，可以增加数据反思的环节（扩展）

### 2.17 SQL 生成失败时如何纠错，如何防止死循环

SQL 生成失败后，系统会把原始问题、生成的 SQL、错误信息和相关元数据上下文一起交给修正节点，让模型重新生成或局部修复 SQL。

防止死循环主要靠最大重试次数、错误类型判断和兜底策略。语法错误和字段错误可以进入自动修复；权限错误、危险 SQL、连续多次修复失败会直接中断，返回澄清问题或转人工处理。

### 2.18 如果 JOIN 的表选错了，如何发现和处理

如果JOIN的表选错，但语法却通过了，只能通过数据反思环节发现，然后把发现的问题，传给校正节点进行修复。（扩展）

要通过问题集经过结果对账和base case分析尽可能提前避免这种问题的发生。（扩展）

### 2.19 如何保证最终统计结果和业务系统数据对得上

执行层面通过召回元数据实现用户问题与数据库元数据进行对齐。

验证层面通过数据反思节点进行节点纠偏。（扩展）

要通过问题集经过结果对账和base case分析。（扩展）

### 2.20 Text2SQL 项目的准确率和 SQL 通过率是怎么评测的

通过率测试集进行评估，

准确率 = 数据正确个数 / 总个数

通过率 = SQL explain通过 / 总个数。

### 2.21 SQL正确率没有达到 100% 的原因有哪些，后续怎么优化

原因：

**召回字段失败**

项目中虽然采用了jieba分词+LLM扩展+三路召回，但是也有几个难以解决的问题。

- 中文查询到英文字段名的语义 GAP——用户说"收入"，但数据库字段叫order_amount。通用模型不一定能把他们映射到一起。

- 二是固定阈值score_threshold=0.6 一刀切，导致某些查询的正确字段被硬截断。

**上下文质量问题**

大模型裁剪本身也会出错——可能误删了需要的表、或保留了无关信息干扰生成。

**SQL 生成本身的局限**

大模型对复杂的查询容易写出语法正确但逻辑错误的SQL。

**校验层的盲区**

> [!warning] EXPLAIN 盲区
> EXPLAIN 只能检查表名和字段名是否存在，检查不了语义——你把 SUM(order_quantity) 当 GMV 算，EXPLAIN 会告诉你 SQL 完全没问题。

解决方案：

- 建 benchmark 让所有优化都有数据依据

- 加 Few-shot 动态示例，这是性价比最高的优化；

- 加 Chain-of-Thought 推理步骤

- 在 EXPLAIN 之后加一层 LLM 语义校验，问 这个 SQL 真的回答了用户的问题吗

- 把硬编码的阈值改成动态的

SQL 正确率达不到 100%，常见原因包括用户问题有歧义，涉及的口径和关联比较复杂。

基于bad case ，提取更多的用户问题术语，提炼到元数据中增加匹配的准确度。

增加数据反思节点的纠偏策略。（扩展）

从终端层面引导用户使用标准语述，减少歧义，FAQ等。

### 2.22 问数项目的数据权限是怎么做的，在哪个阶段鉴权

数据权限主要分为表级权限和行级权限。

在生成sql前用召回的元数据表+用户id传给权限审查接口。获得是否能访问的标志（表级权限），同时获得权限过滤条件（行级权限）。

权限过滤条件会强制追加到 SQL 中，确保用户只能查询自己有权限的数据范围。（扩展）

涉及敏感字段时，还会在字段选择和结果返回阶段做字段级控制和脱敏。（扩展）

### 2.23 如何防止 SQL 注入、越权查询、全表更新等安全风险

SQL注入问题：目前SQL生成用到数值都是和元数据匹配的，如果用户通过自然语义提供的恶意数值是匹配不到元数据的或者匹配到正常的元数据。不会产生注入效果。

权限控制：

在生成SQL前用召回的元数据表+用户id传给权限审查接口。获得是否能访问的标志（表级权限），同时获得权限过滤条件（行级权限）。

权限过滤条件会强制追加到 SQL 中，确保用户只能查询自己有权限的数据范围。（扩展）

全表更新：从SQL的执行函数就定死了，不允许写操作。

### 2.24 为什么问数项目不能只靠 Text2SQL，还要结合 RAG、工具调用或规则校验

因为用户的自然语义是非常不稳定不规范的，而本身的元数据又很多，如果不做RAG，不稳定的问题+大量的元数据上下文会让准确度大幅度下降。

### 2.25 如何把 Skill 嵌入到问数项目里

SKILL的优势主要是

- 能够提炼一些通用的高复用的能力，在多个场景下使用。

- 能够让大模型自主决定是否使用某些能力。

目前问数项目虽然有很多复用的场景，但是基本主要在本项目内用，不太适合复用给其他场景。

目前流程比较固定，暂时没有交给模型来判断是否使用某些能力。

综上，暂时没有特别需要提炼为SKILL的场景，未来对于处理一些通用能力比如各种文档格式的生成，可以考虑提炼为SKILL。

### 2.26 问数项目的数据导入工作量大吗，数据是怎么导入和维护的

导入工作主要是元数据不是实际数据，工作量还好，而且可以利用ai去整理。

同时也需要人工去审查、微调各种元数据，通过网页平台维护（扩展）

### 2.27 问数项目中 LLM API 调用和部署方式如何保证数据安全

- 数据权限-只展示系统放开的字段数据信息

简单回答：不涉及人工智能相关算法。

问数项目定位是大模型应用工程，主要是通过工程手段把整个从自然语言到数据产生，变得更加可控稳定。

### 2.29 查询语句优化做过哪些工作

- 利用jieba分词+LLM语义扩展 的双重关键词策略，全方位获取到元数据字段信息，保证后续SQL语句的准确性

- 利用set集合去掉重复字段，减少上下文噪音。利用prompt最了精确的分层约束：安全约束，方言约束进而保证生成sql的准确性

- 利用explain 校验与LLM自校正的闭环，保证sql输入的准确性

- 从历史查询记录中找出最相似的3-5条sql 直接写入到提示词中。

- 将高频查询sql语句查询结果集直接放入缓存。

目前暂时没有针对EXPLAIN反馈让大模型自动对SQL进行自动改写，主要考虑可能会影响业务数据的逻辑和正确性。

但是后台会监控慢查询日志，针对处理慢的SQL，会复查，补充对应的索引等操作。

### 2.30 Text2SQL 在项目中占比是多少，最终项目效果怎么样

这个项目本质上就是一个完整的 Text2SQL 系统，它不是项目的一个模块，而是项目的全部核心。我的工作流有 12 个节点，覆盖了从自然语言理解到 SQL 执行的全链路。如果要分的话，核心 Agent 工作流和检索层占代码量的 60% 左右，其余是API 服务、认证鉴权和部署配置。

> 常见查询 SQL 准确率基本能在 90% 以上，复杂的多表关联查询能在 80% 以上。

- 自我校验+修复机制：通过更高阶的大模型对生成的sql自我修复，进而保证sql的准确性

- 响应时间：端到端响应时间约3-10秒钟，主要耗时在大模型生成sql是需要获取字段与表关系上。

### 2.31 NL2SQL 采用了什么方案设计？核心难点是什么？有没有调研过业内做得好的产品（如蚂蚁、腾讯、火山的 Data Agent 架构）？

> [!important] 核心结论
> 整个方案中最大的难点其实不是把自然语言翻译成 SQL，而是把业务语义准确映射到正确的数据库、表、字段。

目前NL2SQL这个领域权威开源项目非常有限，很多都是BI厂商的闭源项目，大厂中开源的就是阿里的SpringAI DataAgent 和 京东的Data Agent 。本项目就是借鉴了京东 Data Agent 做的python化改造。

阿里的SpringAI DataAgent 过多的依赖java springAI生态。而且处理流程更长，利用plan-execute模式进行多轮理解和可行性判断。

### 2.32 查询涉及多少张表？最大表的数据量级大概多大？系统生成的 SQL 是简单的宽表查询，还是会涉及七八张表的复杂 Join？为什么不直接构建大宽表来解决多表关联查询问题，而是要设计多表关联？

数据表已经是经过轻度聚合的宽表，但是部分维度表还是单独保存以提高灵活度、适当控制冗余。

所以join并不会太多主要还是事实表和维度表的join。

涉及的表就几十张，最大表在千万级以内。

可以增加意图识别分流，把非sql类的提问分流走，节省token。

### 2.34 面对字段取值高度相似或实体名对齐后依然出现的幻觉，系统如何解决？例如提出具体场景“苹果笔记本”，系统如何判断是指产品还是水果？如果询问某产品，怎么识别出它是产品名称字段？

具体的字段值对齐，我们使用elasticsearch ,会匹配多个关键词，比如“苹果笔记本”那么笔记本就会提高优先匹配名称带有“笔记本”的商品，同时我们也会通过ai和人工维护扩词表，比如“苹果笔记本”会被扩词为Macbook。

### 2.35 现在的问数平台是否往上建了语义层或做了转换，而不是让大模型直接生成 SQL？

目前没有建语义层而是让大模型直接生成sql，因为语义转sql对于大模型本身不是难点，难点是如何把用户的语言拆解与标准语义或元数据进行对齐，实现精确召回。

### 2.36 当前使用的模型较小，有考虑过使用更大的模型吗？

因为准确率的问题核心难点在于如何对齐用户丰富的语言，在于前期的召回流程上，而不在于模型能力上。

由于数据安全考虑，需要本地部署，大尺寸的模型会增加模型本地部署的难度。

#### 3.2.1 项目开篇介绍

这个项目是一个电商场景下的 AI 客服系统，核心目标是让用户通过自然语言完成查订单、查物流、商品咨询、退款政策咨询、退款申请、转人工等操作。系统覆盖三类对话：任务型对话负责办理具体业务，知识型对话负责回答商品和规则类问题，闲聊兜底负责承接非业务问题和安全回复。

#### 3.2.2 系统整体架构

整体分为前端、AI 客服后端、电商业务后端、模型服务和知识服务几部分。

- 前端提供聊天窗口、订单卡片、商品卡片和消息展示；
- AI 客服后端负责对话理解、会话状态、流程编排、结构化结果校验和回复生成；
- 电商业务后端提供订单、物流、商品、退款等接口；
- 模型服务负责自然语言理解和结构化规划；
- 知识服务负责商品知识、平台规则、售后政策等内容的检索和问答。

#### 3.2.3 核心处理流程

主要分为两个阶段：

**意图识别阶段**

用户发起消息后，后端先读取用户ID、历史会话、当前正在办理的业务、已选中的订单或商品，再把当前问题交给大模型判断处理方向。

系统会把问题分成任务办理、知识咨询和普通闲聊三类。

**意图处理阶段**

任务办理会进入确定性的业务流程，比如查订单时收集订单号并调用订单接口，查物流时调用物流接口，申请退款时收集订单号和退款原因并做规则校验。知识咨询会结合知识库或知识图谱查询真实依据，再组织自然语言回复。闲聊会走安全兜底，避免回答敏感或不确定内容。

#### 3.2.4 多轮对话处理

系统会维护每个用户独立的会话状态，记录当前任务、已收集信息、历史对话和被暂停的任务。用户在查物流过程中临时询问客服电话，系统会将当前任务放入到挂起队列中，先处理临时问题，等处理完了临时询问再回到原来的物流查询。

#### 3.2.5 风控和稳定性

> [!tip] 面试一句话
> 高风险动作不会由大模型直接决定。大模型只负责识别用户意图和提取必要信息，真正的退款、订单修改、转人工等动作都由业务规则、接口返回和白名单控制。系统会校验处理方向是否唯一、业务流程是否存在、参数格式是否合法、订单和商品是否属于当前用户、接口是否返回真实数据。校验失败时停止执行并给出澄清或转人工回复。

#### 3.2.6 技术实现

后端使用FastAPI提供聊天接口，模型调用链路负责提示词渲染、模型调用和结构化结果解析。

流程编排采用类似LangGraph的状态图思想，把一轮对话拆成理解、决策、执行、检查和响应几个步骤。

#### 3.2.7 项目整体总结

> [!important] 核心定位
> 这个项目的核心定位是让大模型负责意图理解和结构化规划，业务执行由流程、规则和接口完成。最终系统具备多轮对话、任务中断恢复、订单商品卡片、知识咨询、退款风控、转人工、调试观测和回归测试能力，整体特点是可执行、可控制、可追踪。

### 3.4 请介绍一下AI客服项目的背景、目标和整体方案

这个项目是一个电商场景下的智能客服系统，目标是让用户用自然语言完成查订单、查物流、咨询商品信息、了解退款政策、提交退款申请、转人工等操作。

整体方案是三层架构：

- 前端负责聊天窗口和订单、商品卡片展示；

- AI客服后端负责对话理解、状态管理、流程编排和模型调用；

- 电商业务后端负责提供订单、物流、商品、退款等业务接口。用户发来消息后，客服后端会先读取这个用户的历史会话和当前状态，再判断用户是在办理业务、咨询知识还是普通闲聊，然后交给对应的处理链路。

项目里任务型对话用于处理订单、物流、售后这类明确流程；

知识型对话用于处理售前商品咨询、平台规则和政策问答，其中复杂知识问题可以结合知识库项目；

闲聊用于承接非业务对话并做安全兜底。项目的核心是让大模型负责意图理解和结构化规划，真正的业务动作由代码、流程配置和中台接口执行。

这样既能利用大模型理解自然语言，又能保证业务流程稳定可控。

### 3.5 AI客服项目为什么要做，解决了哪些业务问题

做这个项目主要是因为电商客服里有大量重复问题，比如订单到哪了、物流到哪了、能不能退款、商品有什么信息。

**效率与成本：从”堆人力”到”降本增效”**

- 实现全天24小时客服服务

- 业务增长不增人

**从回答问题转向解决问题**

- 根据用户的描述信息，能够真正解决用户的问题。例如取消订单查看平台政策

- 多模态交互，能够通过图片信息诊断错误原因

### 3.6 AI客服项目的整体链路是什么，用户从提问到得到答案经历哪些步骤

- 接收消息：用户在前端发送消息后，后端先把请求转换成系统内部统一的消息格式。

- 加载状态：系统根据用户 ID 读取历史会话、当前任务、已选中的订单或商品，知道用户之前聊到哪一步。

- 意图识别：如果是文本消息，系统会把用户问题、历史上下文、可用流程和知识类型交给大模型，让模型判断走任务、知识还是闲聊。

- 结果校验：模型输出后，系统会先校验，比如只能命中一条轨道、流程必须存在、命令必须合法、知识问答不能缺少必要对象。

- 执行回复：校验通过后，任务问题按流程执行，知识问题检索依据后回答，闲聊走兜底。最后保存本轮状态，把回复返回前端。

### 3.9 为什么选择本地部署模型，而不是直接调用外部API

- 成本优势：因为客服的特点是频繁但不需要太复杂的文本知识处理。所以本地轻量模型，更加经济实用。

- 数据安全：因为涉及用户订单等隐私数据。

### 3.10 AI客服如何识别商品名，用户输入商品名是否会做匹配评分

项目里优先支持的是对象消息机制。前端右侧会展示用户相关的订单和商品卡片，用户点击某个商品后，后端会把它记录为当前用户选中的商品。后续用户说“这个多少钱”“这个有相似款吗”，系统就能知道“这个”指的是哪个商品。

对于纯文本商品名，生产方案会对接商品知识库的agent 接口。商品知识库会从问题中提取商品名称和向量数据库中的商品根据相似度对齐。这个部分会有评分，如果有断档最高分则会直接匹配，如果有多个接近的中档分数的商品会追问用户让用户选择。（掌柜智库）

### 3.11 AI客服如何校验退款等信息是否合法，比如退款或用户提出不合理诉求时，AI客服如何避免直接同意高风险操作。

AI客服会根据业务规则回答用户退单相关政策问题。但是否能够退单不会交给大模型做决定，主要调用退单相关接口，根据接口返回值确认订单是否满足退单条件。

客户的特殊诉求交给人工客服。

### 3.12 Dify私有化部署也能支持文件导入、分片、API调用和任务拆解，为什么项目里没有直接使用Dify

Dify 私有化部署可以解决知识库、工作流、接口调用和原型搭建问题，但这个项目的重点是电商客服的细粒度业务状态控制。

项目里有很多Dify标准能力不容易精细表达的内容，比如订单商品卡片处理、任务中断和恢复、多个业务流程之间的切换、模型输出白名单校验、缺失信息自动填充、系统提示流程和业务流程叠加、退款等高风险动作控制。直接用Dify可以更快搭起来，但在复杂状态、代码级扩展、可测试性和业务风控上会受限。

因此项目选择自研核心引擎，Dify这类平台能力可以作为可参考的产品形态和外围能力。

### 3.13 为什么这个项目没有做成更产品化的平台能力，后续如何抽象成平台

这个项目当前更偏具体电商客服场景落地，优先目标是把查订单、查物流、商品咨询、退款申请、转人工和数字人链路跑通，所以没有一开始就做成通用平台。

后续要平台化，可以抽象出几类核心能力：流程配置中心、业务工具注册中心、知识意图配置中心、提示词管理、模型配置、渠道适配、权限和风控策略、会话观测、评测集和 bad case 管理。这样不同业务只需要配置新的流程、字段、业务接口、知识类型和渠道适配，不需要重写核心对话处理模块。

### 3.15 电商小二项目相比套壳大模型有什么优势

> [!important] 三大优势（vs 套壳大模型）
> - **计划能力**：套壳大模型通常让模型直接回答用户问题，而电商小二让模型先输出结构化计划。
> - **执行能力**：查订单、查物流、退款申请、保存状态这些动作都由代码和业务接口完成，不靠模型编。
> - **控制能力**：系统有任务状态、轨道校验、流程白名单、命令白名单和必要上下文校验，模型输出不能直接裸执行。

### 3.16 项目过程中遇到过哪些印象深刻的问题，最后是怎么解决的

比较典型的问题是大模型输出看起来格式合法，但内容不一定能执行。比如它可能同时判断用户既要办理业务又要咨询知识，也可能编出一个不存在的业务流程，或者一次开启多个流程。如果直接执行，系统状态会混乱，甚至导致业务错误。

解决方式是引入统一校验机制。校验器先检查一次只命中一个处理方向，再检查业务指令是否存在、指令类型是否合法、是否一次开启多个流程、业务流程是否真实存在；知识咨询也会检查知识类型是否存在，以及是否缺少订单或商品上下文。校验失败时停止执行并返回澄清问题。

> [!important] 核心结论
> 大模型输出不能直接信，必须通过结构化输出、白名单校验和澄清兜底来保证系统稳定。

### 3.18 结构化动作生成模型微调的目标和数据准备是什么

结构化动作生成模型的目标，是让大模型把用户自然语言稳定转换成系统可执行的结构化动作。比如用户说“帮我看看这个订单到哪了”，模型需要识别为订单或物流查询，并提取订单信息、当前上下文和后续动作。

微调数据主要来自高频客服流程和边界场景。样本需要覆盖查订单、查物流、商品咨询、退款申请、转人工、闲聊兜底等路径，也要覆盖模糊意图、多意图、口语化表达、信息缺失、任务中断和恢复等情况。每条样本包含用户表达、历史上下文、期望的结构化动作和最终执行结果。

数据规模可以做到约一万条，按 8：2 划分训练集和验证集。模型可以基于 Qwen3-8B 做LoRA微调，再用vLLM部署。评估重点看意图识别准确率、结构化格式合法率、流程选择准确率、参数提取准确率和异常场景兜底率。

### 3.19 用户在对话中突然切换话题或中断当前任务时怎么处理

系统会为每个用户维护独立对话状态，记录当前信息。

如果用户打断切换话题，当前任务会被挂起，保存在数据库中。

挂起旧任务后会开启新任务，如果感知用户语义需要恢复之前的任务，则可以从之前的挂起任务，从挂起点继续。

### 3.20 新增一个客服业务流程时需要做哪些配置

新增客服业务流程时，需要定义流程名称、触发条件、需要收集的信息、每一步的追问话术、业务接口调用、结果判断、失败兜底和转人工规则。

比如新增“修改收货地址”流程，需要收集订单号、新地址、联系人和手机号；然后校验订单是否属于当前用户、订单是否还能修改地址、新地址格式是否合法；校验通过后调用业务接口提交修改；失败时返回明确原因，风险较高时转人工处理。

工程上我们将每个业务流程，需要哪些信息都进行了槽位配置，每个槽位代表了一种信息。

### 3.22 客服系统如何做调试、观测和回归测试

一开始只要跑通基本问答、办理流程。

然后准备测试集基于RAGAS跑评估测试，找到base case，排查问题

排查问题时，先看用户问题进入了哪条链路，再看模型判断是否正确、结构化结果是否合法、业务接口是否成功、回复是否引用了真实数据。这样能区分是意图识别问题、流程配置问题、接口问题、知识召回问题还是回复生成问题。

经过迭代优化后，让业务人员准备更真实的测试集和上线后的高频问题。再次进行回归测试。
